release-monitor / roadmap · specs · stack

Lernpfad · 2 Grundlagenmodule + 11 Projektphasen

Vom Lesen zum Schreiben: dein erstes eigenes Backend-Projekt

Diese Roadmap hat zwei Teile: zuerst Grundlagen (Sprache, Module, Async — anhand von Beispielen, die mit dem Projekt nichts zu tun haben), danach der Bau von release-monitor selbst — einem kleinen TypeScript/Node-Service, der GitHub-Releases überwacht und bei echten neuen Releases automatisch ein Ticket in Phasical anlegt, inklusive eigener CI/CD-Pipeline zu GHCR. Was in den Grundlagen erklärt wurde, wird in den Projektphasen nicht wiederholt — nur noch verlinkt.

Wie du das hier durcharbeitest

Du schreibst den Code — ich erkläre Konzepte, reviewe und gebe Hinweise, statt fertige Lösungen zu liefern. Jede Phase hat ein klares Lernziel, eine Aufgabe, typische Stolpersteine und ein Erfolgskriterium — also woran du merkst, dass es funktioniert, bevor du weitermachst. Nimm dir für jede Phase so viel Zeit wie sie braucht. Es gibt keine Deadline.

Teil 2: Das Projekt

PHASE 00 Setup & Grundlagen

Node/TS-Projekt aufsetzen, verstehen wie dein Code überhaupt ausgeführt wird — inklusive Vitest-Setup von Zeile eins an.

 PHASE 01 Konfiguration & Environment

YAML-Config einlesen, validieren, Env-Vars für Secrets nutzen.

 PHASE 02 Typen & der Source-Provider

TypeScript-Interfaces, erste echte HTTP-Requests gegen die GitHub API.

 PHASE 03 Datenbank: SQLite + Drizzle

Zentrales Schema, generierte Migrations, erste Queries.

 PHASE 04 Kernlogik: Baseline / Skip / Create

Reine Funktionen, deine erste Entscheidungs-Logik, erste Unit-Tests.

 PHASE 05 Der Ticket-Provider (Phasical)

Zweites Interface, authentifizierte POST-Requests, Fehlerbehandlung.

 PHASE 06 Orchestrierung: der Poll-Loop

Alle Bausteine zu einem Durchlauf zusammensetzen.

 PHASE 07 Scheduling & Status-Endpoint

Wiederkehrende Ausführung, ein minimaler HTTP-Server für /status.

 PHASE 08 Docker & Deployment

Dockerfile, Compose, Volumes — bereit für Coolify.

 PHASE 09 Ausblick: weitere Provider & mehr

GitLab/Codeberg, Jira, evtl. ein Frontend als Phase 2.

 PHASE 10 CI/CD: GitHub Actions → GHCR

Bei jedem Push automatisch testen, Image bauen und zu ghcr.io veröffentlichen.

Grundsätze für diesen Lernpfad

  • Grundlagen einmal, danach nur noch Cross-Reference. Was in G1/G2 erklärt wurde (Funktionen, Module, Interfaces, Async/Await, try/catch), wird in den Projektphasen nicht nochmal ausgewalzt, nur kurz verlinkt.
  • Ein Konzept pro Phase. Wenn du in Phase 03 noch mit SQL-Queries kämpfst, überspring nicht zu Phase 04.
  • Kein Copy-Paste-Code in den Modulen. Konzepte werden an generischen, projektfremden Beispielen gezeigt — die Übertragung auf dein Projekt machst du selbst.
  • Kein Schema-Drift. Ab Phase 03 gilt fest: Datenbankänderungen ausschließlich über generierte Drizzle-Migrations.
  • Tests von Tag eins, keine Ausnahme. Ab Phase 00 gilt: npm test muss grün sein, bevor ein Modul als fertig gilt — Unit-Tests mit Mocks für externe APIs, echte Integrationstests gegen eine isolierte Temp-DB.
  • Jede Phase endet lauffähig. Kein Modul hinterlässt kaputten Code — das Erfolgskriterium ist immer etwas, das du wirklich ausführen kannst.
