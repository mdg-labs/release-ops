Release Ops

Self-hosted dependency updates as pull requests and tickets, powered by Renovate. One GitHub App runs Renovate for every repository it is installed on and opens the update PRs as its own bot user; every update PR becomes a tracked ticket in Kaneo, Jira, or Linear; a dashboard lists open and merged update PRs. Users sign in with GitHub and get an admin or viewer role. Two services in one Docker Compose project: the app and the Renovate worker.

v2 at a glance

Renovate (pinned) GitHub App Go SQLite (WAL) Next.js COSS Kaneo Jira Linear

  • Update PRs from Renovate — stock open-source Renovate (AGPL-3.0, unmodified, pinned) as a separate process in the worker image; the bot user of the GitHub App authors the PRs (§2)
  • One GitHub App per instance, created through the manifest flow on /setup with a first-start setup token; bot identity, webhook sender, and login provider (§3)
  • Runs within seconds — ticking a Renovate checkbox in a PR or in the Dependency Dashboard starts a job via the webhook; without WEBHOOK_URL the instance polls (degraded) (§2.9, §2.11)
  • Tickets per update PR in Kaneo, Jira, or Linear — one ticket per PR, lifecycle follows the PR (updated, superseded, done on merge), with multiple project/team targets per integration, each with its own status mapping (§5)
  • Dashboard of open and recently merged update PRs, jobs with log excerpts and a Problems view (§8)
  • GitHub login with admin and viewer roles derived from organization and team membership (§3.7)
  • Two services — the worker has no database access, no data volume, and no Docker socket; only the app publishes a port (§10)
  • CI: entrypoint workflows + reusable CI/release/image build for both images (dev → nightly, main → VERSION draft, release → GHCR) (§11)
