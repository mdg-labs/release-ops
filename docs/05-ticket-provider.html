Der Ticket-Provider (Phasical)

Dasselbe Interface-Muster wie bei GitHub, diesmal für ausgehende, authentifizierte Requests.

Lernziel

POST-Requests mit JSON-Body. Authentifizierung über Header. Wiedererkennen, dass dies dasselbe Muster wie Phase 02 ist — nur die Richtung des Datenflusses dreht sich um.

Konzepte

POST statt GET

Bei GitHub hast du Daten abgeholt (GET). Jetzt sendest du Daten (POST) — du musst method, headers und einen body angeben. Generisches Beispiel — eine fiktive Bestell-API, nicht dein Projekt-Code:

const response = await fetch(url, {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "Authorization": `Bearer ${apiKey}`,
  },
  body: JSON.stringify({ item: "widget", quantity: 3 }),
});

JSON.stringify ist hier Pflicht — fetch verschickt sonst kein gültiges JSON, sondern die String-Repräsentation eines JS-Objekts ("[object Object]").

Warum das Interface trotzdem eigenständig bleibt

Auch wenn heute nur Phasical existiert, bekommt TicketProvider ein eigenes Interface (siehe Specs) — nicht weil du morgen Jira brauchst, sondern weil die Trennung dich zwingt, sauber zwischen "was ist ein Ticket" (fachlich) und "wie sende ich es an Phasical" (technisch) zu unterscheiden. Die Orchestrierung in Phase 06 kennt später nur ticketProvider.createTicket(...).

Mocking, diesmal inklusive Body-Prüfung

Gleiches Grundmuster wie in Phase 02 — fetch mocken — aber diesmal prüfst du zusätzlich, was du selbst rausgeschickt hast, nicht nur was zurückkommt. vi.fn() merkt sich alle Aufrufe in .mock.calls. Weiter am fiktiven Bestell-Beispiel:

const fetchMock = vi.fn().mockResolvedValue({
  ok: true,
  status: 200,
  json: async () => ({ orderId: "o-123" }),
});
vi.stubGlobal("fetch", fetchMock);

await createOrder({ item: "widget", quantity: 3 });

const [, options] = fetchMock.mock.calls[0]; // [url, options] — das sind die Argumente des ersten Aufrufs
expect(JSON.parse(options.body).item).toBe("widget");

Aufgabe

  1. src/providers/ticket.ts: TicketProvider-Interface und TicketInput-Typ aus den Specs.
  2. src/providers/phasical.ts: createPhasicalProvider(baseUrl: string, apiKey: string, projectId: string), das ein TicketProvider-Objekt zurückgibt.
  3. Innen: POST {baseUrl}/task/{projectId} mit dem Body-Format aus deinem n8n-Workflow (title, description, priority, status).
  4. Bei Erfolg: id aus der Response zurückgeben. Bei Fehler (Status nicht 2xx): einen aussagekräftigen Error werfen, der Statuscode und Response-Body enthält — das erspart dir später viel Rätselraten.
  5. Testweise in src/index.ts ein echtes Ticket anlegen und die zurückgegebene ID loggen.

Stolpersteine

  • Der status-Wert muss exakt einer echten Spalte/einem echten Status in deinem Phasical-Board entsprechen — schau in der UI nach, wie deine erste Kanban-Spalte technisch heißt.
  • Fehler beim ersten Versuch fast immer: falscher Authorization-Header (fehlendes Bearer -Präfix) oder falsche projectId.
  • Logge bei einem Fehler immer den Response-Body mit, nicht nur den Statuscode — die Fehlermeldung der API steht meist genau da drin.

Tests

Wende das Mocking-Muster von oben auf deinen createPhasicalProvider an. Mindestens diese zwei Fälle:

  • Erfolgreiche Response → createTicket(...) gibt die id aus dem gemockten JSON zurück, und du prüfst über fetchMock.mock.calls, dass der Authorization-Header korrekt gesetzt war und der Body deinen Titel enthielt.
  • Fehlerhafte Response (z.B. status: 401) → createTicket(...) muss einen Error werfen (await expect(...).rejects.toThrow()).

fetchMock.mock.calls[0] gibt dir die Argumente zurück, mit denen dein Mock aufgerufen wurde — so prüfst du nicht nur was zurückkommt, sondern auch was du rausschickst. Das ist besonders bei Auth-Bugs Gold wert.

Erfolgskriterium

Ein Testaufruf legt ein sichtbares Ticket in deinem Phasical-DevOps-Projekt an, und du bekommst dessen ID zurückgeloggt. Ein absichtlich falscher API-Key produziert eine Fehlermeldung, die dir sofort sagt, dass es an der Auth liegt. Die gemockten Tests laufen grün und prüfen sowohl Erfolgs- als auch Fehlerfall.
