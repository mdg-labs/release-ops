Konfiguration & Environment

Zwei Arten von Einstellungen trennen lernen: was in eine versionierte Config-Datei gehört, und was ein Secret ist, das nur zur Laufzeit existiert.

Lernziel

Environment-Variablen lesen (process.env). YAML-Dateien parsen. Eingelesene Daten mit zod gegen ein Schema validieren, statt blind zu vertrauen, dass die Datei richtig aussieht.

Konzepte

Warum zwei verschiedene Konfig-Wege?

repos.yml beschreibt was überwacht werden soll — das ist fachliche, unkritische Information, die man committen und im Git-Verlauf nachvollziehen will. PHASICAL_API_KEY dagegen ist ein Secret — landet nie im Git-Repo, sondern kommt zur Laufzeit über Environment-Variablen (in Docker: -e Flag oder .env-Datei, die selbst wieder in .gitignore steht).

process.env

Node stellt alle gesetzten Umgebungsvariablen unter process.env als Objekt bereit. Wichtig: jeder Wert ist ein String — auch Zahlen. process.env.POLL_INTERVAL_MINUTES ist also "360", nicht 360, und muss vor der Nutzung mit Number(...) umgewandelt werden.

const port = Number(process.env.PORT ?? "3000");

Der ??-Operator ("nullish coalescing") liefert den rechten Wert nur, wenn der linke null oder undefined ist — praktisch für Defaults.

YAML parsen

Das npm-Paket yaml übersetzt eine YAML-Datei in ein normales JS-Objekt:

import { parse } from "yaml";
import { readFileSync } from "node:fs";

const raw = readFileSync("repos.yml", "utf-8");
const data = parse(raw); // ganz normales JS-Objekt, aber noch ungetypt (any)

Warum Validierung, nicht nur Parsen?

parse() sagt dir nicht, ob die Datei inhaltlich stimmt — ein Tippfehler wie onwer: statt owner: würde erst viel später als kryptischer undefined-Fehler auffallen. zod beschreibt die erwartete Form als Schema und gibt beim Einlesen sofort eine klare Fehlermeldung, wenn etwas nicht passt. Ein generisches Beispiel, losgelöst von unserem Projekt, damit du den Mechanismus siehst, ohne dass hier schon die Lösung für deine eigentliche Aufgabe steht:

import * as z from "zod";

const PersonSchema = z.object({
  name: z.string().min(1),
  age: z.number().int().positive(),
});

const person = PersonSchema.parse({ name: "Ada", age: 34 }); // wirft, wenn's nicht passt
// person.age ist jetzt typsicher als number bekannt, ohne dass du es selbst deklariert hast

import * as z from "zod" statt import { z } from "zod": seit Zod 4 (stabil seit 2025, npm install zod installiert automatisch diese Version) ist der Namespace-Import der empfohlene Weg — funktional identisch, aber so dokumentiert es Zod aktuell selbst. Falls du älteren Zod-3-Code aus Tutorials siehst: .parse() und .safeParse() funktionieren unverändert, nur einzelne String-Format-Validatoren wie E-Mail/URL haben sich verschoben (für dieses Projekt nicht relevant).

safeParse zum Testen von Validierung

Für Tests ist safeParse praktischer als parse — es wirft nichts, sondern gibt { success: boolean, ... } zurück:

describe("PersonSchema", () => {
  it("akzeptiert gültige Daten", () => {
    expect(PersonSchema.safeParse({ name: "Ada", age: 34 }).success).toBe(true);
  });

  it("lehnt negatives Alter ab", () => {
    expect(PersonSchema.safeParse({ name: "Ada", age: -1 }).success).toBe(false);
  });
});

Aufgabe

Jetzt bist du dran, das oben gezeigte Muster auf die echten Anforderungen aus den Specs anzuwenden — dort steht exakt, welche Felder repos.yml hat, aber nicht, wie du das als Zod-Schema baust. Das ist deine Übersetzungsarbeit:

  1. npm install yaml zod — beide sind Laufzeit-Dependencies (kein -D), da sie im fertigen Programm gebraucht werden, nicht nur beim Entwickeln.
  2. Lege im Projekt-Root eine Beispiel-repos.yml mit 1-2 Repos an (Format siehe Specs).
  3. Schreibe src/config.ts: ein Zod-Schema, das die komplette Struktur aus den Specs abbildet (Repo-Liste und den ticketing-Block), plus eine Funktion loadConfig(path: string), die die Datei liest, parsed, validiert und das typisierte Ergebnis zurückgibt. Exportiere dein Schema mit — du brauchst direkten Zugriff darauf für die Tests unten.
  4. Schreibe src/env.ts: eine Funktion, die alle Env-Vars aus den Specs ausliest, für Pflichtfelder (PHASICAL_API_KEY, PHASICAL_BASE_URL) beim Fehlen einen klaren Fehler wirft, und für optionale einen Default setzt.
  5. In src/index.ts: beide Funktionen aufrufen und das Ergebnis mit console.log ausgeben.

Stolpersteine

  • Vergiss nicht, dass Pfade relativ zum Arbeitsverzeichnis sind, aus dem du npm run dev aufrufst — nicht relativ zur .ts-Datei. Für absolute Sicherheit später CONFIG_PATH als Env-Var nutzen.
  • .parse() wirft eine Exception bei ungültigen Daten — das ist gewollt beim Start (lieber sofort crashen mit klarer Meldung, als später mit undefined kämpfen). Fang die Exception in index.ts ab und gib eine lesbare Meldung aus, statt einen rohen Stacktrace zu zeigen.

Tests

Schreib mindestens diese zwei Fälle für dein eigenes Schema (nach dem PersonSchema-Muster von oben, aber mit deinen echten Feldern):

  • Eine gültige Config (mit allen Pflichtfeldern aus den Specs) → safeParse(...).success muss true sein.
  • Eine Config, der ein Pflichtfeld fehlt (deine Wahl, welches) → success muss false sein.

Kein Dateisystem nötig — teste direkt gegen JS-Objekte, die du im Test von Hand hinschreibst, nicht über loadConfig().

Erfolgskriterium

Mit korrekter repos.yml gibt npm run dev das geparste, typisierte Config-Objekt aus. Wenn du absichtlich einen Tippfehler in die YAML baust (z.B. owner weglassen), bekommst du eine klare Zod-Fehlermeldung statt eines Absturzes irgendwo tief im Code. npm test bleibt grün, inklusive deiner neuen Config-Tests.
