Phase 09 von 10

Ausblick: weitere Provider & mehr

Der Lohn für die Interface-Arbeit aus Phase 02 und 05 — und ein paar Ideen für alles danach.

Warum diese Phase existiert

Kein neues Kern-Konzept mehr — stattdessen der Beweis, dass sich die Abstraktion aus den vorherigen Phasen ausgezahlt hat: Neue Provider hinzufügen, ohne bestehenden Code anzufassen.

Ein zweiter Source-Provider: GitLab

Weil runOnce in Phase 06 nur gegen das SourceProvider-Interface programmiert wurde, brauchst du für GitLab-Unterstützung keine Änderung an der Orchestrierungs-Logik — nur:

  1. Eine neue Datei src/providers/gitlab.ts mit createGitlabProvider(...), die dasselbe SourceProvider-Interface implementiert (GitLab-API-Endpoint statt GitHub).
  2. Eine kleine Factory-Funktion, die anhand von repoConfig.source ("github" vs. "gitlab") den passenden Provider auswählt.

Das ist der ganze Umfang der Änderung — ein guter Test, ob die Abstraktion aus Phase 02 wirklich sauber war.

Ein zweiter Ticket-Provider: Jira

Analog: src/providers/jira.ts implementiert TicketProvider, Auswahl über einen Konfig-Wert (ticketing.provider). Jira nutzt eine andere Auth-Methode (meist Basic Auth mit E-Mail + API-Token statt Bearer-Token) — guter Anlass, den Unterschied bewusst zu durchdenken, statt Code stumpf zu kopieren.

Mögliche Phase-2-Themen (eigenes Lernprojekt)

  • Frontend: eine kleine Übersichtsseite über den /status-Endpoint hinaus — eigenes Thema (React/Vue-Grundlagen, State Management), bewusst getrennt vom Backend-Kern.
  • Repos per UI statt YAML pflegen — bräuchte dann auch eine Schreib-API und ggf. Auth, also nochmal deutlich mehr Fläche.
  • Regex-Filter für Pre-Releases pro Repo, ähnlich wie beim github-release-monitor-Projekt, das wir als Referenz gefunden hatten — falls du doch mal Pre-Releases tracken willst.
  • Open-Sourcing: Lizenzwahl (z.B. MIT oder Apache-2.0, um AGPL-Themen zu vermeiden), README, CONTRIBUTING — falls du es wie geplant für andere Self-Hoster öffnen willst.

Womit du jetzt dastehst

Ein selbst geschriebener, funktionierender Docker-Service mit sauberer Interface-Architektur, versionierten DB-Migrations, Tests für die Kernlogik und echtem Produktionsverständnis vom TypeScript-Code bis zum laufenden Container. Das ist die Grundlage, auf der jedes weitere Projekt leichter wird.
