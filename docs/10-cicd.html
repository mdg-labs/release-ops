CI/CD: GitHub Actions → GHCR

Statt docker build von Hand auf deinem Rechner auszuführen: bei jedem Push baut GitHub selbst das Image und lädt es in die GitHub Container Registry (GHCR) hoch — bereit für Coolify, um es zu pullen.

Lernziel

Was eine GitHub-Actions-Workflow-Datei strukturell ist (Trigger, Jobs, Steps). Was GITHUB_TOKEN automatisch kann, ohne dass du ein eigenes Secret anlegen musst. Wie ein fertiges Image bei GHCR landet und wie du es taggst.

Konzepte

Was CI/CD hier konkret bedeutet

CI (Continuous Integration): bei jeder Änderung automatisch prüfen, ob der Code noch funktioniert (bei uns: npm test). CD (Continuous Delivery/Deployment): bei erfolgreicher Prüfung automatisch ein auslieferbares Artefakt bauen — bei uns ein Docker-Image, veröffentlicht auf ghcr.io, GitHubs eigener Container-Registry.

Aufbau einer Workflow-Datei

Eine GitHub-Actions-Workflow-Datei liegt immer unter .github/workflows/*.yml und hat drei Ebenen:

  • Trigger (on:) — wann soll der Workflow laufen? (z.B. bei jedem Push auf main)
  • Jobs (jobs:) — eine oder mehrere unabhängige Ausführungseinheiten, die auf einer frischen virtuellen Maschine laufen
  • Steps — einzelne Schritte innerhalb eines Jobs, entweder eigene Shell-Befehle (run:) oder wiederverwendbare, von anderen gebaute Bausteine (uses:)

GITHUB_TOKEN — ein Secret, das du nicht selbst anlegen musst

Für jeden Workflow-Lauf erzeugt GitHub automatisch ein kurzlebiges Token namens GITHUB_TOKEN, verfügbar als secrets.GITHUB_TOKEN. Es reicht, um Pakete in dein eigenes Repository bei GHCR zu veröffentlichen — kein Personal Access Token, kein manuelles Secret-Anlegen nötig. Du musst nur explizit erlauben, wofür es genutzt werden darf, über den permissions-Block im Workflow.

Die drei Bausteine für Docker → GHCR

Statt docker build/docker push von Hand im Workflow aufzurufen, nutzt man drei offizielle, wiederverwendbare Actions (das entspricht dem aktuellen offiziellen GitHub-Tutorial, siehe Link unten):

ActionAufgabe
docker/login-actionMeldet sich bei einer Registry an (hier: ghcr.io, mit github.actor als Username und GITHUB_TOKEN als Passwort).
docker/metadata-actionErzeugt sinnvolle Tags & Labels für das Image, abgeleitet z.B. vom Branch-Namen oder Git-SHA — du musst sie nicht selbst zusammenbauen.
docker/build-push-actionBaut das Image gemäß deinem Dockerfile und pusht es, wenn der Build erfolgreich war.

Der komplette Workflow

Angepasst an unser Projekt (Trigger: Push auf main, statt wie im GitHub-Beispiel auf einen separaten release-Branch) — jedes YAML-Feld einzeln erklärt darunter:

name: Build and publish image

on:
  push:
    branches: ["main"]

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Log in to the Container registry
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Extract metadata (tags, labels) for Docker
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}
          tags: |
            type=raw,value=latest,enable={{is_default_branch}}
            type=sha,prefix=

      - name: Build and push Docker image
        uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
FeldBedeutung
on: push: branches: ["main"]Der Workflow läuft bei jedem Push auf main — also nach jedem Merge, nicht bei jedem Push in einen Feature-Branch.
env:Wiederverwendbare Variablen für den ganzen Workflow. ${{ github.repository }} ist ein von GitHub bereitgestellter Kontext-Wert — z.B. dein-user/release-monitor.
permissions:Ohne packages: write darf der automatisch generierte GITHUB_TOKEN nichts bei GHCR veröffentlichen — Standardverhalten ist restriktiv, du musst explizit erlauben.
runs-on: ubuntu-latestDie virtuelle Maschine, auf der der Job ausgeführt wird — von GitHub bereitgestellt, kostenlos im üblichen Rahmen für öffentliche Repos.
uses: actions/checkout@v4Ohne diesen Schritt hat der Runner keinen Zugriff auf deinen Code — er checkt dein Repository in die virtuelle Maschine aus.
tags: | type=raw,... / type=sha,...Zwei Tags pro Build: latest (nur auf dem Standard-Branch) und der Git-Commit-SHA (immer) — so kannst du später ein exaktes Image aus einem bestimmten Commit referenzieren, nicht nur "die aktuellste Version".
steps.meta.outputs.tagsDas id: meta beim vorherigen Step erlaubt es, dessen Ergebnis (outputs) in einem späteren Step wiederzuverwenden — ähnlich wie eine Variable, die zwischen Steps weitergereicht wird.

Aufgabe

  1. .github/workflows/docker-publish.yml mit dem Workflow oben anlegen (Image-Namen ggf. anpassen).
  2. Erweitere den Workflow um einen eigenen, vorgeschalteten Job test, der Node/npm einrichtet (actions/setup-node@v4 mit node-version: 24) und npm ci + npm test ausführt. Der build-and-push-Job soll erst starten, wenn test erfolgreich war — dafür gibt es needs: test auf Job-Ebene.
  3. Push auf main (oder committe testweise direkt dorthin, falls du (noch) ohne Branch-Schutz arbeitest) und schau im "Actions"-Tab deines Repos zu, wie der Workflow läuft.
  4. Nach erfolgreichem Lauf: Repo → "Packages" (rechte Seitenleiste) → dein Image sollte dort auftauchen, mit den beiden Tags.

Stolpersteine

  • Neu veröffentlichte Packages sind bei GHCR standardmäßig privat, auch wenn dein Repo öffentlich ist — für ein docker pull von deinem Coolify-Server aus musst du entweder die Package-Sichtbarkeit auf "public" stellen (Package-Settings) oder dort ein Zugangstoken hinterlegen.
  • needs: test muss exakt den id-Namen (nicht den name:-Anzeigetext) des vorherigen Jobs treffen.
  • Image-Namen bei GHCR müssen komplett kleingeschrieben sein — ${{ github.repository }} enthält aber deinen GitHub-Usernamen genau so, wie du ihn geschrieben hast. Falls dein Username Großbuchstaben enthält, brauchst du einen zusätzlichen Schritt, der den Namen kleinschreibt (z.B. via ${{ github.repository }} durch eine kleine Shell-Zeile mit tr '[:upper:]' '[:lower:]' ersetzen), sonst schlägt der Push fehl.

Erfolgskriterium

Ein Push auf main triggert automatisch beide Jobs, test läuft vor build-and-push, und am Ende erscheint ein neues Image unter "Packages" in deinem GitHub-Profil/Repo, mit einem latest- und einem SHA-Tag.
