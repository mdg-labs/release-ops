Typen & der Source-Provider

Dein erster echter HTTP-Request gegen eine externe API — und das Interface-Pattern, das später GitLab/Codeberg günstig macht.

Lernziel

TypeScript interface vs. konkrete Implementierung. Die fetch-API. async/await. Umgang mit HTTP-Statuscodes (insbesondere 404).

Konzepte

Interfaces und async/await/Promises wurden bereits in G2 — Objekte, Arrays, Interfaces, Async/Await behandelt. Falls dir das noch neu ist: schau kurz dort vorbei, hier geht's direkt mit dem projektspezifischen Teil weiter.

Statuscodes sind kein "Fehler" im try/catch-Sinn

Wichtiger Stolperstein: fetch wirft keine Exception bei HTTP-4xx/5xx-Antworten (z.B. 404). Es wirft nur bei echten Netzwerkfehlern (DNS, Verbindung abgebrochen). Den Statuscode musst du selbst prüfen:

const response = await fetch(url);
if (response.status === 404) {
  return null; // kein Release vorhanden — kein Fehler, sondern ein gültiger Zustand
}
if (!response.ok) {
  throw new Error(`GitHub API Fehler: ${response.status}`);
}

Welche Header die GitHub-API aktuell erwartet

Laut aktueller GitHub-REST-API-Doku gehören drei Header in jeden Request, nicht nur die Auth:

HeaderZweck
Authorization: Bearer <token>Nur setzen, wenn ein Token vorhanden ist — die Latest-Release-Route funktioniert für öffentliche Repos auch ohne, nur mit niedrigerem Rate-Limit.
Accept: application/vnd.github+jsonSagt der API, dass du das Standard-JSON-Format willst. GitHub empfiehlt das explizit statt sich auf einen impliziten Default zu verlassen.
X-GitHub-Api-Version: 2022-11-28Pinnt deinen Request auf eine bestimmte API-Version. Ohne diesen Header bekommst du automatisch die neueste Version — pinnst du sie, brechen zukünftige GitHub-API-Änderungen deinen Code nicht unangekündigt. 2022-11-28 ist aktuell (Stand 2026) die einzige stabile Version — GitHub versioniert die REST API nur bei echten Breaking Changes, nicht laufend.
User-Agent: release-monitorPflichtfeld bei GitHub — ohne gültigen User-Agent bekommst du teils 403. GitHub empfiehlt einen Wert, der dein Projekt identifiziert.

GitHub REST API Docs: Get the latest release — die offizielle Referenz für den Endpoint, den du hier ansprichst.

Aufgabe

  1. Lege src/providers/source.ts an mit dem SourceProvider-Interface und dem Release-Typ aus den Specs.
  2. Lege src/providers/github.ts an: eine Funktion createGithubProvider(token?: string), die ein Objekt zurückgibt, das SourceProvider implementiert.
  3. Innen: GET https://api.github.com/repos/{owner}/{repo}/releases/latest aufrufen, mit allen vier Headern aus der Tabelle oben (Authorization nur falls token gesetzt ist).
  4. 404 → null zurückgeben. Anderer Fehlerstatus → Error werfen. Erfolg → Response-JSON auf dein Release-Objekt abbilden (tag_name → tag, html_url → url, usw.).
  5. In src/index.ts testweise aufrufen für ein echtes Repo (z.B. usekaneo/kaneo) und das Ergebnis loggen.

Stolpersteine

  • Fehlt der User-Agent-Header, bekommst du teils 403 statt der erwarteten Antwort — GitHub blockt Requests ohne erkennbaren Absender.
  • await vergessen ist der häufigste Fehler am Anfang — dann arbeitest du mit einem Promise-Objekt statt dem eigentlichen Wert. TypeScript warnt dich davor meistens, aber nicht immer.
  • Rate-Limit ohne Token: 60 Requests/Stunde — reicht zum Testen mit 1-2 Repos, aber leg dir trotzdem früh ein PAT an: GitHub → Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token. Für releases/latest auf öffentlichen Repos reicht ein Token ohne jegliche Berechtigungen (Public Repositories: Read-only ist der Default) — vergib keine weitergehenden Scopes, die du nicht brauchst.

Mocking: fetch für einen Test austauschen

In einem Test willst du nicht wirklich gegen eine echte API laufen (langsam, Rate-Limit, nicht reproduzierbar wenn sich Daten ändern). Stattdessen ersetzt du fetch testweise durch eine Fake-Funktion, die genau das zurückgibt, was du für den Testfall brauchst. Generisches Beispiel — eine fiktive Wetter-API, nicht dein Projekt-Code: 

import { vi, afterEach } from "vitest";

afterEach(() => {
  vi.unstubAllGlobals(); // wichtig: sonst beeinflussen sich Tests gegenseitig
});

// im Test:
vi.stubGlobal("fetch", vi.fn().mockResolvedValue({
  ok: true,
  status: 200,
  json: async () => ({ temperature: 21 }),
}));

vi.stubGlobal("fetch", ...) ersetzt die globale fetch-Funktion nur für die Dauer des Tests. Ruft dein Code jetzt intern fetch(...) auf, bekommt er die gemockte Antwort statt eines echten Netzwerk-Requests.

Tests

Wende das Mocking-Muster von oben auf deinen createGithubProvider an. Schreib mindestens diese zwei Fälle:

  • Gemockte Response mit status: 404 → getLatestRelease(...) muss null zurückgeben.
  • Gemockte Response mit status: 200 und einem json(), der ein realistisches GitHub-Release-Objekt liefert (tag_name, html_url, published_at, ...) → das zurückgegebene Release-Objekt muss die korrekt gemappten Felder enthalten (tag, url, publishedAt).

Schau dir für den zweiten Fall einmal eine echte Antwort an (z.B. curl https://api.github.com/repos/usekaneo/kaneo/releases/latest), damit dein Mock-JSON realistisch aussieht.

Erfolgskriterium

npm run dev gibt für ein echtes Repo Tag, Name und URL des aktuellen Releases aus. Für ein Repo ohne Releases (oder einen absichtlichen Tippfehler im Namen) bekommst du sauber null zurück, keinen Absturz. Die gemockten Tests laufen grün, ohne dass dabei ein echter Netzwerk-Request passiert (das kannst du prüfen, indem du dein WLAN kurz trennst — die Tests bleiben grün).
