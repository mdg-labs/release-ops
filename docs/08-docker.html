Docker & Deployment

Aus dem Node-Prozess auf deinem Rechner wird ein Image, das genauso auf deinem Coolify-Server läuft.

Lernziel

Multi-Stage-Builds verstehen — warum das Produktions-Image nicht denselben Inhalt hat wie dein Entwicklungsordner. Volumes für persistente Daten (SQLite-Datei, Config).

Konzepte

Warum "Multi-Stage"?

Zum Bauen brauchst du TypeScript, alle Dev-Dependencies, den Compiler. Zum Laufen brauchst du nur noch fertiges JavaScript und die paar Production-Dependencies. Ein Multi-Stage-Build trennt das in zwei Etappen — das Endimage enthält nur, was für die Ausführung nötig ist, und bleibt dadurch deutlich kleiner: 

# Stage 1: bauen
FROM node:24-slim AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm test        # Build bricht ab, wenn Tests fehlschlagen
RUN npm run build   # tsc -> dist/

# Stage 2: laufen
FROM node:24-slim
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/drizzle ./drizzle
CMD ["node", "dist/index.js"]

COPY --from=builder holt gezielt nur fertige Artefakte aus der ersten Stage — der ganze Build-Kram (TypeScript-Compiler, Quellcode, Dev-Dependencies) landet nie im finalen Image.

RUN npm test in der Builder-Stage ist bewusst platziert: schlägt ein Test fehl, bricht docker build komplett ab — ein kaputtes Image kann so gar nicht erst entstehen, geschweige denn deployed werden.

node:24-slim statt nur node:24: das -slim-Tag enthält ein deutlich abgespecktes Debian ohne unnötige Tools — kleineres Image, weniger Angriffsfläche. Node 24 ist Stand August 2026 die aktuelle Active-LTS-Version (siehe Phase 00).

Befehle im Detail: npm ci vs. npm install

BefehlUnterschied
npm installKann package-lock.json aktualisieren, wenn Versionen nicht exakt passen — nicht deterministisch genug für einen reproduzierbaren Build.
npm ci"Clean Install": löscht zuerst node_modules komplett, installiert danach exakt die in package-lock.json fixierten Versionen. Schlägt fehl, wenn package.json und package-lock.json nicht zusammenpassen — genau das willst du im Build: lieber ein harter Fehler als eine stillschweigend andere Version im Image.
npm ci --omit=devWie npm ci, installiert aber nur dependencies, keine devDependencies — genau das richtige für die Runtime-Stage, in der TypeScript & Co. nicht mehr gebraucht werden.

Volumes für Dinge, die den Container überleben müssen

Ein Container-Dateisystem ist standardmäßig flüchtig — stirbt der Container, ist alles weg. Deine SQLite-Datei (DB_PATH) und die Config (repos.yml) müssen das überleben. Dafür mountest du Host-Verzeichnisse/-Dateien in den Container: 

# docker-compose.yml
services:
  release-monitor:
    build: .
    environment:
      - PHASICAL_API_KEY=${PHASICAL_API_KEY}
      - PHASICAL_BASE_URL=https://phasical.mdg-labs.dev/api
      - GITHUB_TOKEN=${GITHUB_TOKEN}
    volumes:
      - ./repos.yml:/config/repos.yml:ro
      - release-monitor-data:/data
    ports:
      - "3000:3000"

volumes:
  release-monitor-data:

Die Config wird :ro (read-only) gemountet — der Container soll sie nie selbst verändern.

Aufgabe

  1. In package.json Script "build": "tsc" ergänzen, testweise lokal npm run build ausführen und den entstandenen dist/-Ordner anschauen.
  2. Dockerfile nach obigem Muster anlegen, an dein Projekt angepasst.
  3. .dockerignore anlegen (mindestens node_modules, dist, .git) — verhindert, dass der Build-Kontext unnötig groß wird.
  4. docker build -t release-monitor . lokal ausführen.
  5. docker-compose.yml wie oben anlegen, mit einer echten repos.yml und einer .env-Datei für die Secrets.
  6. docker compose up — und via curl localhost:3000/status prüfen, dass es läuft.

Befehle im Detail

BefehlWas er tut
docker build -t release-monitor .-t ("tag") vergibt einen Namen fürs Image, unter dem du es später referenzierst. . am Ende ist der Build-Kontext — das Verzeichnis, aus dem Docker Dateien für COPY-Befehle lesen darf.
docker compose upBaut (falls nötig) und startet alle Services aus docker-compose.yml, blockiert das Terminal und zeigt Logs live an. Mit -d (detached) läuft es stattdessen im Hintergrund.
docker compose logs -fZeigt die Logs eines im Hintergrund laufenden Compose-Stacks weiter an. -f ("follow") hält den Stream offen, statt nur einmalig auszugeben.
docker compose downStoppt und entfernt die Container wieder — Volumes (deine SQLite-Daten) bleiben dabei standardmäßig erhalten, nur -v zusätzlich würde auch sie löschen.

Stolpersteine

  • Vergisst du, drizzle/ (die Migrations) mit ins finale Image zu kopieren, schlägt migrate() beim Containerstart fehl — die Migrations werden zur Laufzeit gebraucht, nicht nur beim Build.
  • better-sqlite3 enthält nativen (kompilierten) Code — stell sicher, dass npm ci innerhalb des Containers läuft (nicht nur lokal kopiert wird), damit die Binary zur Container-Architektur passt.
  • Der Ordner für DB_PATH (z.B. /data) muss dem Node-Prozess gehören/beschreibbar sein — bei Rootless-Containern ggf. explizit chown im Dockerfile.

Erfolgskriterium

docker compose up startet fehlerfrei, /status ist von außen erreichbar, und ein Container-Neustart verliert nicht die bereits bekannten Tags (Volume funktioniert).
