Setup & Grundlagen

Bevor du eine einzige Zeile Projektlogik schreibst: verstehen, wie ein Node/TS-Projekt überhaupt aufgebaut ist und wie dein Code vom Tippen bis zur Ausführung kommt.

Lernziel

Was package.json, tsconfig.json und node_modules jeweils tun. Wie du eine .ts-Datei ausführst. Was ein "Script" in package.json ist. Und: Testing ist von Zeile eins an dabei, nicht nachträglich draufgesetzt.

Konzepte

package.json — das Manifest deines Projekts

Jedes Node-Projekt hat eine package.json im Root. Sie beschreibt: Name, Version, welche externen Pakete gebraucht werden (dependencies), und benannte Kommandos (scripts), die du mit npm run <name> startest.

{
  "name": "release-monitor",
  "type": "module",
  "scripts": {
    "dev": "tsx watch src/index.ts"
  },
  "dependencies": {}
}

"type": "module" ist wichtig — es sagt Node, dass du moderne import/export-Syntax statt der alten require()-Syntax nutzt.

node_modules & npm install

Externe Pakete (Libraries) landen nach npm install <paket> im Ordner node_modules und werden automatisch in package.json unter dependencies eingetragen. Dieser Ordner wird nie ins Git-Repo committed (steht in .gitignore) — er wird bei jedem npm install aus der package.json neu aufgebaut.

Der Unterschied zwischen Dependencies und Dev-Dependencies: Dependencies (npm install <paket>) sind Pakete, die zur Laufzeit gebraucht werden. Dev-Dependencies (npm install -D <paket>, kurz für --save-dev) werden nur während der Entwicklung gebraucht (Compiler, Test-Runner, Typdefinitionen) und landen später nicht mit im Produktions-Image — dazu mehr in Phase 08.

tsconfig.json — Regeln für den TypeScript-Compiler

Legt fest, wie streng TypeScript prüft und in welches JS-Format kompiliert wird. Für dieses Projekt reicht ein schlankes Setup mit "strict": true — das schaltet die hilfreichsten Fehlerprüfungen ein (u.a. strictNullChecks: du musst null/undefined explizit behandeln, statt dass sie sich unbemerkt durchschleichen).

Wie dein Code ausgeführt wird

Zwei Wege, die du unterscheiden solltest:

  • Entwicklung: tsx führt .ts-Dateien direkt aus (übersetzt "on the fly" im Speicher, ohne eine Datei auf Platte zu schreiben).
  • Produktion / Docker: tsc kompiliert erst alle .ts-Dateien zu echten .js-Dateien in einen dist/-Ordner, dann führt node dist/index.js das kompilierte JS aus. Das machen wir erst in Phase 08.

Welche Node-Version

Node.js folgt einem LTS-Zyklus (Long Term Support): gerade Versionsnummern werden irgendwann zu "Active LTS" befördert und bekommen 30 Monate Support. Stand heute (August 2026) ist Node.js 24 die aktuelle Active-LTS-Version, Node.js 22 läuft noch in Maintenance-LTS (nur noch kritische Sicherheitsfixes). Nimm für ein neues Projekt Node 24 — falls du nvm nutzt: nvm install 24 && nvm use 24.

Warum das Test-Setup schon hier, nicht erst wenn's "Logik zu testen gibt"

Testing-Tooling nachträglich in ein gewachsenes Projekt einzuziehen ist immer unangenehmer als es von Anfang an dabei zu haben — genau wie bei der DB-Migrations-Regel gilt: keine Ausnahme "nur für den Start". Ab dieser Phase gibt es zu jedem Modul einen eigenen Test-Block. Hier richten wir nur das Werkzeug ein, mit einem bewusst trivialen ersten Test — der Inhalt wird ab Phase 01 sofort relevant.

Aufgabe

  1. Node.js 24 installieren, falls noch nicht vorhanden (siehe oben).
  2. Neuen Ordner release-monitor anlegen, darin npm init -y ausführen.
  3. "type": "module" in der generierten package.json ergänzen.
  4. npm install -D typescript tsx @types/node vitest — TypeScript, Direkt-Runner, Node-Typdefinitionen und Vitest als Dev-Dependencies.
  5. npx tsc --init ausführen, danach in der generierten tsconfig.json mindestens "strict": true und "module": "NodeNext" setzen.
  6. src/index.ts anlegen mit einer einzigen Zeile: console.log("release-monitor: hello").
  7. In package.json unter scripts ergänzen: "dev": "tsx src/index.ts" und "test": "vitest run".
  8. src/setup.test.ts anlegen mit einem einzigen, bewusst inhaltsleeren Test — nicht mehr als describe/it/expect auf irgendeine wahre Aussage (z.B. expect(1 + 1).toBe(2)). Wichtig: das ist noch kein Projekt-Code, sondern nur der Beweis, dass Vitest überhaupt läuft. Echte, inhaltlich sinnvolle Tests fürs Projekt schreibst du ab Phase 01 — dort gibt es dann auch wirklich etwas zu testen.
  9. npm run dev und npm test ausführen — beide müssen grün laufen, bevor du zu Phase 01 weitergehst.

Befehle im Detail

BefehlWas er tut
npm init -yLegt eine package.json mit Standardwerten an. -y ("yes") überspringt die interaktiven Rückfragen (Name, Version, Lizenz, ...).
npm install -D <pakete>-D = --save-dev. Installiert die Pakete und trägt sie unter devDependencies statt dependencies ein.
npx tsc --initnpx führt ein Kommando aus einem installierten npm-Paket aus, ohne dass du dessen Pfad kennen musst. tsc --init generiert eine tsconfig.json mit auskommentierten Standardoptionen.
npm run devFührt das Script dev aus deiner package.json aus — die Kurzform für tsx src/index.ts.
npm testKurzform speziell für das Script test — funktioniert auch ohne run davor (im Gegensatz zu allen anderen Scripts, die npm run <name> brauchen). vitest run (statt nur vitest) heißt: einmal alle Tests ausführen und beenden, statt im Watch-Modus laufen zu bleiben.

Stolpersteine

  • Wenn node dist/index.js: command not found oder ähnliches kommt: du versuchst wahrscheinlich, die .ts-Datei direkt mit node statt mit tsx auszuführen. Node kann kein TypeScript nativ lesen.
  • Cannot use import statement outside a module: "type": "module" fehlt in der package.json.
  • Committe niemals node_modules/ — leg direkt zu Beginn eine .gitignore mit dem Eintrag node_modules/ an.

Erfolgskriterium

npm run dev gibt release-monitor: hello in der Konsole aus, ohne Fehler. npm test zeigt einen grünen Test. Ab jetzt gilt: kein Modul gilt als fertig, solange npm test nicht grün ist.
