Phase 07 von 10

Scheduling & Status-Endpoint

Aus einem einmal laufenden Skript wird ein dauerhaft laufender Dienst.

Lernziel

Cron-Syntax lesen und schreiben. Ein minimaler HTTP-Server ohne Framework. Zustand (letzter Lauf, letzte Fehler) im Speicher halten und darüber ausliefern.

Konzepte

Cron-Syntax

Ein Cron-Ausdruck hat 5 Felder: Minute Stunde Tag-des-Monats Monat Wochentag. * bedeutet "jeder Wert", */6 bedeutet "alle 6 Einheiten":

0 */6 * * *   // Minute 0, alle 6 Stunden → 00:00, 06:00, 12:00, 18:00

Für einen konfigurierbaren Minuten-Wert (aus POLL_INTERVAL_MINUTES) baust du den Ausdruck als String zusammen: `*/${intervalMinutes} * * * *` — funktioniert sauber, solange der Wert unter 60 bleibt (was für dieses Projekt reicht).

import cron from "node-cron";

cron.schedule(`*/${intervalMinutes} * * * *`, () => {
  runOnce(config, sourceProvider, ticketProvider, db);
}, { noOverlap: true });

noOverlap: true ist eine Option der aktuellen node-cron-Version (4.x): läuft dein vorheriger Durchlauf noch (z.B. weil GitHub gerade langsam antwortet), wird der nächste geplante Tick übersprungen statt parallel gestartet zu werden. Ohne das könnten sich bei einem hängenden Request theoretisch mehrere runOnce-Läufe überlappen.

@types/node-cron wird nicht mehr gebraucht

node-cron ist seit Version 4 selbst in TypeScript geschrieben und bringt seine Typen direkt mit — ein zusätzliches @types/node-cron-Paket (früher üblich, für ältere Versionen) würde hier nur veraltete, potenziell falsche Typen installieren. Nicht mit installieren.

Ein HTTP-Server ohne Framework

Node bringt einen eingebauten HTTP-Server mit — für einen einzigen Endpoint musst du kein Express installieren:

import { createServer } from "node:http";

const server = createServer((req, res) => {
  if (req.url === "/status" && req.method === "GET") {
    res.writeHead(200, { "Content-Type": "application/json" });
    res.end(JSON.stringify(getStatus()));
    return;
  }
  res.writeHead(404);
  res.end();
});

server.listen(port);

Zustand im Speicher

getStatus() muss irgendwo herwissen, wann der letzte Lauf war und welche Fehler dabei auftraten. Am einfachsten: ein Modul-weites, veränderliches Objekt, das nach jedem Ereignis aktualisiert wird. Generisches Beispiel — ein simpler Zähler, nicht dein status.ts: 

// generisches Beispiel für Modul-State
let count = 0;

export function increment() {
  count += 1;
}

export function getCount() {
  return count;
}

Das ist bewusst simpel gehalten (kein Persistieren, kein Broadcast) — für einen internen Health-Check reicht In-Memory-Zustand völlig.

Aufgabe

  1. npm install node-cron — kein -D @types/node-cron nötig, siehe oben.
  2. src/status.ts nach demselben Muster wie increment/getCount oben, aber mit den Feldern aus dem /status-Response-Format in den Specs: recordRun(errors: string[]) setzt Zeitstempel und Fehlerliste, getStatus() gibt sie inkl. der Repo-Liste mit ihrem jeweils letzten bekannten Tag (Query aus Phase 03) zurück.
  3. src/server.ts: der minimale HTTP-Server mit dem /status-Endpoint.
  4. src/index.ts final zusammensetzen: Config/Env laden → Provider & DB aufbauen → einmal sofort runOnce ausführen → Cron-Job registrieren → HTTP-Server starten.
  5. runOnce so anpassen, dass es am Ende recordRun(errors) aufruft.

Stolpersteine

  • Läuft runOnce beim Start und ist der Cron-Job zusätzlich sofort fällig, kann es zu doppelten Läufen kommen — node-cron feuert aber standardmäßig erst beim nächsten Intervall-Tick, nicht sofort, das ist also meist unkritisch. noOverlap schützt zusätzlich davor, dass sich zwei Läufe zeitlich überlappen.
  • Der Prozess darf nicht beenden, nachdem runOnce einmal durchgelaufen ist — stell sicher, dass server.listen(...) und der Cron-Job den Node-Prozess aktiv am Leben halten (das tun sie von selbst, solange du nichts explizit beendest).

Tests

Für status.ts reicht ein einfacher Unit-Test ohne echten HTTP-Server — recordRun und getStatus sind reine Funktionen auf Modul-State, genau wie beim increment/getCount-Beispiel oben. Schreib mindestens einen Test, der recordRun mit einer Beispiel-Fehlerliste aufruft und danach prüft, dass getStatus() genau diese Fehler und einen nicht-null-Zeitstempel zurückgibt.

Den HTTP-Server selbst (createServer(...)) automatisiert zu testen würde ein Tool wie supertest brauchen — für dieses kleine Projekt reicht der manuelle curl-Check unten, das lohnt sich hier noch nicht.

Erfolgskriterium

Der Prozess läuft dauerhaft (bricht nicht nach dem ersten Durchlauf ab). curl -s http://localhost:3000/status | jq liefert ein sinnvolles JSON mit Zeitstempel und Repo-Liste (-s = "silent", unterdrückt curls eigene Fortschrittsanzeige; jq formatiert das JSON lesbar — falls nicht installiert, reicht auch curl http://localhost:3000/status ohne Pipe). Der Status-Test ist grün.
