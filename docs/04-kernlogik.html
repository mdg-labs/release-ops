Kernlogik: Baseline / Skip / Create

Das Herzstück des Projekts — und der Fall, für den Unit-Tests wie gemacht sind: kein Mocking nötig, keine Temp-DB, einfach Eingabe rein, Behauptung raus.

Lernziel

Reine Funktionen (pure functions) verstehen und warum sie am leichtesten zu testen sind — der einfachste Testfall im ganzen Projekt, im Gegensatz zum Mocking aus Phase 02 und der Temp-DB aus Phase 03.

Konzepte

Was eine "reine" Funktion ist

Eine reine Funktion hängt nur von ihren Eingabeparametern ab und hat keine Nebenwirkungen (keine Netzwerk-Requests, keine Datenbank, kein globaler Zustand). Gleiche Eingabe → immer gleiche Ausgabe.

// unrein: Ergebnis hängt von der aktuellen Zeit ab (Nebeneffekt "außen")
function isWeekend() {
  return [0, 6].includes(new Date().getDay());
}

// rein: Ergebnis hängt nur vom Parameter ab
function isWeekendFor(date: Date) {
  return [0, 6].includes(date.getDay());
}

Deine Entscheidungslogik (baseline/skip/create) braucht keine Netzwerk- oder DB-Zugriffe selbst — sie bekommt einfach zwei Strings übergeben (den bekannten Tag, falls vorhanden, und den aktuellen Tag) und liefert eine Entscheidung zurück. Das macht sie pur, und pure Funktionen sind der einfachste Code der Welt zu testen.

Die Entscheidung als Typ

Wie in G2 gezeigt: ein Union-Type statt eines losen Strings, damit TypeScript Tippfehler wie "skiped" abfängt:

type Decision = "baseline" | "skip" | "create";

Ein Test am generischen Beispiel

Vitest-Tests bestehen aus describe-Blöcken (Gruppierung) und it-Blöcken (einzelner Testfall) mit expect-Assertions. Am Beispiel von isWeekendFor von oben — nicht deine echte Entscheidungsfunktion, nur die Syntax:

import { describe, it, expect } from "vitest";
import { isWeekendFor } from "./example";

describe("isWeekendFor", () => {
  it("erkennt einen Samstag als Wochenende", () => {
    expect(isWeekendFor(new Date("2026-08-01"))).toBe(true);
  });

  it("erkennt einen Mittwoch nicht als Wochenende", () => {
    expect(isWeekendFor(new Date("2026-08-05"))).toBe(false);
  });
});

Aufgabe

  1. src/decide.ts: eine Funktion decide(knownTag: string | null, currentTag: string): Decision, die die drei Regeln aus den Specs ("Entscheidungslogik") umsetzt. Die Regeln stehen dort in Worten — wie du sie in if/else übersetzt, ist deine Entscheidung.
  2. src/decide.test.ts: mindestens drei Tests — einer pro möglicher Entscheidung, mit Tag-Werten deiner Wahl. Denk an den Edge-Case: was, wenn knownTag und currentTag zufällig identisch sind, obwohl knownTag nicht null ist? Sollte das ein vierter Testfall sein?
  3. npm test ausführen, bis alle Tests grün sind.

Stolpersteine

  • Widerstehe der Versuchung, hier schon die Datenbank abzufragen. Diese Funktion bekommt den bekannten Tag als Parameter — wer ihn aus der DB holt, ist Aufgabe der Orchestrierung in Phase 06.
  • Achte auf die Reihenfolge der Bedingungen: "kein bekannter Tag" muss vor "Tags unterschiedlich" geprüft werden, sonst wird null !== currentTag fälschlich als "create" gewertet.

Erfolgskriterium

npm test zeigt alle Tests grün. Du kannst laut erklären, warum diese Funktion ohne echte Datenbank oder API testbar ist.
