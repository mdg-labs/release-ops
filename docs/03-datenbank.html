Datenbank: SQLite + Drizzle

Der Baustein, der eure feste Regel umsetzt: Schema nur zentral, Migrations nur generiert, nie manuell.

Lernziel

Was eine Migration ist und wozu sie existiert. Ein Schema als Code definieren. Grundlegende SQL-Konzepte (SELECT, INSERT, UPSERT) und wie Drizzle sie in TypeScript abbildet.

Konzepte

Warum "Migration" statt einfach die DB-Datei anpassen?

Eine SQLite-Datenbank ist nur eine Datei. Du könntest sie manuell mit einem Tool öffnen und Spalten hinzufügen. Das Problem: diese Änderung existiert dann nur auf deinem Rechner. Auf dem Server, bei einem Neustart des Containers, oder bei jedem anderen, der das Projekt auscheckt, fehlt sie — das ist Schema-Drift: die reale Datenbankstruktur weicht vom Code ab, und niemand weiß mehr sicher, welcher Stand wo gilt.

Eine Migration ist stattdessen eine versionierte, im Git-Repo gespeicherte SQL-Datei, die eine Änderung exakt beschreibt (z.B. "füge Spalte X hinzu"). Jede Umgebung durchläuft beim Start dieselben Migrations in derselben Reihenfolge — die DB-Struktur ist damit reproduzierbar, genau wie der Code selbst.

Schema-first mit Drizzle

Du schreibst eine Tabellenstruktur einmal als TypeScript. Generisches Beispiel — ein Lesefortschritt-Tracker mit zusammengesetztem Unique Index, nicht unsere echte Tabelle, aber strukturell dasselbe Problem (zwei Spalten zusammen eindeutig, eine dritte wird bei Wiederholung aktualisiert): 

// generisches Beispiel
import { sqliteTable, text, integer, uniqueIndex } from "drizzle-orm/sqlite-core";

export const readingProgress = sqliteTable("reading_progress", {
  id: integer("id").primaryKey({ autoIncrement: true }),
  userId: text("user_id").notNull(),
  bookId: text("book_id").notNull(),
  page: integer("page").notNull(),
}, (table) => [
  uniqueIndex("user_book_idx").on(table.userId, table.bookId),
]);

Aus dieser Datei generiert drizzle-kit generate automatisch eine SQL-Migrationsdatei im Ordner drizzle/. Du schreibst nie selbst CREATE TABLE.

drizzle.config.ts — wie Drizzle Kit dein Projekt findet

Drizzle Kit (das CLI-Tool, das generate/migrate ausführt) braucht eine eigene Config-Datei im Projekt-Root, getrennt von deinem Laufzeit-Code — sie sagt dem Tool, wo Schema und Migrations liegen, nicht deiner App. Das ist reine Verkabelung, kein Rätsel — die kannst du 1:1 übernehmen:

// drizzle.config.ts
import { defineConfig } from "drizzle-kit";

export default defineConfig({
  out: "./drizzle",
  schema: "./src/db/schema.ts",
  dialect: "sqlite",
  dbCredentials: {
    url: process.env.DB_PATH ?? "./data/release-monitor.db",
  },
});

dialect: "sqlite" sagt Drizzle Kit, welchen SQL-Dialekt es beim Generieren der Migrations verwenden soll. dbCredentials.url braucht es auch bei einer lokalen Datei — nicht nur bei Netzwerk-Datenbanken —, weil einige Kit-Befehle (z.B. studio, eine optionale grafische DB-Oberfläche) sich direkt mit der Datei verbinden.

Migrations anwenden

Beim Programmstart lässt du Drizzle prüfen, welche Migrations schon angewendet wurden (das trackt Drizzle selbst in einer internen Tabelle) und wendet fehlende automatisch an — auch das ist Verkabelung, kein Rätsel:

import { migrate } from "drizzle-orm/better-sqlite3/migrator";
migrate(db, { migrationsFolder: "./drizzle" });

Das ist bewusst nicht derselbe Weg wie npx drizzle-kit migrate auf der Kommandozeile — dieser CLI-Befehl ist für manuelles Anwenden während der Entwicklung gedacht. Für den Container-Betrieb rufst du migrate() stattdessen programmatisch beim Start deiner App auf, wie oben gezeigt — dann läuft es automatisch mit, ohne dass jemand manuell ein CLI-Kommando ausführen muss.

Queries mit Drizzle

Weiter am generischen readingProgress-Beispiel — die Query-Struktur, die du für known_releases brauchst, ist dieselbe, nur mit anderen Spaltennamen:

import { and, eq } from "drizzle-orm";

// SELECT
const rows = db.select().from(readingProgress)
  .where(and(eq(readingProgress.userId, "u1"), eq(readingProgress.bookId, "b1")))
  .limit(1)
  .all();

// UPSERT (insert, oder update bei Konflikt)
db.insert(readingProgress)
  .values({ userId: "u1", bookId: "b1", page: 42 })
  .onConflictDoUpdate({
    target: [readingProgress.userId, readingProgress.bookId],
    set: { page: 42 },
  })
  .run();

Für onConflictDoUpdate auf zwei Spalten brauchst du dafür einen Unique Index auf genau diesen zwei Spalten im Schema — sonst weiß SQLite nicht, was "Konflikt" bedeutet.

Aufgabe

Jetzt überträgst du das Muster von oben auf die echte known_releases-Tabelle aus den Specs — dort stehen die Spalten (owner, repo, tag, ...), hier nicht nochmal die fertige Drizzle-Definition dafür:

  1. npm install drizzle-orm better-sqlite3 (Laufzeit) und npm install -D drizzle-kit @types/better-sqlite3 (nur Entwicklung/Build).
  2. src/db/schema.ts: die known_releases-Tabelle gemäß Specs, mit Unique Index auf (owner, repo) — analog zum readingProgress-Beispiel oben, aber mit deinen echten Spalten.
  3. drizzle.config.ts im Projekt-Root wie oben (das kannst du unverändert übernehmen).
  4. npx drizzle-kit generate ausführen — schau dir die generierte .sql-Datei in drizzle/ genau an, bevor du weitermachst. Prüfe, dass darin ein CREATE UNIQUE INDEX-Statement für owner+repo steht.
  5. src/db/client.ts: eine Funktion createDbClient(path: string), die den Ordner für die DB-Datei bei Bedarf anlegt, die SQLite-Verbindung öffnet, migrate() aufruft und den typisierten Drizzle-Client zurückgibt.
  6. In src/index.ts: einen Test-Datensatz einfügen/aktualisieren und danach mit einem SELECT wieder auslesen, zur Kontrolle loggen.

Befehle im Detail

BefehlWas er tut
npx drizzle-kit generateVergleicht dein aktuelles schema.ts mit dem letzten bekannten Snapshot (gespeichert in drizzle/meta/) und erzeugt bei Unterschieden eine neue, durchnummerierte SQL-Datei im out-Ordner. Ohne Unterschiede passiert nichts.
npx drizzle-kit migrateCLI-Variante zum manuellen Anwenden von Migrations gegen die in drizzle.config.ts konfigurierte DB — praktisch zum Testen, aber nicht das, was im Container läuft (dort übernimmt migrate() im Code diese Aufgabe automatisch beim Start).
npx drizzle-kit pushWendet Schema-Änderungen direkt an, ohne eine Migrationsdatei zu erzeugen — praktisch zum schnellen Prototypen, aber genau das, was unsere feste Projektregel ausschließt. Für dieses Projekt nutzen wir push nirgends.
npx drizzle-kit studioStartet eine lokale Web-Oberfläche zum Durchklicken der DB-Inhalte — optional, aber praktisch zum Debuggen, statt die SQLite-Datei mit einem separaten Tool zu öffnen.

Stolpersteine

  • Der Ordner für DB_PATH muss existieren, bevor better-sqlite3 die Datei anlegen kann — leg ihn beim Start programmatisch an (mkdirSync(..., { recursive: true })).
  • Vergisst du den Unique Index auf (owner, repo), funktioniert onConflictDoUpdate nicht wie erwartet — du bekommst einfach neue Zeilen statt Updates.
  • drizzle/ (die generierten Migrations) gehört ins Git-Repo — im Gegensatz zu node_modules/. Nicht in .gitignore aufnehmen.

Tests

Anders als in Phase 02: hier mockst du nichts. Ein Unit-Test mit gemockter DB würde nur beweisen, dass dein Mock sich wie erwartet verhält — nicht, dass Drizzle/SQLite/deine Migrations wirklich zusammenspielen. Das ist ein Integrationstest: er läuft gegen eine echte, aber isolierte SQLite-Datei, die pro Test neu angelegt und danach gelöscht wird. Das generische Grundmuster dafür (mit einer temporären Datei, ohne Bezug zu unserem Projekt): 

import { beforeEach, afterEach } from "vitest";
import { unlinkSync, existsSync } from "node:fs";

const TEST_DB_PATH = "./test-tmp.db";
let db; // dein DB-Client-Typ

beforeEach(() => {
  db = createDbClient(TEST_DB_PATH); // wendet Migrations frisch an, leere DB
});

afterEach(() => {
  if (existsSync(TEST_DB_PATH)) unlinkSync(TEST_DB_PATH);
});

beforeEach/afterEach sorgen für Testisolation: jeder Test startet mit einer sauberen, leeren DB und hinterlässt keine Datei. Ohne das würden sich Tests gegenseitig Daten unterschieben und je nach Ausführungsreihenfolge unterschiedlich fehlschlagen — ein klassischer, schwer zu findender Bug in Test-Suiten.

Bau darauf mindestens einen Test für known_releases: füg per db.insert(...).onConflictDoUpdate(...) zweimal denselben owner+repo mit unterschiedlichem tag ein, dann lies per SELECT nach — es darf nur eine Zeile existieren, und tag muss den zuletzt eingefügten Wert haben.

Erfolgskriterium

Nach dem ersten Start existiert die SQLite-Datei mit korrekt angelegter Tabelle. Führst du das Programm zweimal mit demselben owner+repo aus, bleibt es eine Zeile (Update), nicht zwei (kein Duplikat). Der Integrationstest bestätigt das automatisiert, und npm test hinterlässt danach keine test-tmp.db-Datei im Repo.
