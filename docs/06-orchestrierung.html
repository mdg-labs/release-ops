Phase 06 von 10

Orchestrierung: der Poll-Loop

Der Moment, in dem alle bisherigen Bausteine zum ersten Mal zusammenarbeiten — und wo Fehlerbehandlung anfängt, wirklich wichtig zu sein.

Lernziel

Mehrere async-Schritte zu einem Ablauf verketten. Warum ein Fehler bei einem Repo nicht den ganzen Lauf abbrechen darf. Schleifen über async-Operationen.

Konzepte

Der Ablauf in Worten

Für jedes Repo aus der Config, nacheinander:

  1. Aktuelles Release von GitHub holen (Phase 02)
  2. Falls null (kein Release) → dieses Repo überspringen, weiter zum nächsten
  3. Bekannten Tag aus der DB holen (Phase 03)
  4. Entscheidung treffen (Phase 04)
  5. Bei create: Ticket anlegen (Phase 05), dann Tag in DB speichern
  6. Bei baseline: nur Tag in DB speichern
  7. Bei skip: nichts tun

for...of mit try/catch, kombiniert

for...of mit await im Rumpf und try/catch einzeln sind schon aus G2 bekannt — neu ist hier, wo genau das try/catch sitzt. Wenn GitHub für ein Repo mal einen 500er wirft, sollen die restlichen 9 Repos trotzdem geprüft werden. Das erreichst du, indem du den riskanten Teil pro Repo innerhalb der Schleife in try/catch packst, statt einmal um den ganzen Loop:

for (const repoConfig of config.repos) {
  try {
    await processRepo(repoConfig);
  } catch (err) {
    console.error(`Fehler bei ${repoConfig.owner}/${repoConfig.repo}:`, err);
    // weiter zum nächsten Repo, nicht abbrechen
  }
}

Ein try/catch außerhalb der Schleife würde beim ersten Fehler die komplette Schleife abbrechen — genau das wollen wir hier nicht.

Aufgabe

  1. src/run.ts: eine Funktion runOnce(config, sourceProvider, ticketProvider, db), die den kompletten Ablauf oben umsetzt.
  2. Zerleg sie in eine Hilfsfunktion processRepo(repoConfig, ...) pro Repo, aufgerufen aus der Schleife mit try/catch wie oben.
  3. Sammle aufgetretene Fehler in einem Array (du brauchst sie in Phase 07 für den Status-Endpoint) statt sie nur zu loggen.
  4. src/index.ts so umbauen, dass es Config, Provider und DB-Client zusammensteckt (das nennt man "Dependency Injection" — die Abhängigkeiten werden von außen reingereicht, nicht innen fest verdrahtet) und runOnce einmal aufruft.

Warum Dependency Injection Tests einfach macht

Weil runOnce seine Provider von außen übergeben bekommt statt sie selbst zu erzeugen, kannst du im Test simple Fake-Objekte reinreichen, die dein Interface erfüllen, aber nie wirklich ins Netz gehen — kein Mocking-Framework nötig, nur ein Objekt mit der richtigen Form. Generisches Beispiel: eine fiktive processOrder-Funktion, die eine PaymentProvider-Abhängigkeit von außen bekommt: 

function fakePaymentProvider(shouldSucceed: boolean): PaymentProvider {
  return {
    charge: async () => {
      if (!shouldSucceed) throw new Error("card declined");
      return { transactionId: "tx-1" };
    },
  };
}

// im Test:
const result = await processOrder(order, fakePaymentProvider(true));

Genau dasselbe Prinzip wendest du gleich auf runOnce an — mit Fake-Objekten für SourceProvider und TicketProvider.

Tests

Kombiniert mit der echten Temp-DB aus Phase 03 (siehe dortiges Muster) ist das ein End-to-End-Integrationstest — er beweist, dass alle Bausteine zusammen tatsächlich das tun, was die Specs verlangen. Baue dir dafür:

  • Einen Fake-SourceProvider, dessen getLatestRelease einen Tag deiner Wahl zurückgibt (frei konfigurierbar, damit du zwischen zwei Aufrufen einen "neuen Release" simulieren kannst).
  • Einen Fake-TicketProvider, der einfach mitzählt, wie oft createTicket aufgerufen wurde.

Schreib damit mindestens diese drei Fälle:

  1. runOnce einmal gegen ein leeres, frisches DB aufrufen → createTicket darf nicht aufgerufen worden sein (Baseline-Fall).
  2. runOnce danach ein zweites Mal mit demselben Tag aufrufen → createTicket weiterhin nicht aufgerufen (Skip-Fall).
  3. runOnce ein drittes Mal mit einem anderen Tag aufrufen → createTicket jetzt genau einmal aufgerufen (Create-Fall).

Alle drei Aufrufe laufen gegen dieselbe Test-DB-Instanz (nicht jedes Mal neu anlegen) — sonst simulierst du keine aufeinanderfolgenden Polling-Läufe, sondern immer wieder einen ersten Lauf.

Stolpersteine (manuelle Kontrolle als Ergänzung)

  • Die automatisierten Tests oben decken die drei Pfade sauber ab — trotzdem lohnt sich einmal manuell gegen echte Repos zu prüfen: Eintrag aus der echten SQLite-Datei löschen und neu starten → baseline, kein Ticket. Nochmal starten ohne zu löschen → skip. Tag manuell auf einen älteren Wert setzen → create.
  • Ein Fake-Provider, der immer denselben Tag zurückgibt, verrät dir sofort, ob deine skip-Logik wirklich greift — falls stattdessen bei jedem Lauf ein neues Ticket entsteht, liegt der Fehler fast immer in der Upsert-Bedingung aus Phase 03.

Erfolgskriterium

Die Integrationstests aus dem Test-Block laufen grün und decken alle drei Entscheidungspfade automatisiert ab. Ein kompletter manueller Durchlauf über 2+ echte Repos funktioniert zusätzlich fehlerfrei.
