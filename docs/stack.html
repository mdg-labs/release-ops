Referenz

Tech-Stack & Werkzeuge

Was wir benutzen, und in einem Satz warum — damit du die Wahl nachvollziehen kannst statt sie hinzunehmen.

Sprache & Runtime

WerkzeugWarum
Node.js (LTS)Weitester Verbreitung, größtes Ökosystem, läuft überall wo Docker läuft.
TypeScriptTypen zeigen dir Fehler beim Schreiben statt erst zur Laufzeit — gerade als Einsteiger enorm wertvoll.
tsxFührt TS-Dateien direkt aus, ohne manuellen Kompilierschritt während der Entwicklung.

Daten

WerkzeugWarum
better-sqlite3Synchroner, schneller SQLite-Treiber — kein separater DB-Server nötig, eine Datei reicht.
Drizzle ORM + drizzle-kitSchema als TS-Code, Migrations werden automatisch generiert — erzwingt strukturell, dass die DB nie am Schema vorbei verändert wird.
zodValidiert die YAML-Config zur Laufzeit gegen ein Schema, mit lesbaren Fehlermeldungen.
yaml (npm package)Parst repos.yml in ein JS-Objekt.

Ausführung

WerkzeugWarum
native node:httpFür den einen /status-Endpoint reicht das eingebaute Modul — kein Express nötig für so wenig Oberfläche.
node-cronEinfache, lesbare Wiederholungs-Zeitpläne für den Poll-Loop.

Qualität

WerkzeugWarum
vitestSchneller Test-Runner mit vertrauter describe/it-Syntax, gute TS-Unterstützung out of the box. Wird schon in Phase 00 eingerichtet, nicht erst nachträglich.
eslint + prettierKonsistenter Stil, findet Flüchtigkeitsfehler automatisch.

Deployment

WerkzeugWarum
Docker (multi-stage build)Ein Image, überall lauffähig — passt zu deinem bestehenden Coolify-Setup.

Bewusst nicht genutzt

  • Kein Frontend-Framework — der Service hat keine UI, nur einen JSON-Endpoint. Siehe Phase 09 für den möglichen Nachtrag.
  • Kein PocketBase / kein BaaS — würde Admin-UI, Auth und generische REST-Endpoints mitbringen, die hier niemand braucht, und die eigentliche Logik trotzdem selbst geschrieben werden müsste.
  • Kein Prisma — braucht bei SQLite eine zusätzliche Query-Engine-Binary im Image. Drizzle kommt ohne aus und zeigt dir echtes SQL in den Migrations, was zum Lernen besser ist.
