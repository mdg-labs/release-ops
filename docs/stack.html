Tech stack

Two containers for self-hosting: the app (Next.js with the COSS UI, and Go for auth, the REST API, the job queue and the ticket engine) and the worker (the pinned, unmodified Renovate with a thin Go worker around it). The app owns one SQLite file app.db in WAL mode on volume /data; the worker has no database access.

This page lists tooling. Behaviour is specified in the spec (§2 Architecture, §10 Deployment); on conflict the spec wins.

Architecture at a glance

PartChoice
Update engineRenovate OSS — pinned to one version per release, unmodified, licensed AGPL-3.0-only, run as a separate child process of the worker, one per claimed job (§2.3). Release Ops is AGPL-3.0 as well. The Mend Renovate CE/EE images are not used. The licence notice and a source pointer for the pinned version ship in the worker image and on the About page (§8.3).
GitHubOne private GitHub App per instance, created through GitHub's manifest flow on /setup (§3.3). It is the bot identity, the webhook sender and the login provider. Exactly one installation (§3.4). GitHub (github.com) is the only platform in v2.0.
App ↔ workerThe worker claims jobs, heartbeats and posts results over HTTP through the app's internal listener (INTERNAL_ADDR, Compose network only, authenticated with WORKER_SECRET) — long-poll, no database access (§2.1).
QueueA persistent jobs table in SQLite behind a Go interface: one job per repository, a concurrency cap, a reserved high-priority slot, leases and a reaper (§2.8). Postgres can replace it later, for a hosted deployment only; v2.0 ships SQLite only.
TriggersGitHub webhooks (/hooks/github) start a run within seconds of a ticked checkbox; without WEBHOOK_URL the app falls back to polling (degraded) (§2.9, §2.11).
TicketsKaneo, Jira and Linear, one ticket per update PR (§5, §6).

Update engine — worker

ToolWhy
Renovate OSS (pinned)The update engine: managers, datasources, grouping, presets, lockfile updates. Unmodified, AGPL-3.0-only, run as a child process under a second Unix user that cannot read the worker secret; the Renovate base tag can be overridden at build time at your own risk (§9).
release-ops worker (Go)Claims a job, asks the app for a one-hour installation token scoped to the target repository and the preset repositories, starts Renovate, posts the redacted result (§2.2).
Global Renovate configA file in git, fetched at job start from GLOBAL_CONFIG_REPO / GLOBAL_CONFIG_REF or mounted into the worker; shown read-only in the UI, never parsed (§2.4).
binarySource=installLanguage tools are installed at run time; no Docker socket is mounted anywhere (§2.5, §2.6).

Data

FileContents
/data/app.db (app volume)GitHub users and sessions; instance and installation settings; the GitHub App (secrets encrypted), its installation and the synced repositories; ticket-system integrations and ticket projects; update PRs with their dependencies and tickets; the job queue, job history and webhook deliveries — spec §4, schema view, canonical DDL in db/schema.sql
/data/snapshots/ (app volume)VACUUM INTO snapshots the app writes before it applies pending migrations
Worker cache volumeDisposable per-slot Renovate caches. The worker has no /data volume and no database.

One SQLite file in WAL mode (with app.db-wal and app.db-shm beside it); the Go app is the only writer and Next never opens the DB. Backup and restore: spec §10.

Secrets

ToolWhy
AES-256-GCM (Go crypto/aes)Encrypts, in app.db: the GitHub App's private key, client secret and webhook secret, and the integration credentials of the ticket systems (§4.8). Decrypted only in the app's Go process; never returned by the API, never logged.
APP_ENCRYPTION_KEY32-byte key (hex) for that encryption. Keep it with every backup.
SESSION_SECRETSession cookie signing (Go auth).
WORKER_SECRETShared secret that authenticates the worker to the internal listener. Held by the worker process only; Renovate cannot read it. The worker never holds the encryption key or the App's private key.
SETUP_TOKENFirst-start setup token; only its SHA-256 hash is stored, single use (§3.2).
Installation tokensMinted in the app from an App JWT, valid about one hour, held in memory only, handed to the worker for the job it claimed.

Intentionally not used (v2)

  • No Docker socket and no Docker-in-Docker — Renovate runs as a child process of the worker with binarySource=install.
  • No database access from the worker — it has no data volume and reaches the app only through the internal listener.
  • No modified Renovate and no Mend Renovate CE/EE images — stock open-source Renovate, pinned, as a separate process.
  • No Shoutrrr and no notifications of its own — the ticket systems and GitHub already notify; failures show on the dashboard and in the metrics and health endpoints.
  • No mail — no SMTP, no email addresses.
  • No local accounts — no passwords, no bcrypt, no invitations or password reset, no seed-admin. GitHub is the only identity provider; roles (admin, viewer) are derived from GitHub, with no role editing in the UI.
  • No poll scheduler — no robfig/cron, no poll interval. Webhooks drive runs; the fixed timers (hourly safety net, reconcile, reaper) are described in §5.7; polling exists only as the degraded fallback without WEBHOOK_URL.
  • No release monitoring and no source providers — GitLab, Gitea, Forgejo and Codeberg releases are not watched; tickets follow update PRs, not releases.
  • No second platform in v2.0 — GitHub only; GitLab, GitHub Enterprise Server and private-registry hostRules come later (§1).
  • No Redis, and no Postgres in v2.0 — SQLite in WAL mode is enough for one self-hosted instance; the queue interface leaves room for Postgres in a later hosted deployment.
  • No YAML config for the app — everything via UI + app.db; Renovate's own global config is a file in git, shown read-only.
  • No Drizzle — Go stack uses sqlc + sqlite-migrate-generated migrations.
  • No Bitbucket / Azure DevOps — tickets in Kaneo, Jira and Linear only.
