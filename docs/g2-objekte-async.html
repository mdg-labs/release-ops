Objekte, Arrays, Interfaces, Async/Await & Fehlerbehandlung

Der zweite und letzte Grundlagen-Block, bevor's ans Projekt geht. Wieder komplett anhand generischer Beispiele.

Lernziel

Objekte und Arrays lesen/verarbeiten. Ein interface definieren und verstehen, was es von einer konkreten Implementierung unterscheidet. Was ein Promise ist. async/await sicher anwenden. Fehler mit try/catch behandeln.

Objekte

Ein Objekt bündelt zusammengehörige Werte unter benannten Schlüsseln (auch "Eigenschaften" oder "Properties" genannt) — statt mehrerer einzelner Variablen wie bookTitle, bookYear hast du ein Ding, das beides zusammenhält: 

const book = {
  title: "Dune",
  year: 1965,
};

Auf einzelne Werte greifst du über den Schlüsselnamen zu — meistens mit einem Punkt:

console.log(book.title); // "Dune" — Punkt-Notation, der Normalfall
console.log(book["title"]); // "Dune" — Klammer-Notation, macht dasselbe

Die Klammer-Notation brauchst du nur, wenn der Schlüsselname selbst in einer Variable steckt (z.B. book[someVariable]) — für den ganz normalen Fall reicht der Punkt.

Destructuring — Werte direkt beim Zugriff auspacken

Wenn du aus einem Objekt mehrere Werte brauchst, ist book.title, book.year immer wieder book. voranzustellen umständlich. Destructuring ist eine Kurzschreibweise, die dir erlaubt, mehrere Eigenschaften in einem Schritt in eigene, gleichnamige Variablen "auszupacken": 

const { title, year } = book;

Lies die linke Seite so: "nimm die Eigenschaften title und year aus dem Objekt rechts und leg sie als eigene Variablen mit exakt diesen Namen an." Nach dieser Zeile existieren zwei neue Variablen, title und year, mit den Werten "Dune" und 1965 — du musst danach nicht mehr book.title schreiben, nur noch title: 

console.log(title); // "Dune"
console.log(year);  // 1965

Am häufigsten begegnet dir das bei Funktionen, die ein ganzes Objekt als Parameter bekommen — statt im Funktionskörper ständig params.title zu schreiben, packst du direkt in der Parameterliste aus: 

function describe({ title, year }: { title: string; year: number }): string {
  return `${title} (${year})`;
}

describe(book); // "Dune (1965)"

Das sieht auf den ersten Blick verwirrend aus, weil zwei unterschiedliche Dinge geschachtelt sind: { title, year } ist das Destructuring (welche Werte du auspacken willst), { title: string; year: number } direkt danach ist die Typ-Annotation (welche Form das übergebene Objekt haben muss) — zwei separate geschweifte Klammern für zwei separate Zwecke, die zufällig gleich aussehen.

interface — einer Objekt-Form einen Namen geben

Die Typ-Annotation { title: string; year: number } von eben musstest du direkt in der Funktionssignatur ausschreiben. Brauchst du dieselbe Form an mehreren Stellen (Parameter, Rückgabewert, Array-Elemente, ...), willst du sie nicht jedes Mal neu hintippen. Ein interface gibt dieser Form einen Namen, den du überall wiederverwenden kannst: 

interface Book {
  title: string;
  year: number;
  subtitle?: string; // das ? macht die Eigenschaft optional, wie bei Funktionsparametern in G1
}

Ein interface beschreibt nur die Form — welche Eigenschaften mit welchen Typen existieren müssen —, nicht wie ein konkretes Objekt entsteht oder sich verhält. TypeScript prüft danach bei jeder Zuweisung automatisch, ob die Form passt: 

const dune: Book = { title: "Dune", year: 1965 }; // ok — subtitle fehlt, darf es aber wegen "?"
const broken: Book = { title: "Dune" };            // Fehler — year fehlt und ist nicht optional

Ein interface kann auch Funktionen beschreiben

Das ist der wichtigere Fall für unser Projekt: ein interface kann festlegen, dass "irgendetwas" eine bestimmte Funktion in einer bestimmten Form haben muss — ohne festzulegen, wie diese Funktion arbeitet. Das nennt man eine Abstraktion. Zwei komplett unterschiedliche Implementierungen können dasselbe Interface erfüllen: 

interface Greeter {
  greet(name: string): string;
}

const englishGreeter: Greeter = {
  greet: (name) => `Hello, ${name}!`,
};

const germanGreeter: Greeter = {
  greet: (name) => `Hallo, ${name}!`,
};

Beide Objekte, englishGreeter und germanGreeter, erfüllen dasselbe Greeter-Interface — sie haben beide eine greet-Funktion mit derselben Signatur, nur der Inhalt unterscheidet sich. Eine Funktion, die einen Greeter entgegennimmt, muss nie wissen, welchen konkreten Greeter sie bekommt: 

function announce(greeter: Greeter, name: string) {
  console.log(greeter.greet(name)); // kennt nur die Form, nicht welche konkrete Sprache
}

announce(englishGreeter, "Ada"); // "Hello, Ada!"
announce(germanGreeter, "Ada");  // "Hallo, Ada!"

Das ist genau der Mechanismus, den du im Projekt bei SourceProvider (GitHub heute, evtl. GitLab morgen) und TicketProvider (Phasical heute, evtl. Jira morgen) wiedersiehst.

type vs. interface

Für Objekt-Formen wie oben sind interface und type fast austauschbar — als Faustregel: interface für Objekt-Formen, type für alles andere. Der Fall, wo type etwas kann, das interface nicht kann, ist der Union-Type — "einer von mehreren festgelegten Werten": 

type Status = "active" | "paused" | "cancelled"; // nur genau diese drei Strings sind gültig

function setStatus(status: Status) { /* ... */ }
setStatus("active");     // ok, einer der drei erlaubten Werte
setStatus("unknown");    // Fehler — TypeScript kennt "unknown" nicht als gültigen Wert für Status

Arrays verarbeiten

Ein Book[] ist ein Array, dessen Elemente alle die Form Book haben. Statt mit einer Schleife selbst durchzuzählen und Ergebnisse einzusammeln, bevorzugt moderner JS/TS-Code eingebaute Array-Methoden — jede drückt eine klare Absicht aus, statt dass du den Mechanismus (Zähler, leeres Array, push) selbst nachbaust: 

const books: Book[] = [
  { title: "Dune", year: 1965 },
  { title: "Neuromancer", year: 1984 },
  { title: "Foundation", year: 1951 },
];

map — "wandle jedes Element um, gib ein gleich langes neues Array zurück":

const titles = books.map((b) => b.title);
// ["Dune", "Neuromancer", "Foundation"]

Lies das so: für jedes Element b im Array wird die Funktion (b) => b.title aufgerufen, ihr Rückgabewert landet an derselben Position im neuen Array. Aus 3 Büchern werden 3 Titel.

filter — "behalte nur die Elemente, für die die Bedingung true ergibt":

const recent = books.filter((b) => b.year > 1960);
// [{ title: "Dune", ... }, { title: "Neuromancer", ... }] — Foundation fällt raus (1951)

find — "gib das erste passende Element zurück, oder undefined wenn keins passt":

const oldest = books.find((b) => b.year < 1960);
// { title: "Foundation", year: 1951 }

Genau dieses undefined-als-möglichem-Ergebnis begegnet dir gleich in der Übung wieder — deshalb ist Book | undefined dort der korrekte Rückgabetyp, kein Bug.

some — "gibt es mindestens ein passendes Element? nur true/false":

const hasClassic = books.some((b) => b.year < 1960);
// true

Wichtig bei allen vieren: das Original-Array books bleibt unverändert — jede Methode gibt ein neues Ergebnis zurück, statt books selbst zu verändern.

Das Problem, das Promises lösen

Manche Operationen brauchen Zeit — ein Netzwerk-Request, ein Timer, eine Festplatten-Operation. Würde JavaScript dabei einfach warten (blockieren), stünde in dieser Zeit das gesamte Programm still, auch für alles andere, das nichts mit dieser einen Operation zu tun hat. Die Lösung: solche Operationen geben sofort ein Promise-Objekt zurück — ein Platzhalter, der sagt "der eigentliche Wert kommt später nach", während der Rest des Programms normal weiterläuft.

Ein Promise hat immer einen von drei Zuständen: pending (noch unterwegs), fulfilled (erfolgreich abgeschlossen, Wert liegt vor) oder rejected (fehlgeschlagen).

Ein eigenes Promise bauen — Zeile für Zeile

Das folgende Beispiel baut eine Funktion, die "warte X Millisekunden" als Promise verpackt — setTimeout selbst kennst du evtl. schon aus JS, es ruft eine Funktion erst nach einer Wartezeit auf:

function delay(ms: number): Promise<void> {
  return new Promise((resolve) => setTimeout(resolve, ms));
}

Zerlegt in Einzelteile:

  • new Promise(...) erzeugt ein neues Promise. Es bekommt eine Funktion übergeben, die sofort ausgeführt wird und als einzigen Job hat, irgendwann resolve aufzurufen, sobald der Wert bereit ist.
  • resolve ist selbst eine Funktion, die dir new Promise automatisch bereitstellt — rufst du sie auf, wechselt das Promise von pending zu fulfilled.
  • setTimeout(resolve, ms) heißt: "rufe die Funktion resolve nach ms Millisekunden auf" — resolve wird hier nicht selbst aufgerufen (kein resolve()), sondern nur als "das hier soll später ausgeführt werden" an setTimeout weitergereicht.
  • Promise<void> als Rückgabetyp heißt: "ein Promise, das am Ende keinen konkreten Wert liefert" — uns interessiert hier nur dass die Zeit um ist, nicht ein Ergebnis.

Diesen Aufbau musst du dir nicht merken, um ihn zu nutzen — delay ist ab jetzt einfach eine fertige Funktion, die du aufrufen kannst.

async/await — Promises lesbar konsumieren

Du könntest mit einem Promise über .then(...) arbeiten, aber async/await ist die lesbarere, heute übliche Syntax — sie lässt asynchronen Code aussehen wie ganz normalen, Zeile-für-Zeile ausgeführten Code: 

async function run() {
  console.log("Start");
  await delay(1000); // pausiert HIER, bis das Promise "fulfilled" ist
  console.log("Eine Sekunde später");
}

Zwei feste Regeln, die immer gelten:

  1. await darf nur innerhalb einer mit async markierten Funktion stehen — schreibst du await außerhalb, gibt's einen Syntaxfehler.
  2. Jede async-Funktion gibt selbst automatisch ein Promise zurück, egal was du returnest — run() von oben liefert also ein Promise<void>, auch ohne dass irgendwo Promise hingeschrieben steht. TypeScript wickelt das automatisch ein.

for...of mit await — der Grund, warum wir es in Phase 06 brauchen

Du kannst await auch innerhalb einer Schleife nutzen — dann wartet jeder Durchlauf, bis der vorherige fertig ist, bevor der nächste startet:

const delays = [100, 200, 300];

for (const ms of delays) {
  await delay(ms); // wartet bei diesem Durchlauf, bevor der nächste startet
  console.log(`${ms}ms vorbei`);
}
// Ausgabe kommt nacheinander: "100ms vorbei", dann "200ms vorbei", dann "300ms vorbei"

.forEach() würde hier nicht wie erwartet funktionieren: seine Callback-Funktion darf zwar async sein, aber forEach selbst ignoriert die zurückgegebenen Promises komplett und startet sofort den nächsten Durchlauf, ohne zu warten. Für "einer nach dem anderen, mit Wartezeit dazwischen" ist for...of deshalb die richtige Wahl, nicht forEach.

Fehlerbehandlung mit try/catch

Wenn innerhalb einer async-Funktion etwas fehlschlägt (ein Error geworfen wird, oder ein Promise "rejected"), musst du das behandeln — sonst läuft der Fehler entweder als unbehandelte Exception durch (Programmabsturz) oder verschwindet still, je nachdem wo er landet. try/catch gibt dir die Kontrolle darüber, was in diesem Fall passieren soll: 

async function safeDelay(ms: number) {
  try {
    await delay(ms);
    console.log("fertig");
  } catch (error) {
    console.error("Fehler beim Warten:", error);
  }
}

Alles zwischen try { und } wird normal ausgeführt. Passiert dabei ein Fehler, springt die Ausführung sofort in den catch-Block, mit dem Fehler-Objekt als Parameter (hier error genannt) — der restliche Code im try-Block danach wird übersprungen, aber das Programm läuft danach normal weiter, statt abzustürzen.

Ein ganzes Skript, das await braucht

await darf nur in einer async-Funktion stehen (Regel von oben) — aber deine `run2.ts` ist auf oberster Ebene erstmal keine Funktion, sondern lose ausgeführter Code. Die zuverlässige Lösung: alles, was await braucht, in eine eigene async function main() packen und diese am Ende der Datei einmal aufrufen: 

async function main() {
  console.log("Start");
  await delay(500);
  console.log("Ende");
}

main();

Das ist der eigentliche Übungsteil — diese 8 Zeilen kommen zwischen den Kommentar und die schließende } von main():

const oldest = findOldestBook(books);
console.log("Ältestes Buch:", oldest);

await delay(500);
console.log("fertig");

try {
  await delay("nicht-die-zahl" as any);
} catch (error) {
  console.error("Fehler bei delay:", error);
}

Das as any überredet TypeScript, den eigentlich falschen Typ durchzulassen — nur zu Testzwecken, in echtem Code vermeidest du as any normalerweise. Erwartete Konsolen-Ausgabe, in dieser Reihenfolge: das älteste Buch, 500ms Pause, "fertig", dann die geloggte Fehlermeldung aus dem catch. Kein roter Absturz, kein unbehandelter Fehler im Terminal.

Erfolgskriterium

Alles läuft ohne unbehandelte Fehler durch, inklusive deines absichtlich eingebauten Fehlerfalls. Du kannst in eigenen Worten erklären, was resolve in der delay-Funktion tut, und warum .forEach() für den delay-Loop die falsche Wahl gewesen wäre.
