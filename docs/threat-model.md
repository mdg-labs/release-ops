# Release Ops — Threat Model

**Status: DRAFT for v2.** Rewritten on 2026-11-14 for the v2 design: a self-hosted Renovate-based update bot, one GitHub App as bot, webhook sender and login provider, and a separate worker that runs Renovate. Written from `docs/specs.html` (the v2 contract: §2 engine, worker, internal listener and webhook; §3 setup, login and roles; §5 tickets; §7 API and metrics; §9 environment) and the maintainer-approved v2 plan. It needs maintainer review before anything relies on it. Statements marked "(proposed, confirm)" are inferences or residuals the plan accepts but the spec does not settle; each has an entry under the open questions or in §5.

This doc is the yardstick for every security judgement in the project: the `security-audit` skill, the task-verifier's security layer and `pr-review`'s security triage. A finding is measured against the assets (§1), attackers (§2), entry points (§3), invariants (§4), accepted residuals (§5) and severity rubric (§6), and recorded per §7.

**Reading the anchors.** An owner path or guard marked "(planned, #n)" does not exist in code yet; `#n` is the tracker item that creates it, and the property is the one the spec states. Anything else exists on `dev`. Some existing anchors are v1 code that the v2 items remove or replace (#194, #206, #207); they are listed only where v2 reuses the mechanism. When code moves, the anchor moves in the same change.

## 1. Assets

| Asset | Why it matters | Where it lives |
|---|---|---|
| **GitHub App private key (pem)** | Signs the App JWT that mints installation tokens. The App holds Contents, Pull requests, Issues, Workflows, Checks and merge-queue write, so the key is write access to every repository the one installation covers, and it works until rotated. The most valuable secret in the system. | `github_app.encrypted_private_key` (AES-256-GCM); decrypted only in the app's Go process. Never in the worker. |
| **App client secret** | Completes the OAuth code exchange; with it an attacker can run the sign-in exchange as the App. | `github_app.encrypted_client_secret` |
| **Webhook secret** | Authenticates every GitHub delivery. With it an attacker forges events that enqueue jobs, upsert update PRs and create tickets. | `github_app.encrypted_webhook_secret` |
| **Setup token and break-glass link token** | The setup token lets its holder create the App under their own account while no App is configured, i.e. take the instance. The link token is a 15-minute admin session. | `auth_tokens` rows of kind `setup`, `login_link_tokens` (SHA-256 only); the setup token also in the `SETUP_TOKEN` env or the first-start log line |
| **Installation tokens and user OAuth tokens** | Installation tokens (about 1 h, scoped to a job's repositories) give write access to those repositories; a user token reads what that user can. OAuth codes and the manifest `code` are one-use bearer values. | Memory only. The worker holds the token of the job it runs; the user token is discarded seconds after sign-in. Never stored. |
| **`APP_ENCRYPTION_KEY`** | The only thing between a leaked `app.db` and every stored secret above and below. | Container environment of the app only; never in the DB, image or worker |
| **`WORKER_SECRET`** | Authenticates the worker to the internal listener; with it a caller claims jobs and obtains the installation token of a job it holds. | Env of the app and the worker; unreadable by Renovate |
| **Ticket-system credentials** | Jira/Linear/Kaneo API keys; they often reach far beyond this app. | `integrations.encrypted_payload` (AES-256-GCM) |
| **User accounts, sessions and the stored repo-access list** | A session carries the role and its last evaluation; a viewer's session carries the list of repository ids they may see, which is authorization state. Identity is the numeric GitHub user id; there are no passwords. | `users`, `auth_identities`, `sessions`, `session_repositories`; cookie `release_ops_session` |
| **Repository and update data** | Update PRs, dependency lists, job logs and ticket links reveal private repository names and what they depend on. A viewer must see only their own repositories. | `repositories`, `update_prs`, `update_pr_dependencies`, `update_tickets`, `jobs`, `job_runs` |
| **The installed repositories** | Renovate writes branches and PRs there, and the token can change workflows. Their integrity is what the App key protects. | GitHub |
| **Global Renovate config and tools** | Decide what code runs in every job: `allowedCommands`, presets and the tools directory. Whoever can write them controls later jobs of every repository. | The configured global-config repository and ref, or a host mount into the worker |
| **Ticket integrity** | The app writes tickets into other teams' trackers; forged or spammed tickets mislead people. | Outbound calls in `internal/providers/ticket/`, driven by the ticket engine |
| **Availability: queue and rate budget** | One GitHub rate-limit budget is shared by every token of the installation; exhausting it stops updates, role checks and sign-in. | `jobs`, `installations.rate_limit_*` |
| **The SQLite database file** | Holds all of the above that is stored, plus config; also the target of migrations and snapshots. | `/data/app.db`, `/data/snapshots/` (Docker volume `/data`) |

v1 assets that no longer exist (notification URLs, password hashes, invitation, password-reset and email-change tokens, forge credentials) are not listed; v2 holds no password, no email address and no forge token of a user.

## 2. Attackers

Each attacker has a capability, what it is trusted with, and what it must never reach. A finding names the attacker it relies on. Numbers `2.1` to `2.8` keep their place; the new attackers start at `2.9`. None is retired.

### 2.1 Unauthenticated network client
- **Capability:** sends arbitrary HTTP to the Next.js listener (`0.0.0.0:3000`, the only published port), and through `/api/go/*` to the Go API and through `/hooks/github` to the webhook handler. Can start sign-in and setup flows, guess tokens subject to the rate limits.
- **Trusted with:** the login page, `/setup`, the public API paths (session, GitHub sign-in start and callback, break-glass redemption, setup status, manifest, callback and installed), `/healthz`, `/readyz`, and `/hooks/github` (which only an HMAC-valid caller can use, see 2.9).
- **Must never reach:** any other API route, a session without completing GitHub sign-in with a role, the App key or any secret, the setup flow once an App is stored, a request path to a worker route or `/metrics`.

### 2.2 Signed-in user — admin is the trust ceiling
- **Admin (trust ceiling).** Role derived from GitHub: organization owners, `ADMIN_TEAM` members, the bootstrap admin; on a personal-account installation, the owner. **Capability:** every route in the admin column of the role matrix: integrations and their test connections, ticket projects, repository enable/pause and ticket-project mapping, "run now", settings (concurrency cap), App and installation views, App private-key rotation, the raw global config view, all repositories' data and ticket error text.
- **Viewer.** Any other active org member, optionally limited to `VIEWER_TEAM`. **Capability:** read-only views of the dashboard, update PRs, jobs with bounded log excerpts and problems, limited to repositories they can access on GitHub. Calls nothing that writes. The viewer as a separate adversary is 2.11.
- **Trusted with (admin):** everything the API exposes, except the items below. Roles are never edited in the UI or API.
- **Must never reach (either role):** a stored secret's plaintext (the API returns `has…` flags only), the encryption key, the worker secret, an installation token, a stored credential sent to a host other than the one it was entered for. Nobody changes `allowedCommands` or the global config through the UI or API.
- **Not a finding:** anything an admin can do by design, e.g. pointing an integration at an internal host (§5.9), viewing the global config, running a repository's job.

### 2.3 Author of untrusted GitHub and Renovate content
- **Capability:** controls what GitHub and Renovate report about a repository: PR titles and bodies (including the release notes Renovate renders into the body), labels (anyone with triage rights can set them), branch names, dependency names and versions, Dependency Dashboard text, issue and PR comments. Also controls, through repository content, what the Renovate report and log excerpt a worker posts contain, and their size. Includes an upstream package author whose release notes reach a PR body.
- **Trusted with:** being treated as data.
- **Must never reach:** template execution, the web UI's DOM as markup, a credential for another host, a ticket-system call other than the create, update, status and comment calls the engine makes, an unbounded resource (memory, DB rows, log size), the app's logs as a forged line.

### 2.4 Malicious ticket system
- **Capability:** controls Jira/Linear/Kaneo responses: ticket ids, statuses, metadata lists, errors, redirects, response size. A self-hosted ticket system whose operator is hostile is the same attacker.
- **Trusted with:** being treated as data.
- **Must never reach:** the same as 2.3; in particular its ids and URLs are not trusted as links or paths without building them server-side, and a redirect never carries a credential to another host.

### 2.5 Holder of the SQLite file or a backup of `/data`
- **Capability:** reads `app.db` or a snapshot offline (stolen volume, backup, misconfigured share). Does not have the container environment.
- **Must never reach:** the App private key, client secret, webhook secret or an integration credential in plaintext, or a reusable setup or link token (they are stored as SHA-256 of random values). Note: rows in `sessions` are live session tokens until expiry (at most 8 hours) and `session_repositories` lists a viewer's repositories; the raw global config text is stored in plaintext (§5.14); whether those are accepted is open question 12 (proposed, confirm).

### 2.6 Network observer between browser, GitHub and container
- **Capability:** sees traffic when the operator exposes port 3000 or `WEBHOOK_URL` without TLS: session cookies, the setup token as typed, the OAuth callback's `code` and `state`, webhook payloads. Does not see the app-to-GitHub or app-to-ticket-system calls while they use HTTPS: `github.com`, `api.github.com` and `linear.app` always do. A Jira or Kaneo base URL and `GITHUB_BASE_URL` (GitHub Enterprise Server) are chosen by the admin or operator, and an `http` value exposes the credentials sent there (Basic or Bearer, the App JWT, installation tokens) to this attacker (§5.18).
- **Must never reach:** session cookies, the setup token, or an OAuth code when the operator configured HTTPS (`APP_URL=https://…`). A webhook body read in transit is not a forged one: the HMAC still authenticates.

### 2.7 Co-tenant in the container's network namespace or on the Docker host
- **Capability:** a sidecar sharing the app container's network namespace can reach the Go API on `127.0.0.1:8080` directly and is treated as the trusted loopback proxy for `X-Forwarded-For`; it can also reach the loopback `/metrics` listeners. A container on the Compose network can reach the internal listener and a `/metrics` listener bound to the Compose network. A host user in the `docker` group is root-equivalent and out of scope.
- **Must never reach:** a protected route without a session, a worker route without `WORKER_SECRET`, a job's installation token, or any secret through an operational endpoint.

### 2.8 Compromised dependency, base image or CI step
- **Capability:** a Go module, npm package, base image (the app's Node and Go images, the pinned Renovate image the worker is built from), a tool the worker downloads at run time (`binarySource=install`) or a GitHub Action (`.github/workflows/*.yml`) runs attacker code at build or run time. Code in the worker's Renovate process is the 2.10 capability plus the pinned build's own reach.
- **Must never reach:** a published GHCR image the project did not build, a runtime secret, the App key. The images carry no secrets (T13).

### 2.9 GitHub webhook sender
- **Capability:** anyone who can send an HTTP POST to `/hooks/github` (reachable from the internet whenever `WEBHOOK_URL` is set): arbitrary bodies and headers, replays of a captured genuine delivery, floods, oversized bodies. Without the webhook secret it cannot produce a valid signature. A genuine delivery caused by a repository user (a ticked Dependency Dashboard checkbox, a label) is also in scope as input: it is real GitHub traffic about content anyone with repository access controls.
- **Trusted with:** nothing before the HMAC check. A genuine, signed event is trusted as a trigger and as data (T23).
- **Must never reach:** any parsing, storage, enqueue or GitHub call before the signature verifies; a state change (job, update PR, repository set, installation) from an unsigned request; unbounded memory; an installation other than the one recorded.

### 2.10 Untrusted repository content executed by Renovate in the worker
- **Capability:** a person who can put content on the default branch of an installed repository (a contributor, or an owner of a repository in an organization where the owner is not trusted with the whole installation), or an upstream package author whose version a PR updates. Controls manifests, lock files, the repository's Renovate config, package-manager config, `postUpgradeTasks` entries, wrapper scripts, and whatever code the package managers evaluate while resolving. Renovate runs this as a second Unix user in the worker with the job's installation token in its environment, outbound network access, and its slot's cache directory. `allowScripts=false` stops install scripts but does not make every resolver inert (§5.3, proposed, confirm).
- **Trusted with:** its own repository only: it can already write there.
- **Must never reach:** `APP_ENCRYPTION_KEY`, the App private key, `WORKER_SECRET`, `SESSION_SECRET`, the database, the internal listener's routes with worker authority, another job's token, a token wider than the job's scope, the worker process (signals, `/proc`), or a command outside the admin's `allowedCommands`.
- **Not a finding:** running package-manager code on its own repository with that job's token (§5.3).

### 2.11 Viewer who must not see other repositories
- **Capability:** a valid viewer session: a role of viewer and a stored list of the repository ids the user could access on GitHub at sign-in (fixed for the session, at most 8 hours). Sends any request an admin could, with any ids, filters and pagination.
- **Trusted with:** their own repositories' dashboard, update PRs, jobs, log excerpts, and whether a ticket operation is failing (no error text). Instance-wide queue counts and the build info (§5.8).
- **Must never reach:** any data of a repository outside the list in any list, count, detail, problem, job or metric response; whether such a repository exists (a single resource outside the list answers 404); any admin endpoint or admin-only field; a role change.

## 4. Security invariants

Findings and verifier verdicts cite these by number (`violates T20`). An invariant the code does not fully hold yet is still an invariant; the gap is listed in the open questions. **T6 and T8 are retired** (their v1 code is gone) and are never reused. T1–T5, T7, T9–T17 keep their number with the v2 meaning below; T17 is replaced. T18 and up are new.

| # | Invariant | Anchor and current guard |
|---|---|---|
| **T1** | Every stored secret is encrypted at rest with AES-256-GCM under `APP_ENCRYPTION_KEY`, random 12-byte nonce per write: integration credentials and the App's private key, client secret and webhook secret. Installation tokens, user OAuth tokens, OAuth codes and the manifest `code` are never stored at all. | `internal/crypto/aesgcm.go` (`Encrypt`/`Decrypt`); `internal/store/integrations.go`; `github_app` encrypted columns with `key_id` (`db/schema.sql`, `internal/store/github_app.go` `Create`) |
| **T2** | No API response carries a secret's plaintext: integrations return `hasSecret`, the App returns `hasPrivateKey`, `hasClientSecret`, `hasWebhookSecret`; no token, key or code ever appears in a response, an error message or a ticket error text; key rotation never echoes the submitted key. | `internal/api/handlers/integrations.go` (list item `HasSecret`); `GET /api/v1/github-app` (`internal/api/handlers/github_app.go` `Get`, registered in `internal/api/routes.go`; it reads presence flags only, never the secrets); rotation `internal/api/handlers/github_app.go` (`RotatePrivateKey`, `PUT /api/v1/github-app/private-key`; the same message for every rejected key, no key in a response or log line) |
| **T3** | No secret is logged, on success or failure paths, in the app or the worker: the pem, client secret, webhook secret, `WORKER_SECRET`, session tokens, installation and user tokens, OAuth codes and `state`, the manifest `code`, the setup token, break-glass link tokens, `Authorization` and `X-Hub-Signature-256` values, and any error message wrapping them. The request log carries method, path, status, bytes and duration only. One redacting log handler covers both processes, and every value the worker posts or stores is redacted for the job's token first. The one deliberate exception is the setup token printed once at start while no App is configured (§5.12). **Release blocker.** | `internal/api/router.go` (`requestLogger`, `recoverer`); `internal/logging/` (`Handler`, `Registry`, `PrintOnce` for the setup token), with secrets registered where they are loaded or minted; `internal/renovate/redact/` for the secret shapes and the worker excerpt (#208) |
| **T4** | Every `/api/v1/*` route outside the public auth and setup paths requires a session, enforced in Go. The public Go API binds to `127.0.0.1` only behind Next, so the proxy is not a security boundary; `/hooks/github` is the one non-session route and is authenticated by T18. A separate internal listener (`INTERNAL_ADDR`) mounts the worker routes only (anything else answers 404), requires `WORKER_SECRET` compared in constant time (401 before anything else is evaluated), is never published to the host or proxied by Next, and its routes are not mounted on the public API. The worker holds no DB access, no `/data` volume (only its per-slot cache volumes), no Docker socket, no encryption key and no App private key; Renovate runs as a separate Unix user that cannot read the worker secret (not its environment, files or mounts). `/metrics` is served only on its own listener and never through the proxy. | `internal/api/routes.go` (`RegisterAll` protected group), `internal/api/middleware/auth.go` (`RequireSession`, `Authenticate`), `internal/api/auth/public_paths.go` (`PublicAuthPaths`), `internal/api/router.go` (`Serve` refuses a non-`127.0.0.1` address); internal listener (`internal/queue/internalapi/handler.go` `NewHandler`, `authenticate`; `internal/queue/internalapi/serve.go`), worker image users (`Dockerfile` target `worker`) and the CI smoke test (`docker/worker-smoke.sh`, job `worker-image` in `.github/workflows/ci.yml`) |
| **T5** | The session token is renewed on every successful sign-in (GitHub callback and break-glass redemption) and any pre-login token is discarded; the cookie is `HttpOnly`, `SameSite=Lax`, and `Secure` when `APP_URL` is HTTPS. A session exists only for a user with a role. | `internal/api/auth/session_user.go` (`StartUserSession` → `RenewToken`), `internal/api/auth/session.go` (`NewSessionManager`), `internal/config/config.go` (`SecureCookies`); `internal/api/auth/session_github.go` (`StartGitHubSession`: `Clear`, `RenewToken`), used by the callback (`github_signin.go`) and link redemption (`loginlink.go`) |

### Release blockers

Two properties block the v2.0.0 release because the App private key sits in an internet-facing container: **App private-key rotation (T25)** and **log redaction of secrets, tokens, OAuth codes and the manifest code (T3)**. Neither is rated; they must exist. A release candidate without either is not shippable.

## 5. Accepted residuals

Not findings. Every v2 residual below is "(proposed, confirm)": the plan or the spec accepts it, and the maintainer confirms it by merging this document.

1. **Exactly one installation per instance, on a private App** bounds the blast radius to one account: the App key is write access to every repository that account installed the App on, nothing beyond (proposed, confirm; spec §3.4).
2. **`allowedCommands` is an admin allowlist** in the global config file. A listed command runs, with the job's token in the environment, code that can live in the tools mount. An empty list (the default) runs none (proposed, confirm; spec §2.4, §2.5).
3. **A repository owner runs package-manager code inside the worker** with only the job's token. `allowScripts=false` does not make every resolver inert, so content of an installed repository can execute code as the Renovate user, read the job token, reach any host the worker can reach (§5.5), and write to its own repository. The token is short-lived and scoped to the target repository plus the repositories of §5.4. Rated Medium where it ends at the target repository (open question 6) (proposed, confirm).
4. **The job token also covers the preset and global-config repositories** with the App's Contents read/write (accepted by the maintainer, spec §2.2). Code running in a job can therefore write to the repositories that later jobs fetch their global config and tools from. That path crosses repositories: it can set `allowedCommands` and plant tools run in every later job with that job's token. It is accepted only while those repositories are protected by the operator (a ruleset requiring review that the App cannot bypass, and `GLOBAL_CONFIG_REF` on a protected branch or a commit). It is rated separately from §5.3 (§6: High if the protection is absent) (proposed, confirm; open question 1).
5. **Worker egress is not restricted by Release Ops.** It needs GitHub, package registries, tool-download hosts and the app's internal listener; an operator may apply an allowlist. This is a residual, not an invariant (proposed, confirm).
6. **The worker's per-slot caches are shared by successive jobs of different repositories.** Content of one repository could poison a package or datasource cache that a later job of another reads. Accepted for a self-hosted instance with one trust domain; a hosted offering needs per-tenant isolation (proposed, confirm).
7. **Anyone with write access to a repository can start runs** by ticking a Renovate checkbox, and genuine events from such users are processed. Coalescing, the one-job-per-repository rule and the concurrency cap bound the cost, but they can spend the shared rate-limit budget (proposed, confirm).
8. **Viewers see instance-wide queue counts and build info.** `GET /api/v1/status` returns queue depth and worker contact without repository data, to viewers as to admins (proposed, confirm; spec §7.1).
9. **An admin can make the server call any URL** they configure as an integration base URL or test, including private and loopback addresses. The reach equals the admin's trust (proposed, confirm).
10. **PR labels steer the ticket filter.** The ticket project's label filter (any of) means anyone with triage rights on a repository can suppress or force a ticket for a bot PR by labelling it (proposed, confirm; spec §5.2).
11. **PR-body release notes go into tickets unchanged,** markdown and HTML included, truncated to 4,000 characters. Rendering them safely is the ticket system's job; a hostile release note can put links into a ticket (proposed, confirm).
12. **The setup token is weakly protected in setup mode.** When `SETUP_TOKEN` is not set the generated token is printed to the log at every start that finds no App configured (the deliberate exception to T3), so anyone who reads those logs can complete setup; and the setup token and break-glass link sit behind the per-IP limiter, which keys on an address the client cannot set (T11), so its protection rests on token entropy (proposed, confirm).
13. **The bootstrap login is claimed at first sign-in.** Until the first sign-in whose GitHub login equals `BOOTSTRAP_ADMIN_GITHUB_LOGIN`, whoever holds that login on GitHub becomes the bootstrap admin, including one who re-registered a released name (proposed, confirm).
14. **The global config is plaintext** in `installation_settings.global_config_content` and visible to admins; it must not contain secrets, which is the operator's duty (proposed, confirm; spec §2.4).
15. **Authority lags by design:** a removed org member keeps a session for up to 15 minutes, and a viewer's repository list is fixed for up to 8 hours (proposed, confirm; spec §3.8, §3.9).
16. **`/metrics` has no authentication.** Protection is the bind address (loopback by default) and not publishing the port; an operator who binds it wider exposes repository names and counts (proposed, confirm; spec §7.8).
17. **The rate limiter is in memory and per container**, so it resets on restart (proposed, confirm).
18. **TLS is the operator's job.** The container serves plain HTTP; cookies are `Secure` only when `APP_URL` is HTTPS; `WEBHOOK_URL` may be plain HTTP (the HMAC still authenticates); a Jira or Kaneo base URL and `GITHUB_BASE_URL` may be `http`, in which case the credentials sent to that host travel in the clear; the internal listener speaks plain HTTP on the private Compose network, which only the app and the worker may share (proposed, confirm; open question 8).
19. **Holder of `app.db` plus the container env has everything.** `APP_ENCRYPTION_KEY` protects the DB only when stored apart from it, and snapshots under `/data/snapshots` are as sensitive as `app.db` (proposed, confirm).

## 6. Severity rubric

The rating is the lowest level whose definition the finding meets after the anti-inflation rules.

| Level | Definition |
|---|---|
| **Critical** | An unauthenticated network client (2.1) gets a session, an account, or the plaintext of the App private key, client secret, webhook secret or a stored credential, or makes the server act as a signed-in user; or takes the instance through setup after an App is configured or without the setup token; or repository content (2.10) or any signed-in non-admin (viewer, 2.11) obtains the App private key. Against the production images with default config. |
| **High** | A viewer (2.11) performs an admin action or reads admin-only data; an admin (2.2) obtains a stored secret's plaintext; a hostile ticket system (2.4) obtains a credential or has one sent to a host it was not entered for; a DB-file holder (2.5) recovers a secret without the key; a webhook sender (2.9) without the secret gets any event processed; repository content (2.10) obtains `APP_ENCRYPTION_KEY`, `WORKER_SECRET` or another repository's token, a token wider than its job's scope, or a way to change `allowedCommands` outside the global config; a hostile PR or release note (2.3) executes code, template logic or script in a user's browser; any break of T4, T7, T10, T17–T22 or T24. |
| **Medium** | A finding that meets no Critical or High definition and is a bounded loss that needs a precondition the default setup does not give, or stops short of credentials: a viewer reading another repository's update PR, job or problem data (no code, no secrets), a rate-limit bypass, repository content that exfiltrates the job token where its reach ends at the target repository, a foreign PR or issue starting a run, unbounded resource use by a hostile report, PR body or log excerpt, a session weakness needing an adjacent position (2.6, 2.7), an invariant violation with no working path to a High outcome. |
| **Low** | Needs an already privileged or compromised position, or a defence-in-depth gap with no attack path today. |
| **Info** | No exploitable path: missing hardening, doc drift, a non-default configuration the docs already warn about. |

**Anti-inflation rules.** A finding is rated only after all of these hold:

1. **A §3 entry point**, named with its owner path, that is reachable in the production images (`Dockerfile`, `docker/entrypoint.sh`, the worker image and Compose reference) with default config.
2. **A named §2 attacker**, using only that attacker's capability. Needs-a-signed-in-user is never Critical, with one exception: a path that hands the App private key to a non-admin is Critical (§1: the key is write access to every installed repository). Otherwise it is High only when it crosses a "must never reach" line of 2.2 or 2.11 as the rubric states. A path that needs control of a repository (2.10) and ends only at that repository's own token is Medium at most.
3. **A path that starts from a leaked or guessed secret rates the leak, not its use.** An attacker without the webhook secret, `WORKER_SECRET` or the App key cannot be assumed to hold it.
4. **Dev-only paths do not count** at face value: test helpers (`*_test.go`, `NewRateLimiterForTest`), mocks, fixtures, local dev servers. Rate them by the precondition.
5. **§5 and "any admin can do it by design" are not findings.** A report that finds a new route to a §5.4 outcome (not the accepted scope itself) is rated by §6 as above.
6. **Theory is checked.** The report gives the exact sequence from entry point to outcome; a verifier re-derives it before it is rated above Low.

### Worked examples

- **Critical (constructed).** A new handler for the App's settings is registered outside the `RequireSession` group and returns the stored private key decrypted. Any unauthenticated client (2.1) reads a key that writes to every installed repository. Violates T2 and T4.
- **High (constructed).** The webhook handler parses the JSON body, or verifies the signature over a re-encoded body, before it checks `X-Hub-Signature-256`. A webhook sender (2.9) without the secret makes the app upsert update PRs and create tickets in the ticket system. Violates T18. Not Critical: no session, credential or secret is reached.
- **High (constructed).** The worker is started with the app's environment file, so Renovate's process inherits `APP_ENCRYPTION_KEY`. Repository content (2.10) reads it from its own environment. Violates T22 and T4. With any copy of `app.db` the key unlocks the App private key (Critical by path).
- **High (constructed).** The token endpoint builds the repository list from the `repository` field in the worker's request instead of the claimed job's. Repository content (2.10) obtains a token for another installed repository. Violates T22.
- **High (constructed, separate rating from §5.3).** Content in repository X uses its job token to write to the global-config repository, which has no ruleset, and adds a command to `allowedCommands` and a tool; the next job of every repository then runs it with that job's token. It crosses repositories, so it is rated High. It is not a finding while §5.4 holds (the repository is protected and the token scope is as specified); a finding is a token scope wider than §5.4 states, or a global-config fetch that skips the pinned ref.
- **Critical (constructed).** `GET /api/v1/github-app` returns the stored private key decrypted to any session, or key rotation echoes the old key in its response to a viewer. A viewer (2.11) reads a key that writes to every installed repository. Rated Critical although it needs a session, because of what the key is. Violates T2 and T25.
- **High (constructed).** `GET /api/v1/jobs/{id}` returns the ticket error text of any job to a viewer. Admin-only data reaches a viewer (2.11). Violates T20.
- **Medium (constructed).** `GET /api/v1/update-prs/{id}` forgets the repository-scope filter: a viewer (2.11) reads the title and dependency list of an update PR in a repository outside their list. Metadata only, no code or secrets. Violates T20.
- **Medium (maintainer default).** Repository content (2.10) exfiltrates the job token through the worker's open egress. The token reaches the target repository, which the attacker already writes, for about an hour. Rated Medium for that reach; its reach to the preset and global-config repositories is the separate High rating above.
- **Medium (constructed).** A change lets a client's own `X-Forwarded-For` reach Go (the preload is not loaded, or the proxy or Go takes a client-supplied hop), and the client rotates buckets to try setup or break-glass tokens past the 10 per minute limit (T11, 2.1). Bounded by token entropy.
- **Medium (constructed).** A body with the Dependency Dashboard's marker, authored by a person, is accepted as the dashboard because only the marker is checked; ticking its box starts a run (T23, 2.3). No credential or repository write.
- **Low (constructed).** `/data` is created group-readable, so another account on the Docker host (2.7) reads `app.db`. Needs a position on the host already; the secrets in it stay encrypted under `APP_ENCRYPTION_KEY` (T1).
- **Not a finding.** An admin points an integration at `http://127.0.0.1:8080`, or opens the raw global config (§5.9, §2.2); a repository owner's content runs its own package manager with its own token on its own repository (§5.3); someone with triage rights labels a bot PR (§5.10); a viewer reads the queue counts (§5.8).
- **Info (constructed).** The spec says a second App installation is answered with success and ignored; the code answers 409. Stricter code, doc drift only.

## 7. Disclosure split

Routing follows `.claude/rules/mdg-security.md` and `.claude/scripts/security-route.sh`, which reads the repository's visibility live; a failed `security-route.sh` is a stop, never a guess.

- **Repository public (route `advisories`).**
  - **Critical and High** → a draft private security advisory on `mdg-labs/release-ops` (`.claude/scripts/gh-helpers.sh advisory-create … --dry-run` first). Never a public issue, never a commit message or PR text that describes the flaw.
  - **Medium, Low and Info** → a public GitHub issue in `mdg-labs/release-ops` labelled `security`, titled `Security: <short description>`, created through `/triage`.
- **Repository private (route `issues`, `security.privateRepoIssues`).** A private repository's issues are not public and GitHub offers it no advisories, so every finding, whatever its rating, is an ordinary issue labelled `security`. No advisory is proposed. The route is never `issues` on a public repository.
- A public finding that shares a root cause with a withheld one is withheld too.
- **Fixing an advisory:** run `/orchestrate --advisory GHSA-…`. The commit uses a neutral subject (no vulnerability wording) and its body ends with `Refs: GHSA-…`; it carries no reproduction, payload or severity. The maintainer publishes the advisory once the fix reaches `main`.
- **Outside reports** arrive through GitHub private vulnerability reporting for the repository (`https://github.com/mdg-labs/release-ops/security/advisories/new`), and are triaged with `/security-audit triage`. [`SECURITY.md`](../SECURITY.md) tells reporters to use that channel, not to open public issues, and that only the latest release receives fixes until v2.0.0 ships.

## Open questions for the maintainer

Decided by the maintainer on 2026-11-14 and applied above: attacker numbers `2.1`–`2.8` stay stable and new attackers start at `2.9` (none retired); worker egress is a residual, not an invariant (§5.5); repository content exfiltrating the job token is Medium for the target repository, rated in §6, with the global-config reach rated separately. v1-only questions (login timing, password-change drift, invitation and mail items) are closed with their code. Each open item has a recommended default.

1. **Job token reach into the global-config and preset repositories (§5.4).** The token has Contents write on repositories that later jobs trust. *Default:* accept; require operators to protect those repositories (ruleset requiring review, App not on the bypass list, `GLOBAL_CONFIG_REF` on a protected branch or a commit) and say so in the customer docs; consider a read-only token for the global-config fetch once Renovate's needs are known.
2. **`/api/v1/setup/installed` is public and not in the rate-limit table.** It triggers a GitHub call with the App JWT per request. *Default:* add it to the limited endpoints (10 per minute per IP) and answer the same for an installation id that is not the App's.
3. **Resolved: `X-Forwarded-For` source.** The Next process preloads a hook that sets the header from the socket address, or from the right-most hop outside `TRUSTED_PROXIES` when the peer is in it, and Go takes the last hop; see T11 and spec §7.0.
4. **Resolved: strength of an operator-supplied `SETUP_TOKEN`.** A value shorter than 64 characters, the length of a generated token (32 random bytes as hex), is refused at startup (T14; `config.validate`, spec §3.2).
5. **Resolved: webhook flood limit.** `/hooks/github` counts failed signatures per client IP (the address T11 describes) and answers the 11th failure within one minute from an IP with 429 and `Retry-After`; 10 per minute matches the other public limits. Valid deliveries are never counted. The signature is still computed for every request, because refusing an over-limit IP before the check would also refuse GitHub's valid deliveries whenever they share an address with an attacker (a reverse proxy that is not in `TRUSTED_PROXIES`); the cost per request stays bounded by the 1 MiB body cap (T18). See T11.
6. **How much code survives `allowScripts=false`.** Some managers evaluate project files while resolving. *Default:* treat all repository content as code in the model, list the affected managers in the customer docs and keep the smoke test of #195 asserting that the Renovate user cannot read the worker's environment or files and that repository config cannot extend `allowedCommands`.
7. **`WORKER_SECRET` strength and presence.** *Default:* the app and the worker refuse to start without a 32-byte-or-longer value (T14).
8. **Plain HTTP on the internal listener.** The secret and installation tokens cross the Compose network unencrypted. *Default:* accept for a private Compose network shared only by the app and the worker; document it; mutual TLS belongs to a hosted design.
9. **The setup token line versus log redaction.** The deliberate T3 exception must survive the redaction layer of #227 while every other secret is redacted. *Default:* the setup token is registered with the handler like every other secret, an operator-supplied `SETUP_TOKEN` at config load (`config.Load`) and a generated one when `setup.EnsureToken` mints it; the one startup call that prints it (`logging.PrintOnce`) names the value in its own context, and the handler leaves that value alone in that one record only. Every other line, including a later one that repeats the token, has it removed, and the tests assert both.
10. **CSRF.** Protection rests on `SameSite=Lax`; Go does not check `Origin`. Key rotation and "run now" are state-changing admin actions. *Default:* reject state-changing requests whose `Origin` does not match `APP_URL`.
11. **Redirects and base URLs for ticket systems.** No client sets `CheckRedirect`; `validateBaseURL` checks presence only. *Default:* refuse cross-host redirects for credentialed clients and require `http` or `https` with a host.
12. **Session rows in a DB copy (2.5).** Live session tokens sit in `sessions`. *Default:* accept, given the 8-hour cap; consider storing session tokens hashed.
13. **Resolved: `SECURITY.md`.** Outside reports go through GitHub private vulnerability reporting; see §7 and [`SECURITY.md`](../SECURITY.md).
14. **Actions pinned by tag.** *Default:* pin third-party actions by commit SHA; the Renovate base image of the worker by digest.
15. **Bounds on untrusted sizes.** The webhook body is capped at 1 MiB; the worker's result, report, log excerpts and GitHub or ticket responses have no stated caps. *Default:* cap each with `io.LimitReader` or a request-size limit and record the numbers with the first deployment.
16. **`SESSION_SECRET`.** The spec names it the signing key, while the session manager stores random tokens server-side and ignores it. *Default:* keep the startup check and document it as reserved, or drop it from the spec.
17. **Maintainer action in `CLAUDE.md` `### Security units`.** T6 and T8 are retired and T17 has a new meaning; the unit rows and the `sweep-*` patterns follow the v2 code layout when it lands (#228). *Default:* update those rows in the item that moves the code.
18. **Resolved: a missing `APP_URL` at startup (T14).** `APP_URL` is required and the server refuses to start without it (`config.LoadServer`), since it fixes the OAuth `redirect_uri`, the `Secure` cookie flag and the CSRF `Origin` check (question 10).
