Projekt-Spezifikation

Was release-monitor am Ende tut — als Referenz, auf die die Module verweisen. Du musst das jetzt nicht alles verstehen, das kommt Stück für Stück.

Zweck

Ein Docker-Container, der in festen Abständen eine Liste von GitHub-Repos abfragt, das jeweils neueste stable Release prüft und bei einem echten neuen Release (nicht beim allerersten Sehen des Repos) ein Ticket in Phasical erstellt.

Config (repos.yml)

Der Nutzer pflegt eine YAML-Datei, die im Container gemountet wird:

repos:
  - source: github
    owner: FreshRSS
    repo: FreshRSS
  - source: github
    owner: usekaneo
    repo: kaneo

ticketing:
  provider: phasical
  projectId: "abc123"

source ist heute immer github, aber das Feld existiert von Anfang an — Phase 09 erklärt warum.

Die zwei Kern-Interfaces

SourceProvider

interface SourceProvider {
  getLatestRelease(owner: string, repo: string): Promise<Release | null>;
}

interface Release {
  tag: string;
  name: string;
  url: string;
  publishedAt: string;
}

null bedeutet: kein stable Release vorhanden (z.B. GitHub-404).

TicketProvider

interface TicketProvider {
  createTicket(input: TicketInput): Promise<string>; // gibt Ticket-ID zurück
}

interface TicketInput {
  title: string;
  description: string;
}

Datenbank-Tabelle known_releases

updatedAttextbei jedem Upsert aktualisiert

Entscheidungslogik

  1. Kein Eintrag für owner+repo vorhanden → baseline (nur speichern, kein Ticket)
  2. Eintrag vorhanden, Tag identisch → skip (nichts tun)
  3. Eintrag vorhanden, Tag unterschiedlich → create (Ticket + Tag aktualisieren)
