Produktspezifikation · MVP

Release Ops

Self-hosted Service: überwacht Releases auf GitHub, GitLab, Gitea, Forgejo und Codeberg für konfigurierte Repos und erstellt bei echten neuen Releases (nicht beim ersten Baseline-Sehen) Tickets in Phasical, Jira oder Linear. Ticket-Integrationen unterstützen mehrere Projekt-/Team-Ziele mit eigenem Status-Mapping; offene Tickets werden per Policy superseded, gemerged oder übersprungen. Notifications via Shoutrrr. Konfiguration, Integration-Credentials und Monitoring laufen über eine geschützte Web-UI (COSS). Worker und REST-API laufen in Go; Auth und UI in Next.js mit BetterAuth.

Version: Spec v2.4 (2026-08-06) — CI/CD: branch entrypoints + reusable workflows (slugbase/pipewatch-Pattern), GHCR, VERSION-Releases.

1. Zweck & Nicht-Ziele

Zweck

  • Pollt in konfigurierbaren Intervallen das jeweils neueste stable Release pro konfiguriertem Projekt.
  • Sources (MVP): GitHub, GitLab, Gitea, Forgejo, Codeberg — jeweils releases/latest (GitLab: permalink/latest; Gitea-Familie: Gitea-API v1).
  • Speichert den zuletzt gesehenen Tag pro Projekt in SQLite.
  • Erstellt bei Tag-Wechsel (nach Baseline) ein Ticket im gewählten System.
  • Tickets (MVP): Phasical, Jira, Linear — pro Repo frei kombinierbar mit Source.
  • Jede Ticket-Integration kann mehrere Projekt-/Team-Ziele haben (ticket_projects) — jedes mit eigenem open/done/cancelled/superseded-Mapping.
  • Idempotenz bei offenen Tickets: Default supersede; alternativ merge oder skip_if_open.
  • Notifications an Shoutrrr-Targets (Slack, ntfy, …) bei create, error, supersede.
  • Zeigt Betriebsstatus in der UI: letzter Poll, Fehler, Projekt-Übersicht.

MVP-Nicht-Ziele

  • Keine weiteren Sources (Bitbucket, Azure DevOps, …).
  • Kein Multi-User-RBAC (ein Admin reicht; alle eingeloggten User sind gleichberechtigt).
  • Kein öffentliches Sign-up (Admin-Account per Seed/CLI oder einmalig in UI).
  • Kein High-Availability / Horizontal Scaling.

3. Authentifizierung

BetterAuth (Next.js)

  • Plugin: better-auth mit SQLite-Adapter auf auth.db.
  • MVP-Provider: Email + Password only.
  • Plugin: jwt() — JWKS unter /api/auth/jwks (oder BetterAuth-Default).
  • disableSignUp: true nach Erst-Admin — oder Sign-up nur bis erster User existiert.

Go API Auth

  • Next.js Route apps/web/app/api/go/[...path]/route.ts holt Session-JWT via auth.api.getToken() und forwarded an Go mit Authorization: Bearer.
  • Go Middleware validiert JWT gegen BetterAuth JWKS (Cache Keys, Standard-JWT-Verify).
  • Alle /api/v1/* Endpoints erfordern gültiges JWT — außer optional GET /healthz für Container-Probes.

Kein Session-Cookie direkt an Go — nur JWT-Proxy-Pattern (vermeidet CORS/Cookie-SameSite-Probleme).

4.7 Zeitstempel

Alle TEXT-Timestamps: RFC3339/ISO8601 UTC mit Millisekunden, z.B. 2026-08-06T12:00:00.000Z.

4.8 Credential-Verschlüsselung

  • Algorithmus: AES-256-GCM.
  • Key: APP_ENCRYPTION_KEY — 32 Bytes, hex-encoded (64 Zeichen).
  • Stored format: base64(nonce + ciphertext + tag) oder JSON { "v": 1, "data": "..." }.
  • Go entschlüsselt nur im Worker/API — niemals an Frontend senden außer „configured“ / Maskierung.
  • API gibt bei Integrations has_secret: true, nie den Secret-Wert.

5. Domänenlogik & Idempotenz

5.1 Release-Entscheidung (Tag-Wechsel)

  1. baseline — last_known_tag ist NULL → Tag speichern, kein Ticket.
  2. skip — Tag identisch mit last_known_tag → nichts tun.
  3. neuer Tag — weiter §5.2 (offenes Ticket? Policy?) → dann create, supersede, merge oder skip_open.
  4. error — API-Fehler (außer „kein Release“) → last_error, Run fortsetzen.

„Kein Release“: GitHub/GitLab/Gitea/Forgejo/Codeberg 404 auf latest-release — kein Error.

5.2 Offenes Ticket & Idempotenz

Bei neuem Tag prüft der Worker live den Status des verlinkten Tickets (open_ticket_external_id), nicht nur die lokale DB — das Ticket kann manuell geschlossen sein.

Status-Zuordnung immer über ticket_projects.status_mapping des verlinkten Ticket-Projekts.

Live-StatusVerhalten bei neuem Tag
in done oder cancelledopen_ticket_* leeren → normales create
in openPolicy aus ticket_projects.on_open_ticket_policy (§5.2.1)
unbekannt / API-Fehlererror für Repo; kein neues Ticket

5.2.1 on_open_ticket_policy

PolicyAktionPoll-Event
supersede (Default)Altes Ticket → superseded-Status + Kommentar; neues Ticket anlegensupersede + create
mergeBestehendes Ticket aktualisieren (Titel/Beschreibung/Tag); kein zweites Ticketmerge
skip_if_openKein Ticket; optional Notificationskip_open

Supersede-Kommentar (alle Provider): Link zum neuen Release, alter Tag → neuer Tag.

Nach erfolgreichem create / supersede: open_ticket_external_id und open_ticket_tag aktualisieren. Nach merge: nur open_ticket_tag.

5.5 Notifications (Shoutrrr)

  • Library: github.com/containrrr/shoutrrr im Go-Worker — keine eigenen Slack/Discord/Telegram-Integrationen.
  • UI: Shoutrrr-URL pro Target (z.B. slack://…, ntfy://…, generic://…), verschlüsselt in DB.
  • Events: create, error, supersede (konfigurierbar pro Target).
  • Nach Ticket-Aktionen und bei Poll-Fehlern: an alle zutreffenden Targets senden (global enabled, optional Repo-Filter).

5.6 Poll-Run Ablauf

  1. Insert poll_runs status running.
  2. Für jedes enabled Repo: Source abfragen → Entscheidung → Event loggen.
  3. Run status: success (keine Errors), partial (einige Errors), failed (alle fehlgeschlagen oder kritischer Fehler).
  4. Kein paralleles Polling desselben Runs (Mutex / running-Guard).

5.7 Scheduler

Intervall aus app_settings.poll_interval_minutes. Zusätzlich: manueller Trigger via API/UI.

6.1 Source: GitHub

  • GET https://api.github.com/repos/{projectPath}/releases/latest
  • Headers: Accept: application/vnd.github+json, X-GitHub-Api-Version: 2022-11-28, User-Agent: release-ops
  • Authorization: Bearer wenn Token in Integration
  • Mapping: tag_name→Tag, html_url→URL, published_at→PublishedAt

6.2 Source: GitLab

  • GET {base_url}/api/v4/projects/{urlencoded_path}/releases/permalink/latest
  • projectPath → URL-encode (/ → %2F)
  • Header: PRIVATE-TOKEN: {token}
  • Mapping: tag_name→Tag, _links.self oder assets.links→URL, released_at→PublishedAt
  • 404 = kein Release

6.3 Source: Gitea / Forgejo / Codeberg (Gitea-API)

Gitea, Forgejo und Codeberg teilen dieselbe REST-API (/api/v1). Go-Implementierung: ein GiteaCompatibleSource-Client; kind steuert Default-base_url und UI-Label.

kindDefault base_urlsource_integration_id
giteaaus Integration (Instance-Root)Pflicht
forgejoaus Integration (Instance-Root)Pflicht
codeberghttps://codeberg.org (fest)optional (Token empfohlen)
  • GET {base_url}/api/v1/repos/{owner}/{repo}/releases/latest
  • projectPath = owner/repo (wie GitHub)
  • Header bei Token: Authorization: token {token} (Gitea-Standard)
  • Mapping: tag_name→Tag, html_url→URL, published_at→PublishedAt
  • 404 = kein Release; liefert neuestes non-prerelease, non-draft Release (Forgejo/GitHub-kompatibel)
  • Connectivity-Test: GET {base_url}/api/v1/user

6.4 Ticket: Phasical / Jira / Linear

Factory pro Integration-kind. Liest ticket_projects für Create-Defaults und Status-Mapping.

Connectivity-Tests: GitHub GET /user; GitLab GET /api/v4/user; Gitea/Forgejo/Codeberg GET /api/v1/user; Phasical lightweight GET; Jira GET /rest/api/3/myself; Linear GraphQL viewer.

6.5 Notifications: Shoutrrr

  • shoutrrr.Send(shoutrrrURL, message) — URL aus notification_targets (decrypted).

11. CI/CD (GitHub Actions)

Gleiches Muster wie slugbase, pipewatch und dispatch-one: branch-/event-Entrypoints rufen reusable Workflows (workflow_call) auf. Kein monolithischer Workflow pro Branch.

11.1 Branch-Modell

BranchTriggerNach erfolgreichem CI
devPushBuild + Push GHCR: nightly + {short_sha}
mainPushprepare-release — Draft-Release + Git-Tag nur bei VERSION-Bump
PRpull_requestNur CI — keine Images, kein Release
Releaserelease: publishedBuild + Push GHCR: latest + Release-Version-Tag

Feature-Branches: PR gegen dev oder main. Integration läuft über dev; main ist Release-Track (geschützt).

11.2 Workflow-Layout (.github/workflows/)

DateiTypAufgabe
pr.ymlEntrypointPR → ruft ci.yml
dev.ymlEntrypointPush dev → ci.yml → build-and-push-images.yml
main.ymlEntrypointPush main → ci.yml → prepare-release.yml
release.ymlEntrypointrelease: published → build-and-push-images.yml
ci.ymlReusableCI-Gate — workflow_call only
prepare-release.ymlReusableDraft-Release + Git-Tag bei Version-Bump
build-and-push-images.ymlReusableMatrix web + worker → GHCR

Entrypoints setzen concurrency pro Branch/Release (cancel-in-progress: true außer Release-Publish). Reusable Workflows werden nur via uses: ./.github/workflows/… aufgerufen — kein direktes on: push.

11.3 Entrypoint-Details

pr.yml

on: pull_request
jobs:
  ci:
    uses: ./.github/workflows/ci.yml
    secrets: inherit

dev.yml

on:
  push:
    branches: [dev]
  workflow_dispatch:

jobs:
  ci:
    uses: ./.github/workflows/ci.yml
    secrets: inherit

  meta:
  # short_sha = GITHUB_SHA first 7 chars

  push-images:
    needs: [ci, meta]
    if: needs.ci.result == 'success'
    uses: ./.github/workflows/build-and-push-images.yml
    with:
      tags: |
        nightly
        ${{ needs.meta.outputs.short_sha }}

main.yml

on:
  push:
    branches: [main]
  workflow_dispatch:

jobs:
  ci:
    uses: ./.github/workflows/ci.yml
    secrets: inherit

  prepare-release:
    needs: [ci]
    if: needs.ci.result == 'success'
    permissions:
      contents: write
    uses: ./.github/workflows/prepare-release.yml
    secrets: inherit

Kein Image-Build auf main-Push — Production-Images nur bei release: published (wie slugbase CE-Release-Flow).

release.yml

on:
  release:
    types: [published]

jobs:
  push-images:
    uses: ./.github/workflows/build-and-push-images.yml
    with:
      ref: ${{ github.event.release.target_commitish }}
      tags: |
        latest
        ${{ github.event.release.tag_name }}

11.4 Reusable ci.yml

Parallele Jobs (analog pipewatch/slugbase):

JobWorker (Go)Web (Next.js)

11.5 Root-VERSION & prepare-release.yml

Repo-Root: Datei VERSION — eine Zeile, Semver ohne v-Prefix, z.B. 0.2.0.

Script scripts/ci/create-draft-release.mjs (oder gleichwertig):

  1. fetch-depth: 0 Checkout.
  2. Letzten Release-Tag finden: git tag --list 'v*' --sort=-v:refname (oder letzter published Release via gh).
  3. VERSION bei HEAD vs. VERSION am Tag-Commit lesen.
  4. Wenn HEAD nicht semver-strikt größer → skip (kein Draft, kein Tag).
  5. Bei Bump: Git-Tag v{VERSION} anlegen und pushen; Draft-GitHub-Release mit Title Release Ops v{VERSION}; Notes = git log seit letztem Tag.

Tag-Format: v{X.Y.Z} (entspricht VERSION). Kein date-basiertes release-YYYY-MM-DD — Version kommt aus der Datei.

11.6 GHCR Images & Tags

ImageRegistryBuild context
ghcr.io/{owner}/release-ops-webGHCRapps/web/Dockerfile
ghcr.io/{owner}/release-ops-workerGHCRcmd/worker / Worker-Dockerfile
EventTags pro Image
Push dev (CI green)nightly, {short_sha} (7 Zeichen)

Auth: docker/login-action mit ghcr.io, username: ${{ github.actor }}, password: ${{ secrets.GITHUB_TOKEN }}, Job-permissions: packages: write.

Reusable build-and-push-images.yml Inputs:

workflow_call:
  inputs:
    tags:        # newline-separated suffixes (nightly, abc1234, latest, v0.2.0)
      required: true
    ref:         # optional checkout ref (release target_commitish)
      default: ""
    service:     # optional: web | worker — default both

Build: Docker Buildx, Registry-Cache (buildcache-Tag), kein Runtime-Secret im Image — Env zur Laufzeit (Compose/Coolify).

11.7 MVP-CI-Anforderungen

  • Workflow-Dateien wie §11.2 vorhanden; reusable Workflows haben kein eigenes on: push.
  • PR und Push auf dev/main blockieren bei CI-Failure.
  • dev-Push produziert nach CI zwei Tags pro Image (nightly + SHA).
  • main-Push mit erhöhter VERSION erzeugt Draft-Release + v*-Tag; ohne Bump kein Release-Artefakt.
  • Published Release pusht latest + Version-Tag für web und worker.

12. MVP Acceptance Criteria

  1. Admin kann sich einloggen (Email/Password).
  2. Admin kann Integrationen für alle acht kind-Werte anlegen; Secrets nie in API-Responses.
  3. Admin kann pro Ticket-Integration mehrere Ticket-Projekte anlegen (Phasical-Projekte, Jira-Keys, Linear-Teams) mit eigenem status_mapping und on_open_ticket_policy.
  4. Admin kann monitored Repo mit beliebiger Source/Ticket-Projekt-Kombination anlegen (z.B. Codeberg+Phasical, Forgejo+Jira, Gitea+Linear).
  5. Integration-Test pro Provider liefert Erfolg/Fehler in UI.
  6. Erster Poll: baseline — kein Ticket, last_known_tag gesetzt.
  7. Poll ohne Release-Wechsel: skip.
  8. Neues Release, kein offenes Ticket (oder done/cancelled): create — Ticket im Zielsystem sichtbar.
  9. Neues Release, offenes Ticket, Policy supersede: altes Ticket → superseded-Status + Kommentar; neues Ticket angelegt; tickets_superseded erhöht.
  10. Policies merge und skip_if_open funktionieren wie in §5.2.1.
  11. Status-Mapping wird pro Ticket-Projekt angewendet (unterschiedliche open/done-Werte je Phasical-Projekt, Jira-Key, Linear-Team).
  12. Admin kann Shoutrrr-Notification-Targets anlegen, testen; Events bei create/error/supersede.
  13. Mindestens ein End-to-End-Test pro MVP-Source (GitHub, GitLab, Gitea, Forgejo, Codeberg) und pro Ticket-Provider (Phasical, Jira, Linear) in CI (mock oder Sandbox).
  14. Dashboard, manueller Poll, Settings-Intervall, docker compose up wie zuvor.
  15. Go + Web Tests grün in CI; Workflow-Layout gemäß §11 CI/CD.
