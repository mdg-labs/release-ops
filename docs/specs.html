Release Ops

Self-hosted dependency-update bot: one GitHub App runs Renovate for every repository it is installed on, opens the update pull requests as its own bot user, and turns every update PR into a tracked ticket in Kaneo, Jira, or Linear. A dashboard lists open and merged update PRs and the jobs behind them. Users sign in with GitHub through the same App and get an admin or viewer role derived from their GitHub organization and team membership. Configuration, integration credentials, and monitoring run through a protected web UI (COSS); the UI and the Go API (auth, REST API) ship in the same app image.

Version: Spec v3.0 (2026-11-14) — v2 product: update engine · GitHub App setup · GitHub login · admin/viewer roles · update PRs and tickets · dashboard and REST API

The spec version is numbered independently of the product version: this document describes the v2 product (release v2.0.0).

1. Purpose & Non-goals

Purpose

Release Ops v2 is a self-hosted, Renovate-based dependency-update bot plus the ticket logic Release Ops already has. One GitHub App per instance, created through GitHub's App manifest flow (§3.3), is the bot identity, the webhook sender, and the login provider. For every repository the App is installed on, Renovate (the unmodified, pinned open-source engine) opens the update pull requests, Release Ops tracks each update PR as a ticket in Kaneo, Jira, or Linear through ticket projects (§5.3), and a dashboard shows open and merged update PRs and their jobs. Users sign in with GitHub and get an admin or viewer role derived from GitHub (§3.7).

  • Platform: GitHub (github.com). The App is the only credential Release Ops holds for GitHub.
  • Setup: a first-start setup token and the /setup manifest flow create and install the App (§3.2–§3.4).
  • Login: GitHub OAuth through the App; roles admin and viewer from org and team membership (§3.5–§3.10).
  • Tickets: Kaneo, Jira, Linear — each integration can have multiple project/team targets (ticket_projects) with their own status mapping (§5.3).

v2 non-goals

  • GitHub only. GitLab and GitHub Enterprise Server as platforms come later. Renovate still reads releases, tags, and packages of other hosts as datasources, so dependencies hosted elsewhere are still updated.
  • No private-registry hostRules in v2.0 — later.
  • No hosted offering — later. v2.0 is self-hosted, one instance per GitHub App.
  • No v1 release monitoring: watching upstream releases of GitHub, GitLab, Gitea, Forgejo, or Codeberg projects and opening a ticket per release is removed. Tickets follow update PRs, not releases.
  • No Shoutrrr notifications. Ticket systems and GitHub already notify; failures surface on the dashboard and in the metrics and health endpoints.
  • No mail and no local accounts: no SMTP, no email addresses, no passwords, no invitations, no password reset, no seed-admin, no public self-registration. GitHub is the only identity provider.
  • No role editing in the UI. Roles are derived from GitHub (§3.7).
  • Exactly one GitHub App installation per instance (§3.4).
  • Clean break from v1: v2.0.0 ships a new schema and performs no automatic migration of v1 data; a v1 data volume is not upgraded.

2.1 Internal listener & worker protocol

  • Bind: INTERNAL_ADDR (§9) is the address of a second HTTP listener in the app's Go process, on the Compose network. Its port is never published to the host and never proxied by Next. The public Go API stays on 127.0.0.1 behind Next.
  • Routes: only the worker routes below are mounted on it; no /api/v1/*, no setup, no webhook. A path outside this table answers 404. The worker routes are not mounted on the public Go API.
  • Authentication: every request carries the shared worker secret (WORKER_SECRET, §9) as a bearer credential, compared in constant time. A missing or wrong secret answers 401 and nothing else is evaluated. The secret is never logged. The listener speaks plain HTTP on the private Compose network, so that network is shared with the worker and nothing else.
  • The worker never touches the database. It claims jobs, heartbeats and posts results through these routes; the app is the only DB writer.
MethodPathDescription
POST/internal/v1/jobs/claimLong-poll. The worker offers a free slot. The app answers as soon as an eligible job exists (an enqueue wakes every waiting claim) with the job and its lease, or answers 204 after a bounded wait with no job, and the worker asks again. The claim is atomic (§2.8).
POST/internal/v1/jobs/{id}/tokenIssues the installation token for a job this worker holds under a live lease (§2.3). Any other job, or an expired lease: 409.
POST/internal/v1/jobs/{id}/heartbeatReports liveness; the worker's first heartbeat for a claimed job also marks the job started (§2.9 latency). It carries nothing else. The answer can tell the worker to abort (the repository was paused or removed, or the lease was lost).
POST/internal/v1/jobs/{id}/resultPosts the outcome: Renovate's exit status, a bounded and redacted log excerpt, the Renovate report when present (§2.2), and the raw global config as used (§2.4). Idempotent per attempt.

Request bodies are size-limited and JSON. Heartbeat and result writes go through the app's single writer connection (§4.9).

2.2 Per-job contract

  1. Claim. The worker claims a job (§2.1). The job names one repository (owner/repo), its priority, the slot it runs in, and the lease expiry.
  2. Token. Only now the worker asks for a token. The app mints it in the app process: an App JWT (§3.4) exchanged at POST /app/installations/{installation_id}/access_tokens with the repository list restricted to the target repository plus the preset repositories listed in instance config (PRESET_REPOSITORIES, §9; for example a shared presets repository) and the global config repository when one is configured (§2.4). The token is valid about one hour, is held in memory only, and is returned to the claiming worker over the internal listener (§2.1). The preset repositories must be reachable by the installation (the App is installed on them), as the job needs them to resolve extends presets.
  3. Run. The worker starts Renovate (§2.3) with this environment:
    VariableValue
    RENOVATE_PLATFORMgithub
    RENOVATE_TOKENThe job's installation token
    RENOVATE_REPOSITORIESThe job's owner/repo — exactly one repository
    RENOVATE_GIT_AUTHORThe App's bot identity: <slug>[bot] <<id>+<slug>[bot]@users.noreply.github.com>, where id is the numeric id of the App's bot user (§2.9). The app sends the string with the job, because the worker has no GitHub identity of its own
    plus the config-file location and job-level settings of §2.4–§2.5. Renovate reads the repository, opens or updates branches and PRs as the App's bot user and updates the Dependency Dashboard.
  4. Result. The worker posts the result (§2.1) and frees its slot. The app writes the outcome, ingests the report and hands the repository to the PR-state sync and ticket engine (what they do with it: §5.1, §5.2 and §5.6).
  • The worker never holds the encryption key (APP_ENCRYPTION_KEY) or the App's private key, and never mints a token. Its only secrets are the worker secret and the token of the job it is running.
  • Every value the worker posts or logs is redacted for the job's token first; the app never logs a token either. Renovate's own log redaction is not relied on alone.
  • Renovate's output. The worker runs Renovate with JSON logs and the file report (reportType=file, an option the Renovate documentation marks experimental) and posts a bounded excerpt of the logs and the report. The report schema is not a stable contract, so the app parses it defensively and treats it as enrichment (dependency, from, to): GitHub is the source of truth for PR state, and a missing or unreadable report fails nothing. The Renovate version is pinned (§2.3); report-field assertions are tracked as #222.
  • A repository with no Renovate configuration ends the job early as "no config" (requireConfig=required, §2.5); the result says so (§2.7).

2.3 Worker process model

  • Image: the worker image is built FROM the pinned Renovate image (unmodified, pinned by tag and digest) and adds the release-ops binary. Renovate runs as a child process of release-ops worker, one per claimed job, never in the API process and never from a Docker container (no Docker socket).
  • Two Unix users. The worker process runs as one user; Renovate runs as a second Unix user inside the same container and cannot read the worker secret (not its environment, not a file, not a mounted secret). Renovate gets a minimal environment: PATH, HOME of its own user, the variables of §2.2 and §2.4, and log settings. No app secret and no worker-side setting is passed to it. That Renovate runs as a second user with the tools mount (§2.5) and binarySource=install is covered by a CI smoke test (tracked as #195).
  • Lifetime: the worker enforces the job timeout (§2.5): it stops Renovate's process group, waits briefly and then kills it, by PID. A worker that dies leaves a lease that the reaper reclaims (§2.8).
  • Pinning: Release Ops pins one Renovate version per release. The pin is a literal tag and digest in the worker stage of the Dockerfile; running another Renovate means editing it, at your own risk (§9): the report and log handling is tested against the pinned version only.

2.4 Global self-hosted config & tools

Renovate's self-hosted (global) configuration is a file in git, so it can keep its own review and validation. It is not edited in the UI.

  • Where it comes from. By default the worker fetches it at job start from a configured repository and ref (GLOBAL_CONFIG_REPO, GLOBAL_CONFIG_REF, §9) with the job's installation token (§2.2). The same fetch brings the tools directory (§2.5). Alternatively the file and tools are mounted into the worker from the host and nothing is fetched. A fetch failure fails the job before Renovate starts.
  • Release Ops owns four keys. platform, token and repositories are set by Release Ops per job (§2.2), and allowScripts is fixed to false (§2.5). If the file contains any of them they are ignored (the worker removes them before handing the file to Renovate and logs a warning that names the key, never a value).
  • allowedCommands lives only in this file. It is never per repository (a repository's own config cannot add to it) and never set through the UI or API.
  • The UI shows the file raw. Admins can view the file as the worker last used it, as plain text. Release Ops never parses or evaluates it (it may be JavaScript) and the page cannot edit it (§3.10). The worker returns the raw text with each job result (§2.1) for that purpose. The file must not contain secrets.
  • Everything else in the file is Renovate's: presets, prConcurrentLimit, schedules, binarySource, and so on.

2.6 Worker egress

The worker needs outbound access to:

  • the GitHub API and git over HTTPS (api.github.com, github.com) for the repositories, presets and the global config repository;
  • the package registries and datasources of the ecosystems the repositories manage (npm, PyPI, Maven, Docker registries, GitHub releases of other projects, and so on), whatever Renovate's managers for them contact;
  • the tool downloads when binarySource=install (the hosts the tool installer fetches language runtimes and package managers from);
  • the app's internal listener (§2.1) on the Compose network.

The worker needs no inbound connection and no access to the database, the Docker socket or any ticket system. An egress allowlist can be applied by the operator; the customer-facing list is documented separately (#223).

2.7 Repository selection

  • No explicit repository list. A repository takes part when the App is installed on it (the installation's repository selection, §3.4) and a Renovate config file is present (renovate.json, or any other file name Renovate accepts). Presence is decided by Renovate itself through requireConfig=required: a repository without one ends its job early and is recorded as "no config". The app skips scheduled runs (§2.9) for a repository last recorded as "no config"; a push to its default branch, installation_repositories.added and an admin "run now" still start a job, so adding the file is noticed.
  • Pause and enable. An admin can pause a repository and enable it again (§3.10). A paused repository gets no job from any trigger; events for it are accepted and dropped.
  • "Enable repo". For a repository without a config file, an admin action opens a PR that adds a renovate.json extending the configured preset (endpoint: §7.5; page: §8.3).

2.8 Job queue

A persistent jobs table (§4.6) is the queue. Webhooks only verify, coalesce and return (§2.10); nothing runs in the request path.

  • One job per repository at a time. A repository has at most one running job and at most one queued job. The database enforces this, not only the claim query.
  • Priority. High (webhook triggers and admin "run now") is claimed before normal (the hourly safety net and the polling fallback); within a priority, oldest first. run_after holds a job back until its time.
  • Global cap. A claim succeeds only while the number of running jobs is below the concurrency cap (default 2, instance setting). With a cap of 2 or more, one slot is reserved for high-priority jobs: a normal job is claimed only while running jobs are below cap−1. With a cap of 1 there is no reservation.
  • Coalescing per repository. A trigger for a repository that already has a queued job adds to that job (the highest priority wins, the matched checkbox markers (§2.9) are added) and creates no second one.
  • rerun_requested. A high-priority trigger that arrives while the repository's job is running must not be lost, because Renovate may already have read the old body. It sets rerun_requested on the running job and records the trigger, the matched markers and the webhook arrival time (rerun_trigger, rerun_markers, rerun_webhook_received_at); several ticks during one run collapse into the one flag, the latest trigger, the union of their markers and the earliest arrival time. When the run finishes, the app enqueues exactly one follow-up high-priority job for the repository, which carries the recorded trigger, markers and arrival time (not the finished job's), so the job shows what actually caused it. A normal-priority trigger arriving mid-run is dropped (the run in progress covers it). When the run fails and is retried, the retry is the follow-up: it keeps its own trigger and markers, adds the recorded markers and arrival time, and takes the recorded trigger only if it was a normal-priority job. A follow-up that joins an already queued job merges the recorded values into it the same way.
  • Leases and the reaper. A claim sets running, the lease owner and lease_expires_at. The lease is the job timeout plus a margin (§2.5). Heartbeats show liveness and carry aborts (§2.1). A reaper in the app periodically moves every running job whose lease has expired back to queued (the attempt is counted; with no attempts left the job fails), so a dead worker frees its repository.
  • Retries and backoff. A failed attempt is re-queued with a growing run_after until the attempt limit. There are two policies, and the first one that applies is used:
    • Plain failure. A job gets 3 attempts. The delay after the first failed attempt is 30 seconds and doubles with each further attempt, up to 15 minutes. It is spread by a jitter of ±20 %, so the actual delay is between 0.8 and 1.2 times the doubled one.
    • Rate-limited attempt. An attempt that ended because GitHub or another upstream refused it for a rate limit, or because the app itself refused to start the run while the installation's budget was exhausted (error code rate_limited), is not the job failing, so it has more room: 8 attempts. The delay starts at the same 30 seconds and doubles per attempt, but a single backoff delay is capped at 1 hour (the lifetime of an installation token), not 15 minutes. The jitter is upward only: the delay is increased by a random 0 to 20 %, never shortened, so jobs held back by the same limit do not all return at the reset.
    When GitHub (or another upstream) answered with Retry-After (seconds or an HTTP date), or the rate-limit reset time (X-RateLimit-Reset) is known, run_after is at least that long: the longer of the backoff and the upstream delay is used, and for a rate-limited attempt the upward jitter is added to that. An upstream delay and an upstream reset time are each trusted for at most 24 hours: a longer one is cut to 24 hours, so a wrong or hostile header cannot hold work back for longer. A rate limit that gives no delay holds work back for one minute. A GitHub 403 with neither Retry-After nor an exhausted X-RateLimit-Remaining is a secondary rate limit when its JSON message contains “secondary rate limit” (case-insensitive; nothing broader matches, and only a 403 is read this way): the app reads that body within its usual size bound, holds the installation’s shared budget back for at least one minute (longer when a longer Retry-After was sent) and returns a rate-limit error that carries nothing of the body. Any other 403, such as a permission refusal, is an ordinary error and leaves the budget alone. The worker reports the delay with the failed result in whole seconds, and the app applies the same 24-hour cap to what a worker reports.
  • Rate limit. An installation has one GitHub rate-limit budget, shared by every token minted for it. Renovate runs, the reconcile and polling (§2.11), failed-delivery redelivery and role checks (§3.8) all draw on it. While the budget is exhausted no job is claimed before it resets, and the app's own calls back off the same way. The budget of each installation is kept in memory and on the installation's row (rate_limit_remaining, rate_limit_limit, rate_limit_reset_at, §4.4), so an exhausted budget is still honoured after a restart. At startup the stored budgets of the installations that are not removed are loaded: a stored reset time further away than 24 hours is cut to 24 hours, and a stored reset time that cannot be read is dropped (the server logs a warning naming the installation id) instead of stopping the startup, so that budget holds nothing back until the next GitHub response. The budget is exposed as the metrics of §7.8, labelled with the installation id.
  • Interface. The queue sits behind a Go interface (enqueue, claim, heartbeat, complete or fail, reap), so a Postgres implementation can replace SQLite later (hosted). v2.0 ships the SQLite one only.

Detecting a tick (generic)

  • Renovate's checkboxes have the form - [ ] <!-- name -->; a ticked one is - [x] <!-- name --> (Renovate's source: lib/modules/platform/pr-body.ts, lib/workers/repository/dependency-dashboard.ts). Examples: rebase-check in a PR body; rebase-branch=<branch>, approve-branch=<branch>, unlimit-branch=<branch>, rebase-all-open-prs, approve-all-pending-prs, create-all-rate-limited-prs, create-config-migration-pr on the dashboard.
  • On issues.edited and pull_request.edited the handler compares changes.body.from (the previous body, as GitHub's webhook payloads carry it) with the new body. It is a tick when any marker comment that was on an unchecked line ([ ]) in the old body is on a checked line ([x] or [X]) in the new one. The matching is by marker text, so reordered lines do not matter.
  • No hard-coded marker list: a new Renovate checkbox works without a Release Ops change. The matched markers are stored with the job and shown in the UI as the reason it ran.
  • An edit without changes.body (a title edit), and an edit whose body shows no unchecked-to-checked transition (a text edit, Renovate unticking a box after it acted), are ignored.

Identifying the bot and its objects

  • The App's bot user is <slug>[bot]. Its numeric user id is read once with GET /users/<slug>[bot] after the App is stored, kept with the App (§3.4, github_app.bot_user_id, §4.4) and used for every comparison and for RENOVATE_GIT_AUTHOR (§2.2); identity is the id, never the login.
  • A bot PR or the Dependency Dashboard is identified by author = the App's bot user plus Renovate's markers (the checkbox markers above, or Renovate's PR body markers). Never by branchPrefix or by the dashboard's title: those are set in per-repository or preset JavaScript configuration that Release Ops cannot evaluate.

Loop prevention

Renovate rewrites the dashboard and PR bodies on every run, and each rewrite returns as a webhook. Edits whose sender is the App's own bot are ignored, and so is any edit without a tick. pull_request.closed from the bot itself is not filtered (an automerge frees a slot a follow-up run needs); the one-job-per-repository coalescing (§2.8) bounds the cost.

Latency target

  • A job is started at most 10 seconds after its webhook arrives. The webhook handler only verifies, records and enqueues; an enqueue wakes the waiting claim (§2.1); the claim, token (§2.2) and global config fetch (§2.4) follow. "Started" is the app receiving the worker's first heartbeat for the job, measured on the app's clock from the arrival of the webhook, so it spans the app and worker processes. Both timestamps are stored on the job.
  • The PR or the dashboard is updated when Renovate finishes (minutes, depending on the repository); the target does not cover Renovate's own run time.
  • The target is verified live on the first deployment (#232).
  • Requires a reachable webhook endpoint; without one the degraded fallback of §2.11 applies.

2.10 Webhook endpoint (/hooks/github)

POST /hooks/github is the URL WEBHOOK_URL points at (§3.3, §9). GitHub reaches it without a session (§3.11). Next.js forwards the request body byte for byte (no parsing, no re-encoding) with the X-Hub-Signature-256, X-GitHub-Event and X-GitHub-Delivery headers to the Go handler.

  1. Size cap. The handler reads at most 1 MiB. A larger body is answered 413 and dropped (the safety net of §2.9 covers the repository). GitHub's documented payload cap is 25 MB; the subscribed events' payloads are far smaller, and the cap is raised only if a real payload needs it.
  2. HMAC. HMAC-SHA256 of the raw body with the stored webhook secret (§3.4) is compared in constant time with X-Hub-Signature-256 (sha256=<hex>) before anything is parsed. A missing or wrong signature is answered 401; nothing is stored. With no App configured the endpoint answers 503.
  3. Events. Only the subscribed events are processed (push, pull_request, issues, installation, installation_repositories, §3.3). Any other event, including ping, is answered 202 and ignored.
  4. Deduplicate. X-GitHub-Delivery is recorded; a GUID seen before is answered 202 and does nothing. The record and the resulting enqueue are written in one transaction, so a crash cannot record a delivery without its job. Records are pruned after WEBHOOK_DELIVERY_RETENTION_DAYS (§2.12), which outlasts GitHub's redelivery window.
  5. Decide and enqueue. The event is evaluated by the rules of §2.9 and enqueued; installation and installation_repositories also update the synced repositories (§3.4), and a pull_request event of a bot PR also upserts the update PR (§5.1). No GitHub call happens in the request path.
  6. Answer 202 as soon as the transaction commits, well inside GitHub's 10-second delivery timeout.

2.11 Recovery & polling fallback

  • Failed deliveries. GitHub does not redeliver a failed delivery by itself. At startup and every 15 minutes, when the webhook is active, the app lists the App's recent failed deliveries (GET /app/hook/deliveries, App JWT, status=failure, paged with cursor) and redelivers each with POST /app/hook/deliveries/{delivery_id}/attempts unless a delivery with the same guid has succeeded since. A redelivered event passes through the same endpoint (§2.10). The hourly safety net is the last-resort net behind this.
  • Reconcile. Together with the safety net, the app reconciles installations and repositories hourly and at startup (§3.4).
  • No public URL: polling fallback (degraded). With WEBHOOK_URL unset the webhook is inactive (§3.3), no event arrives, and none of the redelivery above applies. The app then polls per installation instead, at an interval of minutes, using conditional requests (ETag / If-None-Match) so an unchanged repository costs no rate-limit budget: the Dependency Dashboard and open bot PRs (the poller keeps the last body it saw of each and applies the same tick test as §2.9), the closing of a bot PR, and the default branch head. A change enqueues a normal-priority job, trigger polling with the ticked markers, through the same coalescing. The poller lists the open issues the bot user created (GET /repos/{owner}/{repo}/issues?state=open&creator={slug}[bot], keeping those whose user.id is the bot's numeric id and that are not pull requests) and the open PRs of the reconcile (§5.1), reads the default branch head with GET /repos/{owner}/{repo}/git/ref/heads/{branch}, and keeps the ETags and the last bodies and head in memory only: the first pass that sees a repository, such as the first after a start, only records them, so a change made while the app was down is left to the hourly safety net. A bot PR that is no longer listed as open counts as closed. One pass asks for at most one job per repository. The hourly safety net and "run now" work unchanged.
  • The fallback is degraded: reaction time is minutes, not seconds, the 10-second target of §2.9 does not apply, and a tick made while a run was already in progress can be missed. The customer documentation says so (#223); the Settings page shows that the instance is in polling mode.

2.12 Open questions of the update engine

Not settled by the brief, the plan or the documentation; to be decided with the first deployment (#231) or by the maintainer:

  • Numeric defaults: job timeout and lease margin, heartbeat interval, claim long-poll wait, the polling-fallback interval, the ticket engine's retry backoff, and the worker container's CPU and RAM limits. The attempt limits and the backoff curve are settled (§2.8).
  • Retention (settled). Two settings, both whole numbers of days, both read from the environment (§9) at startup:
    • JOB_HISTORY_RETENTION_DAYS: how long a finished job and its history are kept (§4.6). Default 30; valid range 1 to 3650.
    • WEBHOOK_DELIVERY_RETENTION_DAYS: how long a webhook delivery's GUID is remembered (§2.10, §4.6). Default 7; valid range 4 to 3650. The minimum of 4 days is there so that a record always outlasts GitHub's three-day redelivery window: a record pruned earlier could let a redelivered delivery run twice.
    An unset or empty variable (surrounding whitespace is ignored) takes its default. A value that is not a whole number, or lies outside the range, stops the server at startup with an error that names the variable, the range and the value, so a typo cannot silently keep history for a day or for good.
  • The in-repository paths of the global config file and the tools directory, and the mount paths in the mounted variant.
  • Whether finer per-job CPU and RAM limits inside the worker container are wanted beyond the container limits and the job timeout.
  • Whether more than one worker container is supported (the cap counts running jobs across workers; v2.0 documents one).

3. Setup, Authentication & Roles

Setup and auth live entirely in Go. Next.js is UI-only — the setup and sign-in pages and API clients call Go through the same-origin proxy. GitHub is the only identity provider: there is no local password login. One SQLite file (app.db), one writer process.

GitHub references for the calls below: registering a GitHub App from a manifest, create a GitHub App from a manifest, generating a user access token for a GitHub App, organization members, and team members.

3.1 Session model (Go)

  • Sessions: server-side store in the sessions table (e.g. github.com/alexedwards/scs/v2 with SQLite store), §4.0.1.
  • Cookie: release_ops_session — HttpOnly, SameSite=Lax, Path=/, Secure when APP_URL is HTTPS.
  • Signing key: SESSION_SECRET env (32+ random bytes).
  • No JWT between Next and Go — the browser sends the session cookie; the Next proxy forwards Cookie and passes through Set-Cookie on sign-in and logout.
  • The session token is renewed on every successful sign-in (GitHub callback and break-glass redemption): a new token is issued and any pre-login token is discarded.
  • The post-sign-in redirect target is accepted only as a same-origin relative path (apps/web/lib/auth/safe-redirect.ts); anything else falls back to /.
  • Lifetime: capped at 8 hours from sign-in (§3.8). Logout deletes the current session.

3.2 First-start setup token

While no GitHub App is configured the instance is in setup mode: sign-in is unavailable and only the setup endpoints (§7.0) and the /setup page are usable. Setup is protected by a one-time setup token.

  • Source: the SETUP_TOKEN env value when set, which must be at least 64 characters (the length of a generated token, 32 random bytes as hex) so an operator-supplied token is never easier to guess than a generated one, and startup refuses a shorter one; otherwise the server generates a random token on start and prints it to the log. The log line is printed on each start that finds no App configured.
  • Storage: only a SHA-256 hash of the token is stored, as an auth_tokens row of kind setup (§4.0.2); the token itself is never persisted. Comparison is constant-time. Every start that finds no App configured replaces the stored row with the hash of the current token (the generated one, or SETUP_TOKEN), so a missed log line is recovered by restarting. The token has no expiry of its own: it stays valid until it is redeemed or an App is stored.
  • Single use: the token is consumed when POST /api/v1/setup/session opens a setup session (§3.3 step 1). The consume is a guarded write (only a still-unconsumed token matches) made before the session is created, so two concurrent redemptions cannot both succeed.
  • Setup session: the redemption opens a 15-minute setup session in the server-side session store, with the session token renewed. It grants access to the setup routes (§7.0) and nothing else: the protected API still requires a user session (§3.11), and a user session is not a setup session. An expired setup session is destroyed and answers 401.
  • No re-arm: the token stays consumed when a later step fails, including a failed conversion of the manifest code (§3.3 step 4). The admin retries within the setup session, or, once the session has ended, restarts the server for a new token while no App exists.
  • Valid only while no App is configured: once an App is stored, setup/session (both methods), setup/manifest and setup/callback answer 404 and the token is dead, even if SETUP_TOKEN stays in the environment — the env value is ignored from then on. GET /api/v1/setup/status stays available.
  • Setup endpoints are rate limited per client IP (§7.0).

3.3 GitHub App setup (/setup manifest flow)

The App is created through GitHub's manifest flow, so the operator creates no App by hand.

  1. Choose the owner. The operator opens {APP_URL}/setup, enters the setup token, which opens the setup session (§3.2), and chooses who owns the App: a personal account (registration URL https://github.com/settings/apps/new) or an organization (the operator enters its name; registration URL https://github.com/organizations/{org}/settings/apps/new). An optional App name may be entered; GitHub's confirmation page lets the owner change it.
  2. Start. Go requires the setup session, builds the manifest below, and stores a random single-use state bound to this attempt, valid for 1 hour. The UI submits the manifest as a JSON string in the form field manifest by POST to the registration URL with that state.
  3. Confirm. The owner confirms on GitHub, which redirects the browser to redirect_url with a temporary code and the state.
  4. Convert and store. Go compares state with the one bound to the setup session (constant-time, one use) and claims it in a set of redeemed states held by the app process, under a lock, after the rate limiter, the setup-session check and the constant-time match and before any call to GitHub, so when several requests present the same state at once exactly one passes and the others are refused; a mismatch, a missing or an already claimed state is refused without calling GitHub. The set is in memory and is not kept across a restart; the single-use code GitHub issues is the second guard. Then Go calls POST /app-manifests/{code}/conversions within the 1 hour the code is valid. The setup session is required for this request too; its cookie travels with the top-level redirect from GitHub. Go stores the App (§3.4); a failed conversion stores nothing and leaves the setup session usable for a retry (§3.2). The browser is then redirected to the App's installation page, https://github.com/apps/{slug}/installations/new. Every failure of this request is a same-origin redirect (302) to /setup?error=<code>, which shows the message inline, because the browser arrives here from GitHub and would otherwise land on raw JSON: invalid_state (the state is missing, mismatched, spent or older than 1 hour), conversion_rejected (GitHub refused the code), conversion_failed (GitHub could not be reached or did not answer, or the App could not be stored) session_expired (the setup session is missing or has ended, §3.2; the operator restarts the server for a new setup token if no App was stored) and rate_limited (the client address exceeded the route's limit, §7.0; the browser is redirected before any other check and the admin creates the App again after the Retry-After delay). Once an App is stored the route answers 404 instead.
  5. Install. The owner installs the App and selects repositories; GitHub redirects to setup_url with installation_id (and setup_action). Go verifies and records the installation (§3.4) and redirects to /login.
  6. First admin. The first admin signs in with GitHub (§3.5, §3.6).

3.4 App storage, installation & key rotation

Storage

  • One App per instance (singleton). Stored non-secret fields: App id, slug, client id, owner, HTML URL.
  • The private key (pem), client secret, and webhook secret are encrypted at rest with the existing credential encryption (§4.8: AES-256-GCM, APP_ENCRYPTION_KEY). They are decrypted only inside the Go process, never returned by the API (only hasSecret-style flags) and never logged — not on success, not on failure, not inside error messages.
  • Installation tokens are minted in the Go process from an App JWT (RS256 signed with the private key, iss = App id, expiry within 10 minutes) through POST /app/installations/{installation_id}/access_tokens, are valid about one hour, and are held in memory only. A token for a job is issued to the claiming worker only (§2.2).
  • Table shapes (github_app, installations, repositories) are specified in §4.4.

Installation: exactly one

  • The App is private (public: false), so GitHub lets only its owner install it. The instance additionally accepts one installation; a second installation id is not recorded (the event or redirect is answered successfully and ignored, and a warning without secrets is logged).
  • The installation is recorded from the setup_url redirect and/or the installation webhook event, whichever arrives first; both are idempotent. The installation_id from the redirect is untrusted until Go has fetched GET /app/installations/{installation_id} with the App JWT and read the account (login, id, type User or Organization) from that response.
  • When the installation is deleted (installation event deleted, or a reconcile no longer finds it) it is marked removed, and a new installation of the same App may then be recorded.
  • Everything installation-scoped (repositories, and what hangs off them in the v2 data model) belongs to that installation.

Repositories

  • Installed repositories are synced from the installation and installation_repositories events (repositories added and removed) and by a reconcile that lists them with an installation token (GET /installation/repositories) and compares the installation with GET /app/installations. The reconcile runs at start and hourly, with the safety net (§2.11).
  • With WEBHOOK_URL unset the webhook is inactive, no events arrive, and the reconcile is the only sync path — documented as degraded.

Private key rotation

An admin can replace the App's private key without re-running setup (PUT /api/v1/github-app/private-key, §7.0.1). This is a release blocker for v2.0.

  1. The new key is parsed as an RSA private key in PEM form.
  2. It is verified before anything is replaced: Go signs an App JWT with the new key and calls GET /app; the response must succeed and report the stored App id.
  3. Only then is the new key encrypted (§4.8) and stored in place of the old one, in one write. On any failure the old key stays active and the response carries a generic message.
  4. The submitted key is never echoed back, never logged, and never part of an error message. Deleting the old key at GitHub is a separate step the admin takes in the App's settings there.

3.5 GitHub login

Sign-in is GitHub OAuth through the App (user authorization), with state and PKCE, as documented in generating a user access token for a GitHub App.

  1. Start. GET /api/v1/auth/github/login: Go generates a random state and a random PKCE code_verifier, stores both in the server-side pre-login session (bound to the browser's session cookie), and redirects to https://github.com/login/oauth/authorize with the App's client_id, redirect_uri (the registered callback, §3.3), state, code_challenge (S256 of the verifier) and code_challenge_method=S256. An optional post-sign-in path is kept in that session (§3.1).
  2. Callback. GET /api/v1/auth/github/callback?code&state: the returned state must match the session's (constant-time) and is deleted on first use. It is also claimed in a set of redeemed states held by the app process, under a lock, after the rate limiter and the constant-time match and before any call to GitHub, so when several requests carrying the same pre-login session present the same state at once exactly one passes and the others are refused; the set is in memory and is not kept across a restart, and the single-use code GitHub issues is the second guard. A mismatch, a missing pre-login session, an expired attempt (older than 10 minutes) or a replay is refused before any call to GitHub. The browser arrives here from GitHub and would otherwise land on raw JSON, so this refusal and every other failure of the callback is a same-origin redirect (302) to /login?error=<code>, here invalid_state; a rate-limited start or callback redirects (302) to /login?error=rate_limited (§7.0). /login shows a fixed message per code. Go then exchanges the code at POST https://github.com/login/oauth/access_token with client_id, client_secret, code, redirect_uri and the code_verifier.
  3. Identify. With the user token Go calls GET /user and takes the numeric GitHub user id and the current login. When BOOTSTRAP_ADMIN_GITHUB_LOGIN matches and no bootstrap admin is stored yet, the id is stored now (§3.6).
  4. Evaluate. The role is evaluated with the installation token (§3.8). With no role, sign-in is refused (403) and no session is created.
  5. Scope. For a viewer, Go calls GET /user/installations/{installation_id}/repositories with the user token (§3.9).
  6. Discard. The user token is used once for these calls and then discarded: never stored, never logged, not kept in the session, also on every error path. The token response carries expires_in (28800 seconds, 8 hours, for expiring tokens) and, for expiring tokens, a refresh_token (refresh_token_expires_in about 6 months); both are ignored — the token is spent seconds after it was issued, so there is no refresh flow, and the 8-hour session cap (§3.8) matches GitHub's default token lifetime. No scope is requested; the App's permissions and the user's own access bound what the token can read.
  7. Session. Go upserts the user by numeric id (the login is updated to the current one), renews the session token (§3.1), and stores the role, the time of the last evaluation, and (for a viewer) the repository id list in the session.
  • Identity is the numeric GitHub user id, never the login or an email: logins can be renamed and reassigned. The login is display data. The only place a login selects a user is the one-time bootstrap resolution (§3.6).
  • An error from GitHub on the authorize step (e.g. the user denied access) returns the browser to /login with a fixed error code; no GitHub text is reflected.
  • There is no local password login, no POST /api/v1/auth/login, and no registration.

3.6 Bootstrap admin & break-glass login

BOOTSTRAP_ADMIN_GITHUB_LOGIN

  • Optional env: the GitHub login of the pinned first admin.
  • At the first sign-in whose authenticated GET /user login equals the env value (compared case-insensitively, as GitHub logins are), Go resolves it to that user's numeric id and stores the id, once, as the bootstrap admin. From then on the stored id is the bootstrap admin and the env value is ignored — removing or changing it has no effect, and a later rename or reassignment of the login gains nothing.
  • The bootstrap admin is always admin, independent of organization or team membership (§3.7).

Break-glass login link

There is no local fallback login. For recovery (for example when GitHub sign-in is broken), an operator with shell access to the container runs release-ops admin login-link. Shell access already implies admin.

  • The command creates a random token, stores only its SHA-256 hash with an expiry, and prints the link {APP_URL}/login/link?token=… once to the terminal. The server never logs the token.
  • Expiry: 15 minutes. Single use: redeeming (POST /api/v1/auth/login-link) consumes the token first, with a guarded write that matches only an unconsumed, unexpired token, and only then creates the session; concurrent redemptions cannot both succeed. An unknown, expired, or used token is refused (400) with one generic message.
  • The session is the bootstrap admin's: role admin, token renewed (§3.1), the 8-hour cap applies (§3.8). The command refuses when no bootstrap admin has been resolved yet.

3.8 Role evaluation & session lifetime

Roles are checked with the installation token (Organization members: read), not the user token, at login and every 15 minutes during a session.

  1. Bootstrap admin (stored numeric id): admin; no GitHub membership call.
  2. Personal-account installation: admin when the numeric id equals the account owner's id, otherwise no access.
  3. Organization: GET /orgs/{org}/memberships/{username}. Not found, or state other than active: no access. role admin: admin. Otherwise a member.
  4. A member is admin when ADMIN_TEAM is set and GET /orgs/{org}/teams/{team_slug}/memberships/{username} reports state active.
  5. A remaining member is viewer; with VIEWER_TEAM set, only when the same team membership call reports active, otherwise no access.

The membership endpoints take a username, but identity is the numeric id: the evaluation first resolves the current login from the id (GET /user/{account_id}), so a renamed user is still found.

  • Re-check: the session stores when the role was last evaluated. A request on a session whose last evaluation is more than 15 minutes old triggers a re-evaluation before the handler runs. The role is updated in the session when it changed.
  • Losing membership ends the session: when the evaluation says no access, the session is deleted and the request is answered 401.
  • Fail closed: when GitHub cannot be reached or answers with an error other than a definitive "not a member", the request is answered 503; the session is neither extended nor deleted and the next request tries again. A stale role is never served past its 15-minute window.
  • Lifetime cap: a session ends 8 hours after sign-in; re-evaluations never extend it.
  • A viewer's repository list is fixed at sign-in (§3.9), so a session's access cannot outlive the 8-hour cap.

3.9 Repository scope

  • A viewer sees only repositories they can access on GitHub. At sign-in, Go calls GET /user/installations/{installation_id}/repositories with the user token (all pages), intersects the result with the installed repositories, and stores the repository id list with the session — never the token. The list is not refreshed during the session; the 8-hour cap bounds its age.
  • Admins see everything the installation covers; no list is stored for them.
  • Every handler that returns or acts on repository-scoped data filters by this list for a viewer. A repository outside the list answers 404, so its existence is not revealed.

4. Data model

Canonical SQL: schema.html (browser view) · db/schema.sql (source file). All tables in app.db (including auth).

4.0 Schema migrations (generated only)

Never hand-write migration SQL. Workflow:

  1. Edit db/schema.sql (canonical DDL — not under docs/). Every table is declared STRICT.
  2. Run make db-migration name=<change> — sqlite-migrate (pinned as a tool in go.mod) diffs db/schema.sql against the existing migrations and writes migrations/<timestamp>_<change>.sql with a checksum header.
  3. Review the generated file; commit it unedited. Generated migrations are immutable and there are no down migrations.
  4. Runtime apply: the Go server embeds migrations/ and applies pending ones on startup, before it opens its connection pool and listens.

CI runs npm run db:check (sqlite-migrate check) — fails if a migration no longer matches its checksum or if replaying migrations/ does not reproduce db/schema.sql. It needs Go only, no database. Agents: see .claude/rules/11-db-migrations.md.

Applying migrations safely

  • One transaction. All pending migrations run in a single transaction; a failure rolls the whole batch back, so the database never holds a half-applied or dirty migration state, and the next start reports the same error.
  • Snapshot first. Before applying, a VACUUM INTO snapshot goes to snapshots/ next to app.db (/data/snapshots in the container); the newest three are kept. A start with nothing pending takes no snapshot.
  • Checks before commit. foreign_key_check and integrity_check run inside the transaction. Foreign keys are suspended while migrating so table rebuilds can span related tables.
  • Destructive changes need consent. A change that ALTER TABLE cannot express is generated as SQLite's table-rebuild sequence. A change that drops a table or column is refused unless generated with -allow-destructive.
  • Immutable history. Editing or deleting a migration that a database already applied makes startup fail with a checksum or missing-file error.
  • Existing databases. Databases created before the migrations were reset to a single baseline are not upgraded; recreate the data volume.

internal/store/migrate_test.go covers the runner: a fresh database gets the baseline once and a second start applies nothing; a failing migration leaves the database unchanged; an edited or missing applied migration is rejected; every table is STRICT; and sessions.user_id rejects an unknown user.

Retention. A job in a terminal state (succeeded or failed) is deleted once it finished more than JOB_HISTORY_RETENTION_DAYS ago (default 30 days, 1 to 3650; §2.12, §9), together with its job_runs and job_events (the foreign keys cascade). 4.8 Credential encryption

  • Algorithm: AES-256-GCM.
  • Key: APP_ENCRYPTION_KEY — 32 bytes, hex-encoded (64 characters).
  • Stored format: base64(nonce + ciphertext + tag) — 12-byte random nonce prepended to ciphertext; entire blob base64-encoded in integrations.encrypted_payload and the three encrypted columns of github_app (§4.4).

  • API returns has_secret: true for integrations, never the secret value.

4.9 SQLite settings

The queue and the webhook make concurrent access to app.db normal, so the connection setup is part of the design.

  • WAL mode (journal_mode=WAL). It replaces the v1 setup (shared cache, a single connection, no WAL), under which any transaction that read through the pool while holding the connection would deadlock itself.
  • One writer connection. Every write (REST handlers, webhook handler, internal listener, scheduler, reaper, migrations) goes through a single writer connection, so writes are serialized in the app process and never contend with each other.
  • A separate read pool of read-only connections serves reads, so a long read does not block the writer and a write does not block reads.
  • cache=shared is dropped. Foreign keys stay on.
  • Code that holds a write transaction reads through that transaction, never through the pool or the writer handle again.
  • WAL keeps app.db-wal and app.db-shm beside app.db on the data volume; backup and restore handle them as a set (§10).

SQLite stays the only supported database in v2.0. The queue sits behind an interface (§2.8) so Postgres can replace it for a hosted deployment later; there is no dual-database support.

5. Update PRs, Tickets & Idempotency

Renovate opens and maintains the update pull requests (§2); this section is what Release Ops does with them: it tracks each as an update PR (§5.1) and keeps one ticket per PR in sync (§5.2–§5.4). §5.6 and §5.7 are the job flow and scheduling. There is no release decision: a ticket exists because an update PR exists, never because an upstream project published a release (§1).

5.1 Update PR model

Source of truth: GitHub

GitHub is the source of truth for a PR's state. Release Ops learns it from two inputs and the Renovate report only enriches it:

  • pull_request webhooks (opened, reopened, edited, synchronize, closed, labeled, unlabeled). For a bot PR (below) the handler upserts the update_prs row from the payload in the same transaction as the delivery record (§2.10): no GitHub call happens in the request path. The ticket engine (§5.2) is then woken.
  • Reconcile. The app lists the open PRs authored by the App's bot user of a repository (GET /repos/{owner}/{repo}/pulls?state=open, all pages, conditional requests with ETag, keeping the PRs whose user.id is the bot's numeric id, §2.9) and compares them with the stored rows. A stored open PR that is no longer listed is fetched (GET /repos/{owner}/{repo}/pulls/{number}) and set to merged or closed as GitHub reports it. The reconcile runs after every job result for the repository (Renovate has just changed its PRs), hourly with the safety net (§5.7) and at startup, so a missed webhook is repaired. With WEBHOOK_URL unset it is the only input (§2.11). It draws on the installation's shared rate-limit budget (§2.8).

Identifying a bot PR

A PR is an update PR when its author is the App's bot user (numeric id, never the login, §2.9) and its body carries Renovate's markers: the <!--renovate-debug:…--> comment Renovate appends to the body it generates from its body template, or a checkbox marker of the form - [ ] <!-- name --> (§2.9). It is never identified by branchPrefix or by its title: those are set in per-repository or preset configuration Release Ops cannot evaluate. A PR by the bot that has no marker (the "Enable repo" PR, §2.7, §7.5) is not an update PR.

5.2 Ticket rules

One ticket per update PR. A grouped PR is one ticket that lists all its dependencies (the template ranges over them, §5.4). The ticket engine is a process of the app, woken by every write to update_prs and run periodically as a safety net (§5.7). It reads PR state and writes tickets and nothing else; it never calls GitHub except to upsert the PR comment (§5.2.3).

Which PR gets a ticket

A PR gets a ticket when all of these hold at the time the engine looks at it:

  1. It is an update PR (§5.1) in state open. A PR first seen already merged or closed gets no ticket: tickets follow open PRs.
  2. It has at least one dependency (§5.1). This is how three kinds of bot PR are left out: no ticket is created for Renovate's config-migration PR, for onboarding PRs, or for any PR without dependencies, because none of them updates a dependency, so none has a report upgrade or an updates table. The onboarding PR the report names (onboardingPrNumber) is excluded explicitly as well. Release Ops never recognises these PRs by title or branch name.
  3. The repository has a ticket project (below).
  4. The PR passes the project's filter (below).

Ticket project of a repository

The project is the repository's own ticket_project_id when set (the per-repository override), otherwise the installation's default_ticket_project_id (§4.1). With neither, the repository's PRs get no tickets, and the repositories page says so (§8.3).

  • Ordering. The engine handles one ticket's events in order and never runs two operations on one ticket at once. Template syntax that fails to render fails that one operation with a message (no silent fallback, §5.4) and is retried after the admin fixes the template.
  • A PR merged or closed while its ticket creation is still unconfirmed (§5.2.2) gets no transition: the ticket is not known yet, so nothing moves until an admin has resolved the marker (§5.2.2).

5.2.2 At-most-once creation

A ticket must never be created twice for one PR, and a failed create must never block the PR for good. The pattern the v1 engine used for one release tag now protects one PR:

  1. Marker before the call. The engine inserts the update_tickets row (state pending) and sets pending_since before calling CreateTicket. The create call carries the external key (the row's id): the engine appends the line Release Ops key: <id> to the ticket description outside the template, so an admin's template cannot drop it and a person can find the ticket in the ticket system by it.
  2. The link write clears it. The write that stores external_id and external_url sets the state to open and clears pending_since in one transaction. Apart from the admin's clear action (step 4), nothing else clears a marker that may have a ticket behind it.
  3. A failed create. The marker is cleared at once only when the ticket system cannot have stored a ticket: it answered with a 4xx status (408 and 429 included), or the request never left (DNS failure, connection refused, any failure before the request was sent). The next attempt is scheduled with backoff. After any other failure (a 5xx, a timeout, a 2xx answer with an unreadable body or no ID, a shutdown or cancellation while the request was in flight) the marker stays set.
  4. A stuck marker is resolved by an admin, not looped on. While the marker is set the engine creates nothing for that PR and no lifecycle operation runs for it (the ticket is not known); it records that the creation is unconfirmed on the row, which the Problems view shows (§7.7). The engine does not look the ticket up itself. An admin searches the ticket project for a ticket carrying the line Release Ops key: <id> (the row's id) and then uses the clear action, POST /api/v1/update-tickets/{id}/clear-pending-marker (§7.6): it drops the marker together with the error and the retry, and the next event of the PR creates the ticket (step 1). The action is admin only because clearing a marker for a ticket that does exist makes a duplicate. A row that has its ticket stored, or whose marker is gone already, is refused with 409 and nothing changes. A timeout or 5xx therefore ends in a retry the admin decides on, never in a permanent error loop (the v1 gap: a marker with no way to clear it).
  5. Crash safety. The row and the marker are written before the call, and the link and the marker clear together after it. A crash between them leaves a marker, which stays until an admin resolves it (step 4).

Residual risk, stated: an admin who clears a marker without finding a ticket that exists (a search index that lags behind a ticket just stored) makes a duplicate. The key line in the description lets a person recognise it. The PR comment (§5.2.3) is reconciled separately: it looks for its own marker before posting.

5.2.3 The ticket link on the PR

The ticket link is a comment by the App's bot user on the PR, written by the engine after the link is stored (§5.2.2):

  • The comment starts with the hidden marker <!-- release-ops:ticket --> and contains the link to the ticket and its Release Ops state. Its text is fixed by Release Ops, not a template.
  • Upserted, not re-posted. When pr_comment_id is stored the comment is edited in place (PATCH /repos/{owner}/{repo}/issues/comments/{id}) whenever its body changes (a new state, a supersede); if GitHub answers 404 the comment is gone and one new comment is posted and its id stored. When no id is stored the PR's comments are listed first and a comment by the bot with the marker is adopted, so a crash between posting and storing cannot post twice. pr_comment_hash avoids an edit when nothing changed.
  • Never the PR body. Renovate owns the body and rewrites it (it hashes the body it would generate and replaces a body that differs), so nothing of Release Ops is ever written into it.
  • A comment write that fails is retried with backoff and does not hold back the ticket.
  • Assumption, to be confirmed on the first deployment (#232): Renovate does not edit or delete comments it did not write.

Not in v2.0

  • Ticket → PR. One direction only: nothing a person does to a ticket (closing, moving, commenting) acts on the PR.
  • No check run or commit status on the PR for the ticket; the comment is the only link.
  • No ticket-first mode: Release Ops does not inject prBodyNotes or a ticket key into Renovate's configuration, so Renovate opens a PR before any ticket exists.

5.5 Notifications (removed)

v2 has no notifications. Release Ops sends no email, no Slack, no Shoutrrr message and no webhook of its own: the ticket systems already notify on ticket creation and assignment, and GitHub notifies on PRs. The v1 notification_targets and monitored_repo_notifications tables, the Shoutrrr library, the /notifications page and the notification-target endpoints do not exist. The one signal not otherwise covered is failure, and it is surfaced three ways:

  • the Problems view (§7.7, §8.3): job errors, ticket creation errors, rate limits and lost App permissions;
  • /metrics (§7.8): failure counters, queue age and the rate-limit gauges and counters, with example alert rules in the customer documentation (#223);
  • /healthz and /readyz (§7.8): liveness, and readiness with a non-secret reason.

A generic error webhook for operators without Prometheus is not in v2.0 (§13).

5.6 Job run flow

The v1 poll run (one global run over every repository, guarded by a mutex) is replaced by one job per repository (§2.8):

  1. Enqueue. A trigger (§2.9) creates a queued job for the repository, adds to an existing queued one, or, while the repository's job is running, sets rerun_requested.
  2. Claim. A worker with a free slot long-polls (§2.1) and receives the next eligible job: highest priority first, then oldest, under the concurrency cap, the reserved slot and the one-job-per-repository rule. The job becomes running with a lease.
  3. Token. The worker asks for the installation token; the app mints it for the target repository, the preset repositories and the global config repository when one is configured (§2.2).
  4. Prepare and run. The worker fetches (or mounts) the global config and tools (§2.4), starts Renovate as the second Unix user with the environment of §2.2, and heartbeats. Renovate processes the whole repository.
  5. Result. The worker posts the outcome (§2.1). The app records it (succeeded or failed), ingests the report, passes the repository to the PR-state sync (reconcile, §5.1) and wakes the ticket engine (§5.2), and frees the repository.
  6. Follow-up. With rerun_requested set, the app enqueues one high-priority follow-up job. After a failure the job is retried with backoff (§2.8). A lease that expires without a result is reaped (§2.8).

5.7 Scheduling

There is no poll interval and no per-repository interval setting. Time-based work is fixed:

  • Safety net: hourly, a normal-priority job per eligible repository (§2.9).
  • Reconcile: installations and repositories, at start and hourly (§3.4, §2.11).
  • Redelivery of failed webhook deliveries: at start and every 15 minutes (§2.11).
  • PR reconcile: open bot PRs of every enabled repository, hourly with the safety net and after every job result (§5.1).
  • Ticket engine: woken by every PR write, and run periodically as a safety net for retries (interval: §2.12).
  • Retention: a daily pass deletes finished jobs older than JOB_HISTORY_RETENTION_DAYS (default 30 days) with their history (§4.6) and delivery records older than WEBHOOK_DELIVERY_RETENTION_DAYS (default 7 days, §2.10).
  • Reaper: expired leases (§2.8).
  • Polling fallback without WEBHOOK_URL (§2.11).
  • Admin "run now" per repository (§3.10) is an on-demand high-priority job.

5.8 Open questions of the update PR and ticket model

Not settled by the brief, the plan or the documentation; to be decided during implementation or by the maintainer:

  • Ticket-engine timings: the retry backoff (§2.12).
  • A reopened PR. A PR that goes from closed back to open keeps its ticket as it is: a ticket moved to won't do or superseded is not moved back, and no second ticket is created. Whether it should reopen the ticket is not decided.
  • PRs whose body Release Ops cannot read. A custom Renovate body template can leave a PR with no updates table; without a report entry it has no dependencies and so no ticket (§5.2). Whether such a PR should get a ticket without a dependency list is not decided.
  • Renovate and foreign comments (§5.2.3): that Renovate leaves the bot's comment alone is an assumption, confirmed on the first deployment.

Renovate image pin

The worker image is built FROM the pinned Renovate image (§2.3): the worker stage of the Dockerfile names ghcr.io/renovatebot/renovate:<tag>@sha256:<digest> literally, with no floating tag. Dependabot proposes bumps of the tag and digest together as pull requests; CI checks the pin, runs the new image against fixture repositories and runs a renovate_run job through release-ops worker in it. A bump pull request must also move ARG WORKER_RENOVATE_TAG in the Dockerfile and RenovateVersion in internal/buildinfo to the same version. There is no build argument that selects the base image: running a Renovate version other than the pinned one means editing the FROM line, at your own risk, because the report and log handling, and the global config handling, are tested against the pinned version only. The pin is a build-time fact, not a variable of a running container (the worker has no Docker socket and pulls no image).

10. Deployment

  • Two services, two images. The app image ghcr.io/{owner}/release-ops (Next.js + Go) and the worker image ghcr.io/{owner}/release-ops-worker (the pinned Renovate image plus the release-ops binary, §2.3). Both are released with the same tag, and upgraded together.
  • docker-compose.yml: service app and service worker. Only the app publishes a port (3000:3000); the internal listener (§2.1) and the worker publish none.
  • Volumes. The app has release-ops-data:/data (app.db, snapshots/). The worker has only a cache volume (the per-slot Renovate caches, §2.5) and no /data. No Docker socket is mounted anywhere.
  • App entrypoint: docker/entrypoint.sh — Go on 127.0.0.1:8080 plus the internal listener (pending migrations are applied to app.db before either listens) → Next on :3000. Worker entrypoint: release-ops worker.
  • Health probe of the app: GET /api/go/healthz or a dedicated Next route that proxies Go /healthz. The worker starts after the app and keeps asking for jobs until the app answers.
  • Without a public URL (NAT, home lab) leave WEBHOOK_URL unset: the instance runs in the degraded polling mode (§2.11). Exposing only /hooks/github and the UI (including the OAuth callback) is enough for the fast path.
  • Image publish via GitHub Actions — see §11 CI/CD.

Backup, restore & upgrade

All durable state is in app.db on the app's volume (the worker's cache volume is disposable) plus the two secrets that read it: keep APP_ENCRYPTION_KEY and SESSION_SECRET with every backup, because the App's private key and the integration credentials are unreadable without the encryption key (§4.8).

  • Backup. Because the database is in WAL mode (§4.9), copying app.db alone from a running app can miss committed data that still sits in app.db-wal. Use VACUUM INTO (a consistent copy while the app runs) or a volume snapshot that is atomic across app.db, app.db-wal and app.db-shm, or one taken with the app stopped.
  • Before an upgrade take a VACUUM INTO copy or a volume snapshot. The app also writes its own VACUUM INTO snapshot before it applies pending migrations (§4.0, /data/snapshots).
  • Restore. Stop both services first. A VACUUM INTO copy is a single file: delete the existing app.db-wal and app.db-shm on the volume, then put the copy in place as app.db. A volume snapshot is restored whole: put its app.db, app.db-wal and app.db-shm back together, and never delete the snapshot's WAL, which can hold committed data that is not in app.db. Then start the app, then the worker. Jobs that were running when the backup was taken have expired leases and are reaped (§2.8); webhook deliveries that failed while the app was down are redelivered at startup (§2.11).
  • Upgrade. Pull both images at the same tag, restart both. Migrations run at app start (§4.0).

11.5 Root VERSION & prepare-release.yml

Repo root: file VERSION — one line, semver without v prefix, e.g. 0.2.0.

Script scripts/ci/create-draft-release.mjs (or equivalent):

  1. fetch-depth: 0 checkout.
  2. Find last release tag: git tag --list 'v*' --sort=-v:refname (or last published release via gh).
  3. Read VERSION at HEAD vs. VERSION at tag commit.
  4. If HEAD is not semver-strictly greater → skip (no draft, no tag).
  5. On bump: create git tag v{VERSION} and push; draft GitHub release with title Release Ops v{VERSION}; notes = git log since last tag.

Tag format: v{X.Y.Z} (matches VERSION). No date-based release-YYYY-MM-DD — version comes from the file.

12. MVP Acceptance Criteria

Criterion 1 is the primary requirement of v2: the reason the product exists.

  1. Ticking a Renovate checkbox in a bot PR or in the Dependency Dashboard starts a job for that repository at most 10 seconds after the webhook arrives, measured across the app and worker; the PR or dashboard updates when Renovate finishes. Edits by the App's own bot and edits without an unchecked-to-checked transition start nothing (§2.9).
  2. After first-start setup (§3.2–§3.4), an admin can sign in with GitHub (§3.5); a viewer sees only their repositories (§3.9) in every list and detail of §7.5–§7.7, and 404 for any other.
  3. The webhook endpoint verifies the HMAC over the raw body, caps the body, deduplicates X-GitHub-Delivery and answers 202 (§2.10); failed deliveries are redelivered at startup and every 15 minutes; with WEBHOOK_URL unset the instance polls and is documented as degraded (§2.11).
  4. The queue runs one job per repository, honours the concurrency cap and its reserved high-priority slot, coalesces triggers with rerun_requested, reclaims expired leases and backs off with Retry-After (§2.8).
  5. docker compose up starts two services, the app and the worker; the worker has no database access, no data volume and no Docker socket (§2, §10).
  6. Update PR state comes from GitHub: pull_request webhooks and a reconcile that lists the open PRs authored by the App's bot user. A PR is a bot PR by author plus Renovate's body markers, never by branch prefix or title; a merge, a close and a supersede are recorded correctly, including after a missed webhook (§5.1).
  7. The dependencies of a PR are stored as a child list, enriched from the Renovate report with nullable columns and falling back to the PR body; a missing or unreadable report fails no job (§5.1, §4.5).
  8. An eligible update PR gets exactly one ticket listing all its dependencies, rendered from the project's templates. The ticket filter (update types, labels, skip automerged; default every non-automerged PR) is applied, and the ticket project is the repository's override or the installation's default (§5.2). Renovate's config-migration PR, onboarding PRs and PRs without dependencies get no ticket.
  9. The lifecycle follows the status_mapping of the ticket project: a new version of the same PR updates the ticket and adds a note; a PR replaced by a new PR supersedes the old ticket and links the new one; a merged PR moves its ticket to done; a PR closed unmerged moves it to won't do, and a replacement found later still supersedes that ticket. A ticket whose status was changed by hand is left alone (§5.2.1).
  10. Ticket creation is at-most-once: a pending marker is set before the create call and cleared by the write that stores the link, and a marker left by a timeout or 5xx is resolved by an admin's clear action, never by an endless error loop (§5.2.2, §7.6).
  11. The ticket link is one bot comment on the PR, edited and not re-posted, and nothing is written into the PR body (§5.2.3).
  12. Admin can create integrations for the three ticket kinds (kaneo, jira, linear); secrets never in API responses; the connection test per provider returns success or failure in the UI (§4.2, §6.2).
  13. Admin can create multiple ticket projects per ticket integration (Kaneo projects, Jira keys, Linear teams) with their own status_mapping, ticket filter and content templates (§4.3, §5.3, §5.4); the template variables of §5.4 render, .ReleaseNotes is truncated to 4,000 characters, and PR, dependency and release-note text is never executed as a template.
  14. Admin can pause and enable a repository, run a job now, set a repository's ticket project, and use "Enable repo" to open a renovate.json PR extending the configured preset; a viewer can do none of these (§7.5).
  15. The dashboard lists open and recently merged update PRs with repository, age, update type, ticket link and status, and a link to the repository's Dependency Dashboard; the Jobs page shows jobs with log excerpts and a Problems view with job errors, ticket creation errors, rate limits and lost App permissions. A viewer sees that a ticket operation is failing (ticket.hasError, a ticket_failed problem) but never its error text, which only an admin sees (§3.10, §7.6, §7.7, §8.3).
  16. The settings page shows the global Renovate config raw and read-only, the App and installation info and the role mapping; the About page names the pinned Renovate version with its AGPL-3.0 notice (§8.3).
  17. Job history is pruned JOB_HISTORY_RETENTION_DAYS after a job finished (default 30 days), and webhook delivery records WEBHOOK_DELIVERY_RETENTION_DAYS after they were received (default 7 days) (§4.6, §2.12).
  18. /metrics serves the metrics of §7.8 on METRICS_ADDR from the app and the worker, and answers 404 through the /api/go proxy.
  19. No v1 behaviour remains: no release polling, no baseline/skip/create decision, no source providers, no Shoutrrr and no notification targets, no poll endpoints or pages (§1, §5.5).
  20. At least one end-to-end test per ticket provider (Kaneo, Jira, Linear) in CI (fake or sandbox), and the update flow against a fake GitHub; no test contacts a live provider.
  21. Go + web tests green in CI; workflow layout per §11 CI/CD.
