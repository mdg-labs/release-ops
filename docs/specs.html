Release Ops

Self-hosted Service: überwacht GitHub-Releases für konfigurierte Repos und erstellt bei echten neuen Releases (nicht beim ersten Baseline-Sehen) Tickets in Phasical. Konfiguration, Integration-Credentials und Monitoring laufen über eine geschützte Web-UI (COSS). Worker und REST-API laufen in Go; Auth und UI in Next.js mit BetterAuth.

Version: Spec v2.1 (2026-08-06) — Multi-Provider MVP (GitHub/GitLab · Phasical/Jira/Linear).

1. Zweck & Nicht-Ziele

Zweck

  • Pollt in konfigurierbaren Intervallen das jeweils neueste stable Release pro konfiguriertem Projekt.
  • Sources (MVP): GitHub (releases/latest) und GitLab (releases/permalink/latest).
  • Speichert den zuletzt gesehenen Tag pro Projekt in SQLite.
  • Erstellt bei Tag-Wechsel (nach Baseline) ein Ticket im gewählten System.
  • Tickets (MVP): Phasical, Jira, Linear — pro Repo frei kombinierbar mit Source.
  • Zeigt Betriebsstatus in der UI: letzter Poll, Fehler, Projekt-Übersicht.

MVP-Nicht-Ziele

  • Kein Codeberg / Gitea / weitere Sources.
  • Kein Multi-User-RBAC (ein Admin reicht; alle eingeloggten User sind gleichberechtigt).
  • Kein öffentliches Sign-up (Admin-Account per Seed/CLI oder einmalig in UI).
  • Kein High-Availability / Horizontal Scaling.

3. Authentifizierung

BetterAuth (Next.js)

  • Plugin: better-auth mit SQLite-Adapter auf auth.db.
  • MVP-Provider: Email + Password only.
  • Plugin: jwt() — JWKS unter /api/auth/jwks (oder BetterAuth-Default).
  • disableSignUp: true nach Erst-Admin — oder Sign-up nur bis erster User existiert.

Go API Auth

  • Next.js Route apps/web/app/api/go/[...path]/route.ts holt Session-JWT via auth.api.getToken() und forwarded an Go mit Authorization: Bearer.
  • Go Middleware validiert JWT gegen BetterAuth JWKS (Cache Keys, Standard-JWT-Verify).
  • Alle /api/v1/* Endpoints erfordern gültiges JWT — außer optional GET /healthz für Container-Probes.

Kein Session-Cookie direkt an Go — nur JWT-Proxy-Pattern (vermeidet CORS/Cookie-SameSite-Probleme).

4.4 poll_runs & poll_run_events

Audit des Pollers. errors_json ist Array von { "repoId", "message" }.

4.5 Zeitstempel

Alle TEXT-Timestamps: RFC3339/ISO8601 UTC mit Millisekunden, z.B. 2026-08-06T12:00:00.000Z.

4.6 Credential-Verschlüsselung

  • Algorithmus: AES-256-GCM.
  • Key: APP_ENCRYPTION_KEY — 32 Bytes, hex-encoded (64 Zeichen).
  • Stored format: base64(nonce + ciphertext + tag) oder JSON { "v": 1, "data": "..." }.
  • Go entschlüsselt nur im Worker/API — niemals an Frontend senden außer „configured“ / Maskierung.
  • API gibt bei Integrations has_secret: true, nie den Secret-Wert.

5. Domänenlogik

5.1 Release-Entscheidung (pro Repo)

  1. baseline — last_known_tag ist NULL → Tag speichern, kein Ticket.
  2. skip — Tag identisch mit last_known_tag → nichts tun.
  3. create — Tag unterschiedlich → Ticket im gewählten System anlegen, last_known_tag aktualisieren.
  4. error — API-Fehler (außer „kein Release“) → last_error setzen, Run fortsetzen.

„Kein Release“: GitHub 404 auf /releases/latest; GitLab 404 auf latest-release-Endpoint — kein Error, nur kein Tag.

5.2 Ticket-Inhalt

Gemeinsam für alle Ticket-Provider:

FeldWert
titleRelease: {source_kind} {project_path} {tag}
descriptionMarkdown: Release-Name, URL, publishedAt

ticket_config pro ticket_kind

// phasical
{ "projectId": "...", "status": "ready", "priority": "medium" }

// jira
{ "projectKey": "DEV", "issueType": "Task", "priority": "Medium" }

// linear
{ "teamId": "...", "priority": 2, "stateId": "..." }  // priority 0–4, stateId optional

5.3 Poll-Run Ablauf

  1. Insert poll_runs status running.
  2. Für jedes enabled Repo: Source abfragen → Entscheidung → Event loggen.
  3. Run status: success (keine Errors), partial (einige Errors), failed (alle fehlgeschlagen oder kritischer Fehler).
  4. Kein paralleles Polling desselben Runs (Mutex / running-Guard).

5.4 Scheduler

Intervall aus app_settings.poll_interval_minutes. Zusätzlich: manueller Trigger via API/UI.

    Title       string

    CreateTicket(ctx context.Context, input TicketInput) (externalID string, err error)

6.1 Source: GitHub

  • GET https://api.github.com/repos/{projectPath}/releases/latest
  • Headers: Accept: application/vnd.github+json, X-GitHub-Api-Version: 2022-11-28, User-Agent: release-ops
  • Authorization: Bearer wenn Token in Integration
  • Mapping: tag_name→Tag, html_url→URL, published_at→PublishedAt

6.2 Source: GitLab

  • GET {base_url}/api/v4/projects/{urlencoded_path}/releases/permalink/latest
  • projectPath → URL-encode (/ → %2F)
  • Header: PRIVATE-TOKEN: {token}
  • Mapping: tag_name→Tag, _links.self oder assets.links→URL, released_at→PublishedAt
  • 404 = kein Release

6.3 Ticket: Phasical / Jira / Linear

Factory pro ticket_kind. Jeder Provider mappt TicketInput + ticket_config auf natives API-Format (§5.2).

Connectivity-Tests: GitHub/GitLab GET /user; Phasical lightweight GET; Jira GET /rest/api/3/myself; Linear GraphQL viewer.

10. Deployment

  • docker-compose.yml: Services web, worker, Volume release-ops-data:/data.
  • Worker startet Migrations (golang-migrate up) vor HTTP + Scheduler.
  • Web abhängig von Worker (healthz) für sauberen Start.
  • Einzelnes öffentliches Ingress auf web:3000.
  • CI: Go test/lint, web test/lint, Docker build push to GHCR.

11. MVP Acceptance Criteria

  1. Admin kann sich einloggen (Email/Password).
  2. Admin kann Integrationen für alle fünf kind-Werte anlegen; Secrets nie in API-Responses.
  3. Admin kann monitored Repo mit beliebiger Source/Ticket-Kombination anlegen (GitHub+Linear, GitLab+Jira, …).
  4. Integration-Test pro Provider liefert Erfolg/Fehler in UI.
  5. Erster Poll: baseline — kein Ticket, last_known_tag gesetzt.
  6. Poll ohne Release-Wechsel: skip.
  7. Neues Release: create — Ticket im gewählten System sichtbar.
  8. Mindestens ein End-to-End-Test pro Source (GitHub + GitLab) und pro Ticket-Provider (Phasical + Jira + Linear) in CI (mock oder Sandbox).
  9. Dashboard, manueller Poll, Settings-Intervall, docker compose up wie zuvor.
  10. Go + Web Tests grün in CI.

12. Post-MVP

  • Codeberg / Gitea / weitere Sources.
  • Per-Repo Poll-Intervall.
  • Release-Filter (Pre-Releases, Regex auf Tags).
  • Webhook statt Poll.
  • Multi-User mit Rollen.
  • OAuth/Social Login (COSS: p-button-38).
