Release Ops

Self-hosted service: monitors releases on GitHub, GitLab, Gitea, Forgejo, and Codeberg for configured repos and creates tickets in Phasical, Jira, or Linear when genuine new releases ship (not on the first baseline sighting). Ticket integrations support multiple project/team targets with their own status mapping; open tickets are superseded, merged, or skipped per policy. Notifications via Shoutrrr. Configuration, integration credentials, and monitoring run through a protected web UI (COSS). One container for self-hosting: Next.js (COSS UI) and Go (auth, REST API, polling) in the same image.

Version: Spec v2.8 (2026-08-07) — Multi-user invite-only auth · SMTP · rate limits · locked implementation defaults

1. Purpose & Non-goals

Purpose

  • Polls the respective latest stable release per configured project at configurable intervals.
  • Sources (MVP): GitHub, GitLab, Gitea, Forgejo, Codeberg — each via releases/latest (GitLab: permalink/latest; Gitea family: Gitea API v1).
  • Stores the last seen tag per project in SQLite.
  • Creates a ticket in the chosen system on tag change (after baseline).
  • Tickets (MVP): Phasical, Jira, Linear — freely combinable with source per repo.
  • Each ticket integration can have multiple project/team targets (ticket_projects) — each with its own open/done/cancelled/superseded mapping.
  • Idempotency with open tickets: default supersede; alternatively merge or skip_if_open.
  • Notifications to Shoutrrr targets (Slack, ntfy, …) on create, error, supersede.
  • Shows operational status in the UI: last poll, errors, project overview.

MVP non-goals

  • No additional sources (Bitbucket, Azure DevOps, …).
  • No RBAC — all logged-in users have equal permissions (no roles or per-resource ACLs).
  • No public self-registration — accounts only via invitation accept or bootstrap admin (BOOTSTRAP_ADMIN_* / seed-admin CLI on empty users).
  • Self-host with one Docker container — no multi-service Compose.

3. Authentication

Auth lives entirely in Go. Next.js is UI-only — login forms and API clients call Go through the same-origin proxy. One SQLite file (app.db), one writer process.

Session model (Go)

  • MVP: email + password only — no OAuth, no public sign-up.
  • Passwords: bcrypt (golang.org/x/crypto/bcrypt) stored in users.password_hash.
  • Sessions: server-side store in sessions table (e.g. github.com/alexedwards/scs/v2 with SQLite store).
  • Cookie: release_ops_session — HttpOnly, SameSite=Lax, Path=/, Secure when public URL is HTTPS.
  • Signing key: SESSION_SECRET env (32+ random bytes).
  • No JWT between Next and Go — browser sends session cookie; Next proxy forwards Cookie and passes through Set-Cookie on login/logout.

First admin bootstrap

  • When users is empty: create admin via CLI release-ops seed-admin --email … --password … or one-time env BOOTSTRAP_ADMIN_EMAIL + BOOTSTRAP_ADMIN_PASSWORD on first container start (then remove env).
  • No POST /api/v1/auth/register in MVP — bootstrap only.
  • All logged-in users have equal permissions (no RBAC).

Multi-user model (invite-only)

  • After bootstrap, additional accounts are created only via invitation accept — no POST /api/v1/auth/register and no public sign-up UI.
  • Any logged-in user can invite others, list users, revoke pending invitations, and remove other users.
  • Invitations return a one-time URL ({APP_PUBLIC_URL}/accept-invitation?token=…) for copy-link; optional SMTP email when configured (§9).
  • Password minimum: 8 characters (invite accept, reset, login unchanged).
  • Admin/bootstrap never sets another user’s password — invited users choose their own password on accept; existing users use forgot-password or self-service flows.

Self-service email change

  • Logged-in user requests change via POST /api/v1/users/me/email-change-request with newEmail and currentPassword.
  • Verification link is sent to the new email address (SMTP required for delivery; no link returned in API response).
  • Confirm via public POST /api/v1/auth/confirm-email-change with one-time token from the email link.
  • On confirm: update users.email, mark token used, revoke all other sessions for that user (current session remains valid).
  • Email-change tokens use password_reset_token_expiry_minutes from app_settings (§4.1).

User removal

  • DELETE /api/v1/users/{id} — any logged-in user may remove another user.
  • Forbidden: delete self; delete the last remaining user (instance must always have ≥1 user).
  • On delete: revoke all sessions for that user (DELETE FROM sessions WHERE user_id = ?) before deleting the users row.

Session revocation rules

  • Every successful login, invitation accept, and password reset sets sessions.user_id on the new session row (§4.0.1).
  • User delete: delete all sessions for that user_id.
  • Email change confirm: delete all sessions for that user_id except the current session token.
  • Logout: delete current session only (existing behaviour).
  • Index on sessions.user_id supports bulk revocation.

Protected routes

  • Go middleware: all /api/v1/* require valid session except the public auth paths listed in §7.0.
  • GET /healthz — no auth (container probe).
  • Next middleware: pages except public auth routes (§8.2) redirect to login when GET /api/go/api/v1/auth/session returns user: null.

4. Data model

Canonical SQL: schema.html (browser view) · db/schema.sql (source file). All tables in app.db (including auth).

4.0 Schema migrations (generated only)

Never hand-write migration SQL. Workflow:

  1. Edit db/schema.sql (canonical DDL — not under docs/).
  2. Run make migrate-diff name=<change> — scripts/migrate-diff.mjs uses SQLite sqldiff (free, bundled with sqlite3) to generate migrations/*.sql.
  3. Review generated .up.sql and .down.sql; commit both.
  4. Runtime apply: golang-migrate up in entrypoint (unchanged).

CI runs npm run db:check — fails if db/schema.sql drifts from applied migrations. Agents: see .cursor/rules/11-db-migrations.mdc.

4.7 Timestamps

All TEXT timestamps: RFC3339/ISO8601 UTC with milliseconds, e.g. 2026-08-06T12:00:00.000Z.

4.8 Credential encryption

  • Algorithm: AES-256-GCM.
  • Key: APP_ENCRYPTION_KEY — 32 bytes, hex-encoded (64 characters).
  • Stored format: base64(nonce + ciphertext + tag) — 12-byte random nonce prepended to ciphertext; entire blob base64-encoded in encrypted_payload / shoutrrr_url_encrypted.
  • Go decrypts credentials only in the Go process — never sent to frontend except “configured” / masking.
  • API returns has_secret: true for integrations, never the secret value.

5. Domain logic & Idempotency

5.1 Release decision (tag change)

  1. baseline — last_known_tag is NULL → store tag, no ticket.
  2. skip — tag identical to last_known_tag → do nothing.
  3. new tag — proceed to §5.2 (open ticket? policy?) → then create, supersede, merge, or skip_open.
  4. error — API error (except “no release”) → last_error, continue run.

“No release”: GitHub/GitLab/Gitea/Forgejo/Codeberg 404 on latest release — not an error.

Tag comparison: poll skip uses exact string equality between the fetched release tag and last_known_tag (no semver ordering). Provider tests may assert tag parsing separately; poll decisions never reorder tags.

5.2 Open ticket & idempotency

On a new tag, Go checks the linked ticket status (open_ticket_external_id) live, not only the local DB — the ticket may have been closed manually.

Status classification always via ticket_projects.status_mapping of the linked ticket project.

Live statusBehavior on new tag
in done or cancelledclear open_ticket_* → normal create
in openpolicy from ticket_projects.on_open_ticket_policy (§5.2.1)
unknown / API errorerror for repo; no new ticket

5.2.1 on_open_ticket_policy

PolicyActionPoll event
supersede (default)Old ticket → superseded status + comment; create new ticketsupersede + create
mergeUpdate existing ticket (title/description/tag); no second ticketmerge
skip_if_openNo ticket; optional notificationskip_open

Supersede comment (all providers): link to new release, old tag → new tag.

After successful create / supersede: update open_ticket_external_id and open_ticket_tag. After merge: only open_ticket_tag.

5.5 Notifications (Shoutrrr)

  • Library: github.com/containrrr/shoutrrr in the Go process — no custom Slack/Discord/Telegram integrations.
  • UI: Shoutrrr URL per target (e.g. slack://…, ntfy://…, generic://…), encrypted in DB.
  • Events: create, error, supersede (configurable per target).
  • After ticket actions and on poll errors: send to all matching targets (globally enabled, optional repo filter).

5.6 Poll run flow

  1. Insert poll_runs status running.
  2. For each enabled repo: query source → decision → log event.
  3. Run status: success (no errors), partial (some errors), failed (all failed or critical error).
  4. No parallel polling of the same run (mutex / running guard).

5.7 Scheduler

Interval from app_settings.poll_interval_minutes. Additionally: manual trigger via API/UI.

6.1 Source: GitHub

  • GET https://api.github.com/repos/{projectPath}/releases/latest
  • Headers: Accept: application/vnd.github+json, X-GitHub-Api-Version: 2022-11-28, User-Agent: release-ops
  • Authorization: Bearer when token in integration
  • Mapping: tag_name→Tag, html_url→URL, published_at→PublishedAt

6.2 Source: GitLab

  • GET {base_url}/api/v4/projects/{urlencoded_path}/releases/permalink/latest
  • projectPath → URL-encode (/ → %2F)
  • Header: PRIVATE-TOKEN: {token}
  • Mapping: tag_name→Tag, _links.self or assets.links→URL, released_at→PublishedAt
  • 404 = no release

6.3 Source: Gitea / Forgejo / Codeberg (Gitea API)

Gitea, Forgejo, and Codeberg share the same REST API (/api/v1). Go implementation: one GiteaCompatibleSource client; kind controls default base_url and UI label.

11. CI/CD (GitHub Actions)

Same pattern as slugbase, pipewatch, and dispatch-one: branch/event entrypoints call reusable workflows (workflow_call). No monolithic workflow per branch.

11.1 Branch model

BranchTriggerAfter successful CI
devPushBuild + push GHCR: nightly + {short_sha}
mainPushprepare-release — draft release + git tag only on VERSION bump
PRpull_requestCI only — no images, no release
Releaserelease: publishedBuild + push GHCR: latest + release version tag

Feature branches: PR against dev or main. Integration runs via dev; main is the release track (protected).

11.2 Workflow layout (.github/workflows/)

FileTypeTask
pr.ymlEntrypointPR → calls ci.yml
dev.ymlEntrypointPush dev → ci.yml → build-and-push-image.yml
main.ymlEntrypointPush main → ci.yml → prepare-release.yml
release.ymlEntrypointrelease: published → build-and-push-image.yml

build-and-push-image.ymlReusableOne image release-ops → GHCR

Entrypoints set concurrency per branch/release (cancel-in-progress: true except release publish). Reusable workflows are only invoked via uses: ./.github/workflows/… — no direct on: push.

pr.yml

  ci:
    uses: ./.github/workflows/ci.yml
    secrets: inherit

dev.yml

on:
  push:
    branches: [dev]
  workflow_dispatch:

jobs:
  ci:
    uses: ./.github/workflows/ci.yml
    secrets: inherit

  meta:
  # short_sha = GITHUB_SHA first 7 chars

  push-image:
    needs: [ci, meta]
    if: needs.ci.result == 'success'

main.yml

on:
  push:
    branches: [main]
  workflow_dispatch:

jobs:
  ci:
    uses: ./.github/workflows/ci.yml
    secrets: inherit

  prepare-release:
    needs: [ci]
    if: needs.ci.result == 'success'
    permissions:
      contents: write
    uses: ./.github/workflows/prepare-release.yml
    secrets: inherit

No image build on main push — production images only on release: published (like slugbase CE release flow).

release.yml

    with:
      ref: ${{ github.event.release.target_commitish }}
      tags: |
        latest
        ${{ github.event.release.tag_name }}

11.5 Root VERSION & prepare-release.yml

Repo root: file VERSION — one line, semver without v prefix, e.g. 0.2.0.

Script scripts/ci/create-draft-release.mjs (or equivalent):

  1. fetch-depth: 0 checkout.
  2. Find last release tag: git tag --list 'v*' --sort=-v:refname (or last published release via gh).
  3. Read VERSION at HEAD vs. VERSION at tag commit.
  4. If HEAD is not semver-strictly greater → skip (no draft, no tag).
  5. On bump: create git tag v{VERSION} and push; draft GitHub release with title Release Ops v{VERSION}; notes = git log since last tag.

Tag format: v{X.Y.Z} (matches VERSION). No date-based release-YYYY-MM-DD — version comes from the file.

11.7 MVP CI requirements

  • Workflow files as in §11.2 present; reusable workflows have no own on: push.
  • PR and push to dev/main block on CI failure.
  • dev push produces an image with nightly + SHA after CI.
  • main push with increased VERSION creates draft release + v* tag; without bump no release artifact.
  • Published release pushes one image with latest + version tag.

12. MVP Acceptance Criteria

  1. Admin can log in (email/password).
  2. Admin can create integrations for all eight kind values; secrets never in API responses.
  3. Admin can create multiple ticket projects per ticket integration (Phasical projects, Jira keys, Linear teams) with their own status_mapping and on_open_ticket_policy.
  4. Admin can create monitored repo with any source/ticket-project combination (e.g. Codeberg+Phasical, Forgejo+Jira, Gitea+Linear).
  5. Integration test per provider returns success/failure in UI.
  6. First poll: baseline — no ticket, last_known_tag set.
  7. Poll without release change: skip.
  8. New release, no open ticket (or done/cancelled): create — ticket visible in target system.
  9. New release, open ticket, policy supersede: old ticket → superseded status + comment; new ticket created; tickets_superseded incremented.
  10. Policies merge and skip_if_open work as in §5.2.1.
  11. Status mapping is applied per ticket project (different open/done values per Phasical project, Jira key, Linear team).
  12. Admin can create and test Shoutrrr notification targets; events on create/error/supersede.
  13. At least one end-to-end test per MVP source (GitHub, GitLab, Gitea, Forgejo, Codeberg) and per ticket provider (Phasical, Jira, Linear) in CI (mock or sandbox).
  14. Dashboard, manual poll, settings interval; docker compose up with one service.
  15. Go + web tests green in CI; workflow layout per §11 CI/CD.
