<p class="lede">
    Self-hosted service: monitors releases on GitHub, GitLab, Gitea, Forgejo, and Codeberg for configured repos and creates tickets in Phasical, Jira, or Linear when
    <em>genuine</em> new releases ship (not on the first baseline sighting). Ticket integrations support multiple project/team targets with their own status mapping; open tickets are
    superseded, merged, or skipped per policy.
    Notifications via Shoutrrr.
    Configuration, integration credentials, and monitoring run through a protected web UI (COSS).
    <strong>One container</strong> for self-hosting: Next.js (COSS UI) and Go (auth, REST API, polling) in the same image.
  </p>

  <h2 id="purpose">1. Purpose &amp; Non-goals</h2>
  <h3>Purpose</h3>
  <ul>
    <li>Polls the respective latest <strong>stable</strong> release per configured project at configurable intervals.</li>
    <li><strong>Sources (MVP):</strong> GitHub, GitLab, Gitea, Forgejo, Codeberg — each via <code>releases/latest</code> (GitLab: <code>permalink/latest</code>; Gitea family: Gitea API v1).</li>
    <li>Stores the last seen tag per project in SQLite.</li>
    <li>Creates a ticket in the chosen system on tag change (after baseline).</li>
    <li><strong>Tickets (MVP):</strong> Phasical, Jira, Linear — freely combinable with source per repo.</li>
    <li>Each ticket integration can have <strong>multiple project/team targets</strong> (<code>ticket_projects</code>) — each with its own open/done/cancelled/superseded mapping.</li>
    <li>Idempotency with open tickets: default <code>supersede</code>; alternatively <code>merge</code> or <code>skip_if_open</code>.</li>
    <li>Notifications to Shoutrrr targets (Slack, ntfy, …) on create, error, supersede.</li>
    <li>Shows operational status in the UI: last poll, errors, project overview.</li>
  </ul>
  <h3>MVP non-goals</h3>
  <ul>
    <li>No additional sources (Bitbucket, Azure DevOps, …).</li>
    <li>No multi-user RBAC (one admin is enough; all logged-in users have equal permissions).</li>
    <li>No public sign-up — admin via <code>BOOTSTRAP_ADMIN_*</code> env on first start or <code>seed-admin</code> CLI only (no in-app registration or setup wizard).</li>
    <li>Self-host with <strong>one</strong> Docker container — no multi-service Compose.</li>
  </ul>

  <h2 id="architecture">2. Architecture</h2>
  <p>Self-host target: <strong>one container</strong>, <strong>one public port</strong> (<code>3000</code>). No separate <code>web</code> + <code>worker</code> in Compose/Coolify.</p>
  
```
┌──────────────────────────────────────────────────────────────┐
│  Browser  ──►  :3000  release-ops Container                  │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ Next.js (apps/web) — public HTTP                         │  │
│  │   ├─ UI (COSS)                                          │  │
│  │   └─ /api/go/*    Proxy (cookies) ──► Go (127.0.0.1:8080)   │  │
│  │ Go (cmd/server) — container-only, not exposed           │  │
│  │   ├─ Auth (session cookie) + REST /api/v1/*           │  │
│  │   ├─ Poll scheduler                                     │  │
│  │   └─ app.db (SQLite — users, sessions, app data)        │  │
│  └────────────────────────────────────────────────────────┘  │
│  Volume: /data  (app.db)                                     │
└──────────────────────────────────────────────────────────────┘
          │
          ▼
   GitHub / GitLab / Gitea / Forgejo / Codeberg
          │
          ▼
   Phasical / Jira / Linear  ·  Shoutrrr (Notifications)
```

  <table>
    <tr><th>Component</th><th>Bind</th><th>Responsibility</th></tr>
    <tr><td>Next.js</td><td><code>0.0.0.0:$&#123;PORT&#125;</code> (default 3000)</td><td>COSS UI, HTTP proxy to Go (forwards <code>Cookie</code> / <code>Set-Cookie</code>)</td></tr>

  <h2 id="auth">3. Authentication</h2>
  <p>Auth lives entirely in <strong>Go</strong>. Next.js is UI-only — login forms and API clients call Go through the same-origin proxy. One SQLite file (<code>app.db</code>), one writer process.</p>
  <h3>Session model (Go)</h3>
  <ul>
    <li>MVP: <strong>email + password</strong> only — no OAuth, no public sign-up.</li>
    <li>Passwords: <code>bcrypt</code> (<code>golang.org/x/crypto/bcrypt</code>) stored in <code>users.password_hash</code>.</li>
    <li>Sessions: server-side store in <code>sessions</code> table (e.g. <code>github.com/alexedwards/scs/v2</code> with SQLite store).</li>
    <li>Cookie: <code>release_ops_session</code> — <code>HttpOnly</code>, <code>SameSite=Lax</code>, <code>Path=/</code>, <code>Secure</code> when public URL is HTTPS.</li>
    <li>Signing key: <code>SESSION_SECRET</code> env (32+ random bytes).</li>
    <li>No JWT between Next and Go — browser sends session cookie; Next proxy forwards <code>Cookie</code> and passes through <code>Set-Cookie</code> on login/logout.</li>
  </ul>
  <h3>First admin bootstrap</h3>
  <ul>
    <li>When <code>users</code> is empty: create admin via CLI <code>release-ops seed-admin --email … --password …</code> <strong>or</strong> one-time env <code>BOOTSTRAP_ADMIN_EMAIL</code> + <code>BOOTSTRAP_ADMIN_PASSWORD</code> on first container start (then remove env).</li>
    <li>No <code>POST /api/v1/auth/register</code> in MVP — bootstrap only.</li>
    <li>All logged-in users have equal permissions (no RBAC).</li>
  </ul>
  <h3>Protected routes</h3>
  <ul>
    <li>Go middleware: all <code>/api/v1/*</code> require valid session except <code>POST /api/v1/auth/login</code> and <code>GET /api/v1/auth/session</code>.</li>
    <li><code>GET /healthz</code> — no auth (container probe).</li>
    <li>Next middleware: pages except <code>/login</code> redirect to login when <code>GET /api/go/api/v1/auth/session</code> returns <code>user: null</code>.</li>
  </ul>

  <h2 id="schema">4. Data model</h2>
  <p>Canonical SQL: <a href="/schema/">schema.html</a> (browser view) · <a href="https://github.com/mdg-labs/release-ops/blob/dev/db/schema.sql"><code>db/schema.sql</code></a> (source file). All tables in <code>app.db</code> (including auth).</p>

  <h3 id="schema-migrations">4.0 Schema migrations (generated only)</h3>
  <p><strong>Never hand-write</strong> migration SQL. Workflow:</p>
  <ol>
    <li>Edit <code>db/schema.sql</code> (canonical DDL — not under <code>docs/</code>).</li>
    <li>Run <code>make migrate-diff name=&lt;change&gt;</code> — <code>scripts/migrate-diff.mjs</code> uses SQLite <code>sqldiff</code> (free, bundled with <code>sqlite3</code>) to generate <code>migrations/*.sql</code>.</li>
    <li>Review generated <code>.up.sql</code> and <code>.down.sql</code>; commit both.</li>
    <li>Runtime apply: <code>golang-migrate up</code> in entrypoint (unchanged).</li>
  </ol>
  <p>CI runs <code>npm run db:check</code> — fails if <code>db/schema.sql</code> drifts from applied migrations. Agents: see <code>.cursor/rules/11-db-migrations.mdc</code>.</p>

  <h3>4.6 <code>poll_runs</code> &amp; <code>poll_run_events</code></h3>
  <p>Poller audit. <code>errors_json</code>: array <code>&#123; "repoId", "message" &#125;</code>. <code>tickets_superseded</code> counts supersede actions.</p>
  <p><code>poll_run_events.action</code>:</p>
  <ul>
    <li><code>baseline</code> · <code>skip</code> · <code>create</code> · <code>supersede</code> · <code>merge</code> · <code>skip_open</code> · <code>error</code></li>
  </ul>

  <h3>4.7 Timestamps</h3>
  <p>All <code>TEXT</code> timestamps: RFC3339/ISO8601 UTC with milliseconds, e.g. <code>2026-08-06T12:00:00.000Z</code>.</p>

  <h3>4.8 Credential encryption</h3>
  <ul>
    <li>Algorithm: AES-256-GCM.</li>
    <li>Key: <code>APP_ENCRYPTION_KEY</code> — 32 bytes, hex-encoded (64 characters).</li>
    <li>Stored format: <code>base64(nonce + ciphertext + tag)</code> — 12-byte random nonce prepended to ciphertext; entire blob base64-encoded in <code>encrypted_payload</code> / <code>shoutrrr_url_encrypted</code>.</li>
    <li>Go decrypts credentials only in the Go process — never sent to frontend except “configured” / masking.</li>
    <li>API returns <code>has_secret: true</code> for integrations, never the secret value.</li>
  </ul>

  <h2 id="domain">5. Domain logic &amp; Idempotency</h2>
  <h3>5.1 Release decision (tag change)</h3>
  <ol>
    <li><strong>baseline</strong> — <code>last_known_tag</code> is NULL → store tag, no ticket.</li>
    <li><strong>skip</strong> — tag identical to <code>last_known_tag</code> → do nothing.</li>
    <li><strong>new tag</strong> — proceed to §5.2 (open ticket? policy?) → then <code>create</code>, <code>supersede</code>, <code>merge</code>, or <code>skip_open</code>.</li>
    <li><strong>error</strong> — API error (except “no release”) → <code>last_error</code>, continue run.</li>
  </ol>
  <p>“No release”: GitHub/GitLab/Gitea/Forgejo/Codeberg 404 on latest release — not an error.</p>
  <p><strong>Tag comparison:</strong> poll skip uses <strong>exact string equality</strong> between the fetched release tag and <code>last_known_tag</code> (no semver ordering). Provider tests may assert tag parsing separately; poll decisions never reorder tags.</p>

  <h3>5.2 Open ticket &amp; idempotency</h3>
  <p>On a new tag, Go checks the linked ticket status (<code>open_ticket_external_id</code>) <strong>live</strong>, not only the local DB — the ticket may have been closed manually.</p>
  <p>Status classification always via <code>ticket_projects.status_mapping</code> of the linked ticket project.</p>
  <table>
    <tr><th>Live status</th><th>Behavior on new tag</th></tr>
    <tr><td>in <code>done</code> or <code>cancelled</code></td><td>clear <code>open_ticket_*</code> → normal <strong>create</strong></td></tr>
    <tr><td>in <code>open</code></td><td>policy from <code>ticket_projects.on_open_ticket_policy</code> (§5.2.1)</td></tr>
    <tr><td>unknown / API error</td><td><code>error</code> for repo; no new ticket</td></tr>
  </table>

  <h4>5.2.1 <code>on_open_ticket_policy</code></h4>
  <table>
    <tr><th>Policy</th><th>Action</th><th>Poll event</th></tr>
    <tr><td><code>supersede</code> (default)</td><td>Old ticket → <code>superseded</code> status + comment; create new ticket</td><td><code>supersede</code> + <code>create</code></td></tr>
    <tr><td><code>merge</code></td><td>Update existing ticket (title/description/tag); no second ticket</td><td><code>merge</code></td></tr>
    <tr><td><code>skip_if_open</code></td><td>No ticket; optional notification</td><td><code>skip_open</code></td></tr>
  </table>
  <p>Supersede comment (all providers): link to new release, old tag → new tag.</p>
  <p>After successful <code>create</code> / <code>supersede</code>: update <code>open_ticket_external_id</code> and <code>open_ticket_tag</code>. After <code>merge</code>: only <code>open_ticket_tag</code>.</p>

  <h3 id="ticket-projects">5.3 Ticket projects &amp; status mapping</h3>
  <p>UI flow: create integration (credentials) → define <strong>ticket projects</strong> below → monitored repo selects a <code>ticket_project_id</code>.</p>

  <h4><code>create_config</code> (when creating a ticket)</h4>
  
```

&#123; "status": "ready", "priority": "medium" &#125;

// jira — external_project_id = projectKey
&#123; "issueType": "Task", "priority": "Medium", "initialStatus": "To Do" &#125;

// linear — external_project_id = teamId
&#123; "priority": 2, "stateId": "..." &#125;
```


  <h4><code>status_mapping</code> (per project — required)</h4>
  <p>Each ticket project defines its own mapping. Values are provider-native IDs/slugs/names.</p>
  
```
&#123;
  "open": ["ready", "in-progress", "in-review"],
  "done": ["done"],
  "cancelled": ["cancelled", "canceled"],
  "superseded": "cancelled"
&#125;
```

  <table>
    <tr><th>Key</th><th>Type</th><th>Description</th></tr>
    <tr><td><code>open</code></td><td>array</td><td>Status counts as “still open” — no new ticket without policy</td></tr>
    <tr><td><code>done</code></td><td>array</td><td>Completed — next release creates a fresh ticket</td></tr>
    <tr><td><code>cancelled</code></td><td>array</td><td>Cancelled — treat like done</td></tr>
    <tr><td><code>superseded</code></td><td>string</td><td>Target status for policy <code>supersede</code> (single value)</td></tr>
  </table>

  <h4>Provider notes</h4>
  <table>
    <tr><th>Provider</th><th><code>external_project_id</code></th><th>Status values in mapping</th></tr>
    <tr><td>Phasical</td><td><code>projectId</code></td><td>Board column slugs (<code>ready</code>, <code>in-progress</code>, …) — <strong>different per project</strong></td></tr>

  <h3 id="notifications">5.5 Notifications (Shoutrrr)</h3>
  <ul>
    <li>Library: <code>github.com/containrrr/shoutrrr</code> in the Go process — no custom Slack/Discord/Telegram integrations.</li>
    <li>UI: Shoutrrr URL per target (e.g. <code>slack://…</code>, <code>ntfy://…</code>, <code>generic://…</code>), encrypted in DB.</li>
    <li>Events: <code>create</code>, <code>error</code>, <code>supersede</code> (configurable per target).</li>
    <li>After ticket actions and on poll errors: send to all matching targets (globally enabled, optional repo filter).</li>
  </ul>

  <h3>5.6 Poll run flow</h3>
  <ol>
    <li>Insert <code>poll_runs</code> status <code>running</code>.</li>
    <li>For each <code>enabled</code> repo: query source → decision → log event.</li>
    <li>Run status: <code>success</code> (no errors), <code>partial</code> (some errors), <code>failed</code> (all failed or critical error).</li>
    <li>No parallel polling of the same run (mutex / <code>running</code> guard).</li>
  </ol>

  <h3>5.7 Scheduler</h3>
  <p>Interval from <code>app_settings.poll_interval_minutes</code>. Additionally: manual trigger via API/UI.</p>

  <h3>6.2 Source: GitLab</h3>
  <ul>
    <li><code>GET &#123;base_url&#125;/api/v4/projects/&#123;urlencoded_path&#125;/releases/permalink/latest</code></li>

  <h3>6.3 Source: Gitea / Forgejo / Codeberg (Gitea API)</h3>
  <p>Gitea, Forgejo, and Codeberg share the same REST API (<code>/api/v1</code>). Go implementation: one <code>GiteaCompatibleSource</code> client; <code>kind</code> controls default <code>base_url</code> and UI label.</p>
  <table>
    <tr><th>kind</th><th>Default <code>base_url</code></th><th><code>source_integration_id</code></th></tr>

    <tr><td><code>codeberg</code></td><td><code>https://codeberg.org</code> (fixed)</td><td>optional (token recommended)</td></tr>
  </table>
  <ul>
    <li><code>GET &#123;base_url&#125;/api/v1/repos/&#123;owner&#125;/&#123;repo&#125;/releases/latest</code></li>
    <li><code>projectPath</code> = <code>owner/repo</code> (like GitHub)</li>
    <li>Header with token: <code>Authorization: token &#123;token&#125;</code> (Gitea standard)</li>
    <li>Mapping: <code>tag_name</code>→<code>Tag</code>, <code>html_url</code>→<code>URL</code>, <code>published_at</code>→<code>PublishedAt</code></li>

  <h2 id="deployment">10. Deployment</h2>
  <ul>
    <li><strong>One image</strong> <code>ghcr.io/&#123;owner&#125;/release-ops</code> — no separate <code>-web</code> / <code>-worker</code> image.</li>
    <li><code>docker-compose.yml</code>: <strong>one</strong> service <code>release-ops</code>, volume <code>release-ops-data:/data</code>, port <code>3000:3000</code>.</li>
    <li><code>Dockerfile</code> multi-stage: Next standalone build + Go binary + shared runtime layer with <code>docker/entrypoint.sh</code>.</li>
    <li>Entrypoint: <code>golang-migrate up</code> on <code>app.db</code> → Go on <code>127.0.0.1:8080</code> → Next on <code>:3000</code>.</li>
    <li>Health probe: <code>GET /api/go/healthz</code> or dedicated Next route that proxies Go <code>/healthz</code> — no second service.</li>
    <li>Coolify / simple self-host: one container, one URL, one volume.</li>
    <li>Image publish via GitHub Actions — see <a href="#ci">§11 CI/CD</a>.</li>
  </ul>

  <h2 id="ci">11. CI/CD (GitHub Actions)</h2>
  <p>
    Same pattern as <code>slugbase</code>, <code>pipewatch</code>, and <code>dispatch-one</code>:
    <strong>branch/event entrypoints</strong> call <strong>reusable workflows</strong> (<code>workflow_call</code>).
    No monolithic workflow per branch.
  </p>

  <h3>11.1 Branch model</h3>
  <table>
    <tr><th>Branch</th><th>Trigger</th><th>After successful CI</th></tr>
    <tr><td><code>dev</code></td><td>Push</td><td>Build + push GHCR: <code>nightly</code> + <code>&#123;short_sha&#125;</code></td></tr>
    <tr><td><code>main</code></td><td>Push</td><td><code>prepare-release</code> — draft release + git tag only on <code>VERSION</code> bump</td></tr>
    <tr><td>PR</td><td><code>pull_request</code></td><td>CI only — no images, no release</td></tr>
    <tr><td>Release</td><td><code>release: published</code></td><td>Build + push GHCR: <code>latest</code> + release version tag</td></tr>
  </table>
  <p>Feature branches: PR against <code>dev</code> or <code>main</code>. Integration runs via <code>dev</code>; <code>main</code> is the release track (protected).</p>

  <h3>11.2 Workflow layout (<code>.github/workflows/</code>)</h3>
  <table>
    <tr><th>File</th><th>Type</th><th>Task</th></tr>
    <tr><td><code>pr.yml</code></td><td>Entrypoint</td><td>PR → calls <code>ci.yml</code></td></tr>
    <tr><td><code>dev.yml</code></td><td>Entrypoint</td><td>Push <code>dev</code> → <code>ci.yml</code> → <code>build-and-push-image.yml</code></td></tr>
    <tr><td><code>main.yml</code></td><td>Entrypoint</td><td>Push <code>main</code> → <code>ci.yml</code> → <code>prepare-release.yml</code></td></tr>
    <tr><td><code>release.yml</code></td><td>Entrypoint</td><td><code>release: published</code> → <code>build-and-push-image.yml</code></td></tr>
    <tr><td><code>ci.yml</code></td><td>Reusable</td><td>CI gate — <code>workflow_call</code> only</td></tr>
    <tr><td><code>prepare-release.yml</code></td><td>Reusable</td><td>Draft release + git tag on version bump</td></tr>
    <tr><td><code>build-and-push-image.yml</code></td><td>Reusable</td><td>One image <code>release-ops</code> → GHCR</td></tr>
  </table>
  <p>Entrypoints set <code>concurrency</code> per branch/release (<code>cancel-in-progress: true</code> except release publish). Reusable workflows are only invoked via <code>uses: ./.github/workflows/…</code> — no direct <code>on: push</code>.</p>

  <h3>11.3 Entrypoint details</h3>
  <h4><code>pr.yml</code></h4>
  
```
on: pull_request
jobs:
  ci:
    uses: ./.github/workflows/ci.yml
    secrets: inherit
```


  <h4><code>dev.yml</code></h4>
  
```
on:
  push:
    branches: [dev]
  workflow_dispatch:

jobs:
  ci:
    uses: ./.github/workflows/ci.yml
    secrets: inherit

  meta:
  # short_sha = GITHUB_SHA first 7 chars

  push-image:
    needs: [ci, meta]
    if: needs.ci.result == 'success'
    uses: ./.github/workflows/build-and-push-image.yml
    with:
      tags: |
        nightly
        $&#123;&#123; needs.meta.outputs.short_sha &#125;&#125;
```


  <h4><code>main.yml</code></h4>
  
```
on:
  push:
    branches: [main]
  workflow_dispatch:

jobs:
  ci:
    uses: ./.github/workflows/ci.yml
    secrets: inherit

  prepare-release:
    needs: [ci]
    if: needs.ci.result == 'success'
    permissions:
      contents: write
    uses: ./.github/workflows/prepare-release.yml
    secrets: inherit
```

  <p>No image build on <code>main</code> push — production images only on <code>release: published</code> (like slugbase CE release flow).</p>

  <h4><code>release.yml</code></h4>
  
```
on:
  release:
    types: [published]

jobs:
  push-image:
    uses: ./.github/workflows/build-and-push-image.yml
    with:
      ref: $&#123;&#123; github.event.release.target_commitish &#125;&#125;
      tags: |
        latest
        $&#123;&#123; github.event.release.tag_name &#125;&#125;
```


  <h3>11.4 Reusable <code>ci.yml</code></h3>
  <p>Parallel jobs (similar to pipewatch/slugbase):</p>
  <table>
    <tr><th>Job</th><th>Worker (Go)</th><th>Web (Next.js)</th></tr>
    <tr><td>lint</td><td><code>golangci-lint run</code></td><td><code>npm run lint</code></td></tr>
    <tr><td>test</td><td><code>go test ./...</code></td><td><code>npm test</code></td></tr>
    <tr><td>typecheck</td><td><code>go vet</code> / optional staticcheck</td><td><code>npm run typecheck</code></td></tr>
    <tr><td>build</td><td><code>go build -o /dev/null ./cmd/server</code></td><td><code>npm run build</code> (production)</td></tr>
    <tr><td>db</td><td><code>npm run db:check</code> (schema ↔ migrations via <code>sqldiff</code>)</td><td>—</td></tr>
  </table>
  <p>All jobs must be green before downstream jobs (images / release) run. No <code>--no-verify</code> in CI.</p>

  <h3>11.5 Root <code>VERSION</code> &amp; <code>prepare-release.yml</code></h3>
  <p>Repo root: file <code>VERSION</code> — one line, semver without <code>v</code> prefix, e.g. <code>0.2.0</code>.</p>
  <p>Script <code>scripts/ci/create-draft-release.mjs</code> (or equivalent):</p>
  <ol>
    <li><code>fetch-depth: 0</code> checkout.</li>
    <li>Find last release tag: <code>git tag --list 'v*' --sort=-v:refname</code> (or last published release via <code>gh</code>).</li>
    <li>Read <code>VERSION</code> at <code>HEAD</code> vs. <code>VERSION</code> at tag commit.</li>
    <li>If <code>HEAD</code> is not semver-strictly greater → <strong>skip</strong> (no draft, no tag).</li>
    <li>On bump: create git tag <code>v&#123;VERSION&#125;</code> and push; draft GitHub release with title <code>Release Ops v&#123;VERSION&#125;</code>; notes = <code>git log</code> since last tag.</li>
  </ol>
  <p>Tag format: <code>v&#123;X.Y.Z&#125;</code> (matches <code>VERSION</code>). No date-based <code>release-YYYY-MM-DD</code> — version comes from the file.</p>

  <h3>11.6 GHCR image &amp; tags</h3>
  <table>
    <tr><th>Image</th><th>Registry</th><th>Build</th></tr>
    <tr><td><code>ghcr.io/&#123;owner&#125;/release-ops</code></td><td>GHCR</td><td>Root <code>Dockerfile</code> — Next + Go in the same image</td></tr>
  </table>
  <table>
    <tr><th>Event</th><th>Tags</th></tr>
    <tr><td>Push <code>dev</code> (CI green)</td><td><code>nightly</code>, <code>&#123;short_sha&#125;</code> (7 chars)</td></tr>
    <tr><td>Release <code>published</code></td><td><code>latest</code>, <code>v&#123;X.Y.Z&#125;</code> (= release <code>tag_name</code>)</td></tr>
  </table>
  <p>Auth: <code>docker/login-action</code> with <code>ghcr.io</code>, <code>username: $&#123;&#123; github.actor &#125;&#125;</code>, <code>password: $&#123;&#123; secrets.GITHUB_TOKEN &#125;&#125;</code>, job <code>permissions: packages: write</code>.</p>
  <p>Reusable <code>build-and-push-image.yml</code> inputs:</p>
  
```
workflow_call:
  inputs:
    tags:        # newline-separated (nightly, abc1234, latest, v0.2.0)
      required: true
    ref:         # optional checkout ref
      default: ""
```

  <p>Build: Docker Buildx, registry cache (<code>ghcr.io/&#123;owner&#125;/release-ops:buildcache</code>), no runtime secret in image.</p>

  <h3>11.7 MVP CI requirements</h3>
  <ul>
    <li>Workflow files as in §11.2 present; reusable workflows have no own <code>on: push</code>.</li>
    <li>PR and push to <code>dev</code>/<code>main</code> block on CI failure.</li>
    <li><code>dev</code> push produces an image with <code>nightly</code> + SHA after CI.</li>
    <li><code>main</code> push with increased <code>VERSION</code> creates draft release + <code>v*</code> tag; without bump no release artifact.</li>
    <li>Published release pushes <strong>one</strong> image with <code>latest</code> + version tag.</li>
  </ul>

  <h2 id="mvp">12. MVP Acceptance Criteria</h2>
  <ol>
    <li>Admin can log in (email/password).</li>
    <li>Admin can create integrations for all eight <code>kind</code> values; secrets never in API responses.</li>
    <li>Admin can create multiple <strong>ticket projects</strong> per ticket integration (Phasical projects, Jira keys, Linear teams) with their own <code>status_mapping</code> and <code>on_open_ticket_policy</code>.</li>
    <li>Admin can create monitored repo with any source/ticket-project combination (e.g. Codeberg+Phasical, Forgejo+Jira, Gitea+Linear).</li>
    <li>Integration test per provider returns success/failure in UI.</li>
    <li>First poll: <strong>baseline</strong> — no ticket, <code>last_known_tag</code> set.</li>
    <li>Poll without release change: <strong>skip</strong>.</li>
    <li>New release, no open ticket (or done/cancelled): <strong>create</strong> — ticket visible in target system.</li>
    <li>New release, open ticket, policy <code>supersede</code>: old ticket → superseded status + comment; new ticket created; <code>tickets_superseded</code> incremented.</li>
    <li>Policies <code>merge</code> and <code>skip_if_open</code> work as in §5.2.1.</li>
    <li>Status mapping is applied <strong>per ticket project</strong> (different open/done values per Phasical project, Jira key, Linear team).</li>
    <li>Admin can create and test Shoutrrr notification targets; events on create/error/supersede.</li>
    <li>At least one end-to-end test per MVP source (GitHub, GitLab, Gitea, Forgejo, Codeberg) and per ticket provider (Phasical, Jira, Linear) in CI (mock or sandbox).</li>
    <li>Dashboard, manual poll, settings interval; <code>docker compose up</code> with <strong>one</strong> service.</li>
    <li>Go + web tests green in CI; workflow layout per <a href="#ci">§11 CI/CD</a>.</li>
  </ol>
